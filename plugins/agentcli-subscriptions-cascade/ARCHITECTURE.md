# Каскад подписок — архитектура

Плагин BB `agentcli-subscriptions-cascade` (пакет `bb-plugin-agentcli-subscriptions-cascade`).
Один тред работает на первой ступени каскада, у которой есть лимит.
Ступень — это «машина × провайдер (CLI) × аккаунт». Порядок ступеней владелец
задаёт свободно. Файлы проекта лежат по общему пути, по умолчанию `/opt/bbfs`.
Mutagen держит этот путь одинаковым на всех машинах.

Версия 0.2.7. Готовы настройки, обнаружение, профили каскада, движок выбора
ступени, модуль лимитов, тестовый источник квоты (в том числе для одного треда
из CLI), согласия, служебные строки, мастер «Настроить» и исполнитель пути B
(свой провайдер, импорт штатного моста Claude Code, запуск CLI на машине
ступени, синхронизация Mutagen). Режим исполнения по умолчанию — `provider`.
Карточка подтверждения в ходе и переход Claude ↔ Codex внутри треда — тоже (ниже).

Исследования, на которых держится каркас (приватные, `.local/docs/research/seamless-execution/research/`):
`recon-bb-sdk.md` (пути A и B), `limits-adapters.md` (контракт лимитов и
правила выбора), `cross-provider.md` (контракт адаптера, передача контекста,
карточка подтверждения).

## Модель данных

- **Машина**: вкл./выкл., платформа, общий путь, признак опоры и «SSH к опоре»
  (`anchorSsh`, цель для Mutagen с этой машины; у опоры не используется).
  Опорная машина — Tru, эталон файлов. Нативный Windows получает свой путь
  с пометкой «с переводом путей». WSL получает тот же `/opt/bbfs`.
- **Ступень**: `hostId`, `providerId`, `profileRef` и `account`.
  `authority`: `subscription` или `gateway` — нативный CLI через API-шлюз,
  полноправная ступень. `quotaSource`: `provider` или `vclaude`.
  Ещё у ступени есть `quotaGroup` и `confirm` («спрашивать при входе», профиль
  может переопределить). `onUnknown`: `skip` или `try`.
- **Строка модели**: название, провайдер и ячейки `hostId → {modelId, source: auto|manual|none}`.
  Модель без ассоциации на машине не участвует в каскаде этой машины.
- **Профиль** (`profiles[]`, порядок = порядок в списке моделей): `id` (он же ID
  модели провайдера), название, вкл./выкл., `policy` (`only` | `prefer-then-any` |
  `any`), `modelKey`, `stepOrder` (null — общий порядок; неупомянутые ступени —
  в конце), `excludedSteps`, `excludedProviders` («без Codex», включая будущие
  ступени), `confirm` (stepId → «спрашивать при входе»). Умолчания пишутся,
  только если поля `profiles` нет; пустой список владельца сохраняется.
- **Политики**: `executionMode` (`off` | `relay` | `provider`), `modelPriority`
  (общий приоритет моделей для `any`; неупомянутые строки — следом по таблице),
  подтреды на чужих машинах, возврат через N минут (30) и ожидание сброса до N часов (6).
  Ещё — порог остатка, свежесть показания (60 с), бюджет чтения перед ходом (5 с)
  и перепроверка (5 мин).
- **Файлы**: режим Mutagen по умолчанию и по проекту (`lazy` | `warm`),
  синхронизация `.env` и исключения (`node_modules`, артефакты сборки).
- **Тестовый источник квоты** (`testQuota`): флаг, список тестовых тредов и
  лимит каждой ступени вручную (есть / исчерпан / неизвестен / недоступна, время
  сброса). Движок видит его только в тестовых тредах (`quotaLookupFor`); превью
  и схема «i» на экране считаются по нему, пока флаг включён. Подмена одного
  треда — `testQuota.threads[threadId]` (CLI `test-quota`), действует без общего
  флага; исчерпание с прошедшим сбросом считается «лимит есть». Для S1–S17.
- `bindingEpoch` — отпечаток машины, провайдера, профиля, аккаунта, типа
  квоты и источника квоты. Если он сменился, старые согласия и чтения лимитов
  не действуют.

## Профили каскада

Список моделей провайдера «Каскад» (`model/list`) — это включённые профили, у
которых есть хотя бы одна участвующая ступень; первый — по умолчанию.
Подпись пункта (`description`) — первая ступень и правило, например
«Старт: Opus · Tru — первая в приоритете моделей. Дальше любые модели по
ступеням Tru → Mac → UA; Codex — с подтверждением».

Из коробки: «Авто» (`any`), «Авто · без Codex», «Opus → Авто», «Fable → Авто»
(`prefer-then-any`), «Только Opus 5.5», «Только Fable 5.2» (`only`). Владелец
создаёт («+ Профиль»: «Только модель», «Модель → Авто», «Без Codex»),
дублирует, переименовывает, удаляет, выключает профили и перетаскивает их.
Устаревший ID модели `m:<ключ>` читается как «только X».

Карточка профиля: название, подпись, политика тремя кнопками, модель из таблицы,
чипы ступеней (перетаскивание — свой порядок, щелчок — исключить, «?» —
подтверждение), провайдеры целиком, превью «сейчас ход пошёл бы на: Opus ·
vclaude Mac». Кнопка «i» открывает схему: попытки слева направо, лимит цветом,
отметка «ход сейчас», исключённые — серые и перечёркнутые. В штатном списке
моделей кнопки «i» нет: каталог модели в SDK (`availableModelSchema`) несёт
только `description`, поэтому там видна подпись «Старт: …».

## Выбор ступени (`engine.ts`)

Ступень выбирается до каждого хода, **только между ходами**.

1. `buildPlan(профиль)` разворачивает профиль в попытки «ступень × модель»:
   ступени — включённые, на включённых машинах, в порядке профиля.
   - `only`: модель X по ступеням; ступень без ассоциации — «нет модели».
   - `prefer-then-any`: X по всем ступеням, затем фаза `any` без повторов.
   - `any`: на каждой ступени модели по общему приоритету с ассоциацией на
     машине; нет ни одной строки для провайдера ступени — модель CLI по умолчанию.
   Исключённые ступени и «нет модели» остаются в плане с пометкой `skip`
   (для схемы), в выбор не идут. Подтред без разрешения — только машина родителя.
2. Готова попытка, у которой CLI доступен и квота не исчерпана (лимит
   спрашивается по ступени и модели — модельные окна учитываются). При
   неизвестной квоте всё решает `onUnknown` ступени.
3. Возврат на более приоритетную попытку (S4) — не раньше чем через
   `returnAfterMinutes` после последнего перехода и только при подтверждённой
   квоте (неизвестная квота возврата не даёт, даже с `onUnknown: try`); иначе
   `pendingReturn`.
4. Попытка с подтверждением (профиль поверх ступени) без действующего согласия
   даёт `confirm`. Тот же исполнитель после разового согласия — «Продолжить ещё один ход?».
5. Готовых нет — ожидание ближайшего известного сброса в пределах
   `exhaustedWaitHours`, при неизвестных сбросах — перепроверка через
   `recheckMinutes`, иначе `ask-owner`. «Только X» в «Авто» не уходит.

`explainProfile` вызывает те же `buildPlan` и `selectStep` и ставит отметку
«ход сейчас» по решению движка; тест сверяет схему с `selectStep` на всех
профилях и 128 сочетаниях лимитов.

## Лимиты (`limits.ts`, `LimitsAdapter`)

Контракт дословно из `limits-adapters.md`: `Stage`, `WindowSample`,
`Reading = sample | unknown`, `LimitsAdapter { supports, read, onNativeEvent }`.

- **Подписка Claude / Codex**: `bb.sdk.system.usageLimits({ hostId, refresh: true })`.
  Один запрос на машину; параллельные вызовы объединяются. Пассивно лимиты
  приходят из `rate_limit_event`, строки статуса Claude и
  `account/rateLimits/updated` Codex.
- **Claude через vclaude** (`quotaSource: vclaude`): RPC плагина
  `thread-account-usage.vclaude` (`bb.sdk.plugins.callRpc`). Остаток
  считается **в единицах пакета** (`remaining`), срок пакета — `expiresAt`,
  периодического сброса нет. Ключи и адрес кабинета остаются в
  thread-account-usage. Если плагина нет или он вернул ошибку — `unknown`.
- **Другой шлюз**: опрос не поддерживается (`unsupported`), лимиты приходят
  только из событий CLI (`spend_limit`). Сейчас на Mac usageLimits
  отдаёт `unauthenticated`: это шлюз, а не отсутствие входа.
- Правила: положительное решение — только по показанию не старше
  `positiveFreshSeconds` с известным временем источника. Известное исчерпание
  держится до сброса, его не стирают частичный ответ и отказ источника.
  При нескольких блокирующих окнах возврат возможен после самого позднего
  сброса. Чтение старого `bindingEpoch` отбрасывается.

## Единый адаптер провайдера (`adapter.ts`)

Сведён из `cross-provider.md` и `limits-adapters.md`.

```ts
interface ProviderAdapter<Input, Frame> {
  id; displayName; capabilities(stage);
  relayEnv;                                  // 1. запуск, путь A: какую переменную штатного провайдера подменить
  start(turn, input); resume(session, turn, input); // 1. запуск, путь B / relay
  parseEvent(frame): AdapterEvent[];         // 2. разбор событий
  exportContext(slice): Packet;              // 3. передача контекста
  importContext(packet, turn): Input;
  limits: LimitsAdapter;                     // 4. лимиты: остаток, сброс, тип окна
}
```

Чтобы подключить Gemini CLI или ACP, нужен новый адаптер в `defaultRegistry`.
Движок, лимиты и экран при этом не меняются. `start/resume/exportContext/importContext`
у `claude-code` и `codex` пока бросают `AdapterError('notImplemented', …, beforeDispatch: true)`.

## Поток хода (целевой)

```
сообщение пользователя
  → сервер фиксирует turnId и границу журнала (through)
  → LimitMonitor.refresh(ступени, бюджет 5 с) → healthFromReading
  → selectStep → run | confirm (карточка, ход паркуется) | wait | ask-owner
  → если сменилась машина: handOver (ниже)
  → если сменился провайдер или сессия не пригодна: exportContext(slice) → importContext
  → TurnExecutor.runTurn(target, …) → кадры → parseEvent → таймлайн BB
       ↳ события лимитов → LimitMonitor.observe
  → исход: completed | limit-exhausted (ход закрыт как прерванный → снова selectStep) | auth | failed
  → nextThreadState (ступень, момент перехода)
```

### Передача хода между машинами (`executor.ts`, `handOver`)

Опора — Tru. Переход с машины A на машину B:

1. `pause(A)`: старый исполнитель остановлен, запись в общий путь прекращена.
2. `flush(A → Tru)`: строка «Mac → Tru: flush 0,6 с ✓». Шаг пропускается, если A — опора.
3. `flush(Tru → B)`. Шаг пропускается, если B — опора.
4. На B сверяются корень, конфликты и хеши ожидаемых файлов. Успешный `flush`
   сам по себе содержимого не доказывает (cross-provider.md). При
   расхождении ход остаётся в очереди, тред показывает файл.
5. `resume(B)`, запуск CLI на B.

Mutagen в режиме `lazy` поднимает сессию проекта перед ходом, в `warm` держит
её постоянно. `.env` синхронизируется, если его не выключили. `node_modules`
и артефакты сборки исключены (`syncIgnores`).

## Этапы исполнения (места под разведку)

**Этап 1 — путь A, `executionMode: relay`.** Обёртка над штатными
провайдерами через `bb.providers.experimental_contributeEnv`. Для
`claude-code` подменяется `BB_CLAUDE_CODE_EXECUTABLE`, для `codex` —
`BB_CODEX_BRIDGE_APP_SERVER_COMMAND` и `_ARGS`: туда ставится relay
(`adapter.relayEnv`). Relay вызывает `selectStep` и запускает нативный CLI на
выбранной машине через `bb terminal`. Разбор вывода и таймлайн остаются
штатными. Из `claude-origin-failover` берутся транспорт relay,
`quota-window.mjs` и связка с provider-retry. Запрет нативных инструментов и
склейка истории текстом не берутся. Служебные строки выводятся строкой под
шапкой треда (`app.slots.experimental_threadHeaderRow`) и сообщением в треде.
Набор средств уточнит реализация. Место в коде: `RelayExecutor implements TurnExecutor`.

**Этап 2 — путь B, `executionMode: provider` (реализован).**

```
BB runtime ──stdin/stdout──► мост «Каскада» (bridge/wrapper.ts, процесс на машине треда)
                               │ import()  <кэш демона>/provider-claude-code/<digest>/host.mjs
                               ▼
                           штатный мост Claude Code (разбор, лента, разрешения — штатные)
                               │ spawn BB_CLAUDE_CODE_EXECUTABLE = <dataDir>/launcher/claude-code.sh
                               ▼
                           запускатель (node host.mjs, CASCADE_LAUNCHER_MAIN=1)
                               ├─ POST {BB_SERVER_URL}/api/v1/plugins/<id>/rpc/routeTurn → движок + sync/prepareTurn
                               ├─ события ленты → unix-сокет моста → thread/delta (timeline/)
                               ├─ ступень здесь: spawn claude (модель ступени вместо ID профиля)
                               └─ ступень на другой машине: терминал BB (REST) → агент node → claude
                                    файл сессии --resume туда и обратно; finishTurn → sync/finishTurn
```

- **Импорт без копии.** Сервер считает `sha256(<rootDir>/dist/host.js)`
  штатных плагинов (`bridge/digests.ts`) и кладёт в `providerOptions.cascade.digests`.
  Мост берёт ровно этот каталог кэша, сверяет sha256 и форму экспорта
  (`experimental_apiVersion === 1`, `handleLine`). Нет артефакта, другой digest
  или другая форма — ход отклоняется с подсказкой (`restartRecommended`), тред
  и штатные провайдеры целы (S13). `initialize` без моста отвечает сам.
- **Один процесс CLI на сессию.** Штатный мост держит `claude` на всю сессию
  (stream-json) и запускает короткие пробы (`--fork-session --no-session-persistence`).
  Поэтому ступень выбирается в запускателе на каждом сообщении пользователя
  (`launcher/session-relay.ts`): та же ступень — сообщение текущему процессу;
  другая — процесс закрывается, новый стартует на новой ступени с `--resume`,
  служебные запросы начала сессии повторяются ему, ответы на них мосту не идут.
  Пробы идут туда же, где прошлый ход, без синхронизации.
- **Канал до машины ступени** — терминал BB по REST сервера
  (`/api/v1/terminals`, без процесса `bb` на опрос; веб-сокет терминала через
  прокси Mac не открывается). Кадры `@@CX` в base64 через PTY, нумерация кадров
  stdout, сердцебиение и сторожевой таймер агента, повтор опроса до 90 с;
  усечённая прокрутка и пропуск кадра — авария. Терминал живёт на демоне машины
  ступени, обрыв связи с сервером не рвёт CLI. Автоповтора после аварии нет.
- **Файл сессии.** У каждой машины свой `~/.claude`: при `--resume` файл
  уезжает на машину ступени (gzip, sha256) и возвращается после выхода. Файл
  только дописывается, поэтому более длинное продолжение не затирается — ни
  пробой со старой копией на машине ступени, ни возвратом на машине моста.
  Логин и токены не переносятся; `ANTHROPIC_*`, OAuth, `*_TOKEN`/`*_KEY` не уезжают.
- **Чужая машина.** Флаги с локальными путями (`--mcp-config`, `--settings`,
  `--plugin-dir`, `--strict-mcp-config`) отбрасываются: MCP-инструменты BB на
  чужой машине недоступны. Под root агент делает то же, что штатный мост BB:
  `bypassPermissions` → `default` (разрешения идут через `can_use_tool`).
- **Codex** — app-server живёт весь runtime: ступень выбирается при его старте
  (там же карточка подтверждения входа на ступень Codex), смена машины — после
  перезапуска runtime. Модель ступени Codex мост ставит в `options.model`
  (профиль каскада «auto» Codex не понимает).
- **Переход Claude ↔ Codex внутри треда** (0.1.5) — в мосте на `turn/start`:
  1. RPC `peekProvider` (тот же движок, без побочных эффектов): чей ход.
  2. Тот же провайдер — ход уходит его штатному мосту как раньше.
  3. Другой — у каждого провайдера своя нативная сессия, курсор — номер события
     треда (`seq`). Первый переход: служебный `thread/start` штатному мосту
     нового провайдера, первым элементом ввода — сводка (RPC `handoffBrief`,
     `bridge/handoff.ts`: сообщения пользователя дословно, ответы агента,
     команды, правки файлов; без рассуждений и без текущего запроса) с подсказкой
     `bb thread messages <тред> --json --after-seq N`. Возврат: `thread/resume`
     прежней сессии (`--resume` у Claude) + дельта событий после её курсора.
     Сессия недоступна (`thread/resume` с ошибкой или `sessionRestorable:false`)
     — новая сессия со сводкой с начала треда и строка в ленте.
  4. BB знает один `providerThreadId` треда (outerId — первая сессия): мост
     переводит его в ID сессии активного провайдера во входящих командах и
     обратно в исходящих событиях; ответ на служебный `thread/start|resume`
     в BB не уходит.
  5. Курсоры и активный провайдер хранятся на сервере (`StoredThreadState.native`,
     RPC `nativeSessions`) — переживают перезапуск моста. Уходящая сессия
     получает курсор `through` (последнее событие до текущего запроса).
  Сервер не ответил — ход остаётся у активного провайдера. Курсор сдвигается
  при отправке хода, без проверки сохранения сессии CLI (cross-provider.md,
  шаг 7 — следующий этап).
- **Паспорт треда** для других плагинов: RPC `threadStatus` и
  `bb subscriptions-cascade status --thread <id> --json` →
  `{cascade, profileId, step{hostId, providerId, model, accountKey, kind}, anchorHostId, syncMode, path, freshCopyHostId}`.
- **Перевод тредов**: `bb subscriptions-cascade adopt --stuck|--thread <id>|--project <id> [--dry-run] [--model <профиль>]`
  — штатный Handoff (`--to subscriptions-cascade`) и `provider-retry cancel` у исходного.

Опирается на внутренности BB 0.50.1 (проверять после обновления BB):
кэш артефактов `<daemonDataDir>/plugin-host-artifacts/<pluginId>/<sha256>/host.mjs`,
`BB_CLAUDE_CODE_EXECUTABLE`, `BB_CODEX_BRIDGE_APP_SERVER_COMMAND/_ARGS`, ключи
`providerOptions` моста Claude (`memoryEnabled`, `sandboxEnabled` …), REST
`/api/v1/terminals*` и `/api/v1/plugins/<id>/rpc|cli`, формат ID терминала
`term_[23456789a-km-z]{10}`, поведение моста под root (`isBypassPermissionsAvailable`).

## Сбои и штатные механизмы BB (S14–S17)

Проверено по коду BB 0.50.1 (встроенные `provider-retry` 0.1.0 и `provider-claude-code`).

- **S14, ошибки без лимита.** CLI ступени пишет свой `result` в тот же stdout,
  штатный мост Claude разбирает его сам: `api_error_status` → `errorInfo`
  (529 → `overloaded`, 5xx → `internal`, 429 → `rate-limit`). `provider-retry`
  фильтра по провайдеру не имеет — смотрит только `errorInfo.category` и
  `httpStatusCode`, поэтому 529/5xx у треда каскада повторяются так же, как у
  штатного Claude. Падение процесса CLI без `result` даёт `errorInfo: null` —
  как и у штатного Claude, автоповтора нет. Каскад на такие ошибки ступень не
  меняет: в лимиты (`observeLimit`) попадают только события лимита.
- **Лимит посреди хода.** На ошибку лимита `provider-retry` спрашивает все
  плагины с discoverable-методом `provider-retry.v1.availability`. Каскад
  отвечает за свои треды (`retryAvailability`): есть готовая ступень — `ready`
  (повтор сразу, ход идёт на следующую ступень), всё исчерпано — `blocked` до
  ближайшего сброса, дольше порога — `unavailable`, чужой тред или режим `off` —
  `not-routed` (политика provider-retry не меняется). Оригинал не правится.
- **Отказ каскада** (лимиты, сервер каскада не ответил, файлы не готовы) — код
  выхода запускателя 75/1 без `result`: штатного автоповтора нет, в ленте
  строка с причиной. Сервер каскада не ответил — ход не запускается (без
  тихого перехода на штатный CLI машины моста).
- **S15, обрыв канала до машины ступени.** CLI живёт в терминале BB на демоне
  машины ступени; опрос вывода повторяется до 90 с, кадры пронумерованы —
  продолжение с места обрыва, без повторов и без второго запуска CLI. Обрыв
  дольше — авария хода (`transportError`), автоповтора нет: повтор того же
  сообщения задублировал бы ход. Файл сессии на машине ступени длиннее — его
  не затирает следующий `--resume`.
- **S16, очередь, steer, автоматизации, подтреды.** Каждое новое сообщение
  пользователя (из очереди, автоматизации, `bb thread spawn --provider
  subscriptions-cascade --model auto`) — новый ход и новый выбор ступени. Steer
  (`bb thread tell` в идущий ход) уходит текущему процессу CLI без выбора
  ступени: ступень меняется только между ходами.
- **S17, остановка хода.** Прерывание хода штатный мост шлёт в stdin CLI — реле
  передаёт его процессу ступени. Сигнал процессу (stop/close треда) запускатель
  перехватывает: CLI ступени получает SIGTERM — локально напрямую, на чужой
  машине кадром `K` агенту в терминале BB.

## Мастер «Настроить» на сервере, SSH одной кнопкой, ленивая настройка (0.2.1)

- **Состояние на сервере.** Шаги машин — `bb.storage.kv` (`wizard:<hostId>`),
  мастер исполняет сервер (`setup` в `server.ts`): экран можно закрыть, при
  возврате видно, где остановились («Продолжить»). Входы: Настройки → плагин
  → «Каскад подписок» (секция «Машины»), кнопка «Настроить» под цепочкой
  ступеней, CLI `bb subscriptions-cascade setup [--machine <id|имя>]
  [--recheck] [--reset] [--allow-ssh] [--dry-run] [--json]`, строка-отказ
  ленты («Что сделать: … Настроить …»). RPC экрана и мастера discoverable.
- **«Перепроверить всё»** (`recheck`) — проверки всех шагов заново, ничего
  не удаляя. **«Настроить с нуля»** (`reset`, с подтверждением) — снять
  сессии Mutagen каскада (`bbcascade=1`), убрать ключи каскада из
  `authorized_keys` опоры, алиас и ключ на исполнителе, сбросить шаги; файлы
  проектов и общий путь не трогаются. То же — в строке каждой машины.
- **Шаг ssh** (`sync/ssh-setup.ts`): проверка `ssh -o BatchMode=yes`; нет
  входа — ключ `~/.ssh/bb_cascade_ed25519` (ed25519, без пароля) на
  исполнителе; затем **согласие владельца** («Разрешить машине X входить на Y
  по ключу SHA256:…», с открытым ключом и местом записи) — кнопка «Разрешить
  вход по ключу» или `--allow-ssh`; ключ в `authorized_keys` пользователя
  опоры (без дублей, пометка `bb-cascade:<hostId>`), блок `Host bb-<опора>`
  в `~/.ssh/config` исполнителя (HostName = «Адрес для SSH» опоры,
  IdentitiesOnly, ServerAliveInterval), проверка входа, «SSH к опоре»
  машины = алиас. Выключение машины снимает ключ с опоры и алиас.
- **Ленивая настройка при ходе.** Подготовка хода упала на ненастроенной
  машине (`not-configured`/ошибка) — сервер запускает мастер для этой
  машины (без шагов, требующих согласия) и повторяет подготовку; строка
  подготовки показывает «настройка UA: мастер». Нужно согласие (ключ на
  опору; системное окно пароля Mac ждёт человека) — ступень пропускается в
  этом ходе со строкой «Нужно разрешение … Разрешить: …», ход идёт на
  следующую ступень. Карточки «Нужно разрешение» в ленте нет — строка с действием.

## Отказ с автоповтором BB (0.2.2)

Каскад не просит владельца «отправить сообщение ещё раз». Отказ, после которого
ход надо повторить, запускатель отдаёт штатному мосту Claude в форме вывода CLI
(`syntheticRefusal`), и повтор делает встроенный provider-retry:

- `limit` — `rate_limit_event` rejected + `result` с 429: provider-retry
  спрашивает `provider-retry.v1.availability`, каскад отвечает `ready`, повтор
  идёт на другую ступень. Так переходит ход, уже начатый в мосту Claude, на
  Codex после «Да» в карточке (S3): согласие «на этот ход» переносится на повтор
  (`carryConsent`, 15 мин, один раз), мост каскада выбирает мост Codex по
  `peekProvider` до запуска моста Claude. Адрес сервера мост берёт из `envVars`
  запросов runtime — у процесса моста `BB_SERVER_URL` может не быть (из-за
  этого на 0.2.0 Codex не выбирался, и карточка ходила по кругу).
- Модель недоступна на аккаунте («Fable 5.2 requires usage credits»): попытка
  ступень × модель снимается для треда (`modelBlocks`) и на сутки в таблице
  моделей (ячейка «недоступна на аккаунте» с причиной), ход отдаётся как
  `limit` — повтор на следующей попытке профиля. Распознаётся в выводе Claude
  Code; у Codex (app-server, без реле) — пока нет.
- `overload` — `result` с 529: плагин переустановлен посреди подготовки
  («generation … is retired», «stale API handle»), повтор через секунды уже
  на новой версии; в ленте «Плагин обновился — ход повторится автоматически».
- Первое сообщение сессии с таким отказом: CLI машины моста запускается только
  ради начала сессии (не тратит лимит), сообщение получает отказ, следующие —
  по каскаду.

## Первый ход, карточка и Codex (0.2.3–0.2.4)

- **Ответ provider-retry** (`provider-retry.v1.availability`, таймаут BB — 5 с)
  — только из имеющегося состояния, бюджет 1,5 с; свой тред (есть сохранённое
  состояние каскада) — `ready`/`blocked`/`unavailable`, чужой — `not-routed`.
- **Ступень выбирается в ходе.** Сессия stream-json Claude стартует на
  `thread.start`, до сообщения: запускатель поднимает CLI машины моста только
  для начала сессии, ступень (и карточку подтверждения) выбирает на первом
  сообщении — как у следующих ходов. На `thread.start` BB карточку не покажет.
- **Сессия Codex — после «Да».** `peekProvider` выбирает другого провайдера
  только по решённому ходу (`run`); при «нужно подтверждение» мост остаётся на
  текущем провайдере, его ход показывает карточку, «Да» → повтор хода штатным
  автоповтором, на повторе согласие «на ход» уже есть → мост открывает сессию Codex.
- **Запуск app-server.** Штатный мост Codex при подменённой команде без
  `BB_CODEX_BRIDGE_APP_SERVER_ARGS` запускает её без аргументов: `codex`
  стартовал TUI («stdin is not a terminal»). Мост задаёт `ARGS=["app-server"]`,
  запускатель добавляет `app-server`, если подкоманды нет. На чужой машине
  агент запускает CLI с пайпами (без TTY). Старт app-server — открытие
  сессии, не ход: карточку там не спрашиваем.

## App-server Codex всегда через каскад (0.2.5)

Штатный мост Codex держит app-server на каждый тред, но запускает его с
`process.env` и тремя переменными Codex — без `BB_THREAD_ID`. Запускатель без
треда уходил в штатный `codex` на машине треда мимо маршрута (S3 на 0.2.4).
Теперь мост каскада, отдавая команду треда мосту Codex, запоминает этот тред, и
запускатель app-server спрашивает его через сокет моста (`{whoami:"codex"}`,
запасной путь — `CASCADE_THREAD_ID`). Тем же ответом приходит адрес сервера BB
(`serverUrl`, запасной путь — `CASCADE_SERVER_URL`): `BB_SERVER_URL` у app-server
тоже нет, мост знает его из `envVars` запросов runtime. Дальше — `routeTurn`, синхронизация и
запуск на машине ступени. Тред не узнан — отказ «Codex не запущен мимо
каскада»; служебный app-server без треда (`maintenance`) — штатно.

Автоповтор после «Да» приходит вводом «Please continue.»: сводка для Codex
добавляет блок `<current-request>` с исходной просьбой пользователя и
пометкой, что это повтор, а не новая задача.

## Реле app-server Codex (0.2.7)

- **Пути.** Мост Codex шлёт пути машины треда (worktree на опоре), на машине
  ступени проект — в общем пути `/opt/bbfs/<единица>`. Запускатель переписывает
  все строки JSON-RPC моста (initialize, thread/start, turn/start …) на путь
  ступени, ответы app-server — обратно (`launcher/codex-relay.ts`); app-server
  стартует в папке ступени.
- **Синхронизация на каждый ход.** Первый ход подготовлен маршрутом при старте
  app-server; после `turn/completed` файлы возвращаются на опору (RPC
  `syncTurn` phase finish), перед следующим `turn/start` — снова готовятся
  (`syncTurn` prepare, машина закреплена за app-server). Подготовка не удалась —
  ошибка на этот `turn/start` с причиной.
- **Сводка в тексте ввода.** Сводка перехода вклеивается в текст первого
  текстового элемента ввода (поля `mentions`, `visibility` сохраняются).
  Исходная просьба для автоповтора берётся по `retryOfRequestId` запроса.
  Сводка задаёт рамки: продолжать просьбу, не исследовать окружение, ключи,
  чужие треды и дела; историю этого треда — только при нехватке контекста.
- **Строки ленты перехода** ждут открытия хода нового провайдера (сессия и
  app-server открываются до его хода, BB строки без хода не показывает) и
  выходят с его providerTurnId; переход не состоялся — выходят сразу.

## Обновление плагина и зависимостей

- **Mutagen.** Версия и SHA-256 архивов заданы в `sync/setup.ts`
  (`MUTAGEN_VERSION`, `MUTAGEN_SHA256`). Проверка шага mutagen сравнивает
  версию: другая — обновить, но только если на машине нет идущих сессий
  каскада; иначе обновление откладывается до следующей подготовки хода.
  Установка останавливает демон прежней версии. Версия входит в отпечаток
  сессии (`MUTAGEN_SESSION_VERSION`, `bbc-cfg`): после обновления сессии
  пересоздаются, агенты Mutagen на обеих сторонах одной версии.
- **Агент на машине ступени** (`launcher/agent-source.ts`) не ставится:
  его исходник передаётся в терминал BB при каждом запуске, поэтому новая
  версия плагина сразу работает новым агентом.
- **`bb plugin install` новой версии.** Сервер плагина перезагружается:
  таймеры снимаются в `bb.onDispose`, состояние тредов, мастера и согласий
  лежит в `bb.storage.kv` и переживает перезагрузку; прогресс подготовки
  (в памяти) теряется — идущая подготовка закончится отказом с причиной и
  повторяемым кодом. Мост новой версии пишет новые скрипты запускателя при
  старте runtime; уже идущий ход доводит старый процесс запускателя (его
  RPC к серверу совместимы в пределах контракта), новые ходы идут на новой
  версии после перезапуска runtime треда. CLI на чужой машине при остановке
  хода получает SIGTERM (S17). Проверено юнит-тестами (перезагрузка без
  утечки таймеров, смена версии Mutagen); на живом BB — при установке 0.2.x.

## Согласия и подтреды (`consent.ts`)

Карточка: «Перейти · на этот ход / в треде до сброса / навсегда»,
«Пропустить ступень», «Ждать прежнюю», «Отменить ход».

- Тредовое согласие действует до сброса окна, из-за которого произошёл переход.
  Если время неизвестно — до ручного отзыва.
- «Навсегда» — правило для ступени в проекте, включая будущие треды.
- Подтред — свой тред: разовые и тредовые согласия родителя к нему не
  переходят. Подтред без `subthreadsUseOtherMachines` не уходит с машины
  родителя.

**Карточка в ходе (0.1.5).** `routeTurn` на решение `confirm` отвечает
`{ action: 'confirm', prompt }` (откуда → куда, причина, граница тредового
согласия = сброс окна прежней ступени, «новая сессия со сводкой» / «прежняя
сессия + события»). Запускатель (`launcher/confirm.ts`) внутри хода штатного
моста просит мост каскада показать карточку: строка `{threadId, turnKey, confirm}`
в сокет моста → `timeline/` `requestConfirmation` → `interaction/request`
(`payload.kind = agentcli-subscriptions-cascade/confirm-step`, `turnId` — текущий
ход). Ждёт ответа без таймаута, ответ — RPC `answerConfirmation`, затем
`routeTurn` снова с тем же `turnKey`:

- «Да»: согласие `turn` (этот ход, `turnKey`), `thread` (до сброса окна, иначе
  до отзыва) — в состоянии треда; `forever` — правило проекта в kv
  (`exec:consents:<проект>`), действует и в других тредах.
- «Пропустить ступень» — `skippedStepIds` только этого хода (`skipTurnKey`).
- «Ждать прежнюю» — ход не идёт (код 75), строка ожидания до сброса.
- «Отменить ход», закрытая карточка, карточку показать нельзя — ход не идёт.

Ответ проверяется по `proposalId` и ревизии (`timeline/decide`); ответ к
другой карточке — спросить заново. Запускатель ушёл (ход прерван) — карточка
снимается. Ответы runtime на карточки мост принимает мимо очереди входящих.

## Мастер «Настроить» (`wizard.ts`)

Шаги на каждой включённой машине: `probe` (хост-RPC, только чтение) →
`folder` → `mutagen` → `verify` (команда и пробная запись через `bb file`).
У каждого шага сначала идёт проверка, применение — только если она не прошла.
Поэтому повторный запуск безопасен и продолжает с места остановки. Ошибка
останавливает текущую машину, остальные машины идут дальше. Права:

- macOS — системное окно `do shell script … with administrator privileges`;
- Linux под root — без запроса;
- Linux не под root — `sudo -n`, иначе шаг ручной;
- нативный Windows — Mutagen ставится вручную.

Команды выполняются через `bb.sdk.terminals.create({ scope: host_path, start: argv })`.
«Предпросмотр шагов» (`dryRun`) ничего не выполняет. Путь с особыми символами
не подставляется в команды с правами.
