# Image Gen — архитектура


## Решение

Отдельный BB-плагин `image-gen` (папка `plugins/image-gen` этого репозитория, метки `image-gen/vX.Y.Z`), устроенный по образцу Local Transcribe.
**Codex** рисует сам встроенным `image_gen`. **Остальные провайдеры** вызывают `image_generate` или
`image_edit`. Плагин запускает `codex exec` обычным процессом в BB-терминале выбранной машины,
забирает картинку из `$CODEX_HOME/generated_images/<codex thread id>/`, проверяет SHA-256 и
кладёт её в папку проекта вызывающего. Служебных BB-тредов нет.

Почему не Codex-тред на каждую картинку: такие треды пришлось бы выбирать и убирать, они плодят
«зоопарк». Почему не отдельный HTTP-сервис: нужны порты, авторизация и деплой на каждую машину.
BB уже даёт всё необходимое: KV, host-RPC, терминалы, инструменты агентов, CLI, инструкции и
уведомления.

## Интерфейсы

| Кто | Как |
|---|---|
| Агент любого провайдера | инструменты `image_generate`, `image_edit`, `image_status`, `image_cancel`, `image_retry`, `image_services` |
| Человек / скрипт в треде | `bb image-gen generate --prompt … [--out dir] [--ref f]…`, `bb image-gen edit --image f --prompt …`, `status`, `cancel`, `services` |
| Другие плагины | discoverable RPC `image-gen`: `services`, `generate`, `edit`, `status`, `cancel`, `retry` |
| Инструкции | Codex: «рисуй сам; если инструмента нет или лимит — один раз `image_generate`». Остальные: «вызывай `image_generate`/`image_edit`». Провайдер берётся из треда (`providerId`). Модель на выбор не влияет. |

`image_edit` = генерация в режиме правки: первая картинка правится по инструкции, остальные
служат референсами. Исходный файл не меняется.

## Где что работает

| Часть | Где | Ресурсы |
|---|---|---|
| `server.ts` (очередь, каскад, доставка, уведомления) | внутри процесса сервера BB | ≈240 КБ кода, своих процессов и портов нет |
| `host.ts` (probe, файлы, lease) | в общем plugin-host процессе на каждой машине BB | ≈250 КБ кода |
| `runner/imagegen_runner.py` (stdlib) | раскладывается в `<host-data>/runtimes/<sha>/` при первом вызове | работает только во время задания |
| `codex exec` | терминал на машине-исполнителе | ≈150–200 МБ, ~40 с на картинку |
| Задания | KV плагина на сервере BB | несколько КБ на задание |
| Рабочие папки | `<host-data>/jobs/<jobId>_<n>/` у исполнителя | удаляются через `keepDays` (30) |
| Авторизация | собственный `codex login` машины; ключ API — секретная настройка (файл 0600) | плагин не читает `auth.json` |

## Каскад

1. явно запрошенный `executor`;
2. машина вызывающего треда;
3. остальные готовые машины, сначала свободные;
4. tier 1 — платный OpenAI API (`maxTier=1` и `openaiApiKey`).

Готовность машины (`probe`): найден `codex` (PATH login-shell или `~/.local/bin`, `/opt/homebrew/bin`,
`/usr/local/bin`, `/usr/bin`; переопределяется через `IMAGEGEN_CODEX_BIN`), `codex login status` = ChatGPT,
`image_generation=true`, есть python3 ≥ 3.9.

| Исход попытки | Дальше |
|---|---|
| completed | доставка → completed |
| not_started / auth | следующий исполнитель |
| limited | только исполнитель с другим `accountGroups`, иначе `limited` (+ время сброса, если Codex его сообщил) |
| failed (Codex отработал, картинки нет) | failed; тот же запрос можно повторить |
| unknown / fenced | `unknown`, без автоповтора; `image_retry confirmUnknown=true` — только с согласия пользователя |
| cancel | терминал закрыт, без fallback, без уведомления |

**Если нет Codex.** На машине вызывающего Codex нет, а на другой есть — генерирует другая машина,
файл возвращается вызывающему. Codex нет ни на одной машине — задание сразу `failed`
с объяснением: где чего не хватает и два пути (поставить Codex и выполнить `codex login`
или включить платный API).

## Жизненный цикл и гарантии

`queued → starting → running → returning → completed` (`failed | limited | unknown | cancelled | return_failed`).

- Ожидание: инструмент ждёт до `waitSeconds` (по умолчанию 120 с). Если успел — результат приходит
  в ответе и уведомление не отправляется. Если нет — возвращается `jobId`, а позже приходит ровно
  одно уведомление (`queue-if-active`, маркер, восстановление после неясной отправки).
- Дубли: ключ запроса — тред + `clientKey` либо промпт/референсы/режим/папка. Для активного,
  готового или `unknown` задания повтор возвращает то же задание.
- Исполнитель пишет `attempt.json` **до** старта Codex. Есть attempt, но нет результата → картинка
  восстанавливается из `generated_images` или фиксируется `unknown`; повторной генерации нет.
- Перезапуск BB: задания в KV, ID терминала детерминирован, результат читается с машины.
- Потеря машины: lease (120 с) истекает, исполнитель сам останавливает Codex.
- Доставка: передача блоками по 1 МБ через host-RPC. У каждой передачи свой временный файл,
  итоговый файл создаётся через link без перезаписи и проверяется по SHA-256. Рядом кладётся
  `*.png.json` с происхождением.

## Установка, обновление, откат, другой человек

```sh
bb plugin install 'git:https://github.com/<owner>/bb-config.git@^0.1.0' --subdirectory plugins/image-gen --tag-prefix image-gen/ --yes
bb plugin update image-gen --yes                  # релиз = тег vX.Y.Z
bb plugin install 'git:…@v0.1.2' --yes            # откат на конкретный тег
bb plugin config image-gen set maxTier 1          # только если нужен платный API
```

Исполнитель встроен в сборку (`runtime.generated.ts`, SHA-256) и раскладывается по машинам при
первом вызове новой версии. Другой человек ставит этот же Git-плагин в свой BB и логинит Codex
на своих машинах. В коде нет адресов и ID машин: всё задаётся настройками.

## Проверки

- `npm test`: 21 JS-тест (ядро + e2e собранного плагина с подставным BB на двух машинах
  и подставным Codex) и 9 тестов исполнителя. Реальных генераций нет.
- Реально, 17.11.2026, в рабочем BB:
  - установка из GitHub, обновления 0.1.0 → 0.1.3 через `bb plugin update`;
  - генерация на сервере ≈40 с;
  - правка по картинке на второй машине с доставкой обратно;
  - спящая машина показана как offline.
- Реальные ошибки, пойманные этими проверками и исправленные:
  - `codex login status` пишет в stderr;
  - `codex exec -i` проглатывал промпт без `--`.
- Ещё не проверено вживую:
  - лимит подписки (тексты взяты из старого сервиса);
  - платный API (только на подставном fetch);
  - Codex-тред, переходящий на `image_generate`;
  - потеря машины посреди генерации.
