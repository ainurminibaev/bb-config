# Настройка и восстановление

## Базовые настройки Codex на каждой машине

Для scripts/codex_defaults.py нужен Python 3.11+.

`config/codex.json` хранит безопасные общие defaults CLI. Сейчас это минимальный
`project_doc_max_bytes = 65536`: штатный бюджет Codex 32768 байт обрезает большие
AGENTS.md, включая симлинк на CLAUDE.md. Это настройка загрузчика Codex,
не context-mode. Смена модели не меняет бюджет.

`scripts/restore.py --apply` автоматически применяет этот default на текущей
машине под текущим пользователем, в том числе без `--plugins`. Для
установки без фонового плагина этот шаг выполняется на каждой машине и для
каждого отдельного CODEX_HOME.

Для отдельной установки/обновления Codex без восстановления остальных настроек:

```sh
python3 scripts/codex_defaults.py --apply --verify
python3 scripts/codex_defaults.py --check --verify
```

Скрипт учитывает CODEX_HOME (иначе ~/.codex), меняет только корневой параметр,
атомарно сохраняет файл с прежними правами, сохраняет больший заданный бюджет.
Авторизации, MCP, маршруты, аккаунты и прочие поля не копирует и не меняет.
`--check` возвращает ненулевой код при недостающей настройке; `--verify`
проверяет реальный `codex debug prompt-input` с маркером после 34000 байт,
без вызова модели. Проверка требует установленного Codex с этой командой.
Начать новую сессию после применения; работающие процессы не перезапускаются.
Переопределения в проектном конфиге и аргументах CLI имеют свой приоритет.

При установке или обновлении CLI на новой машине применяй defaults до первого
рабочего треда и проверяй их после обновления. Снимок `snapshot.py` сохраняет
настройки BB; native-настройка Codex восстанавливается из config/codex.json
через скрипт выше, без копирования полного профиля CLI.

### Проверка новых установок

Общий defaults-файл и его применение входят в restore.py --apply. Для установки
одного CLI без полного restore обязательный шаг — codex_defaults.py --apply --verify.
Правило закреплено в AGENTS.md: установив или подключив новую машину, агент
проверяет native-настройку под пользователем запуска Codex до первого рабочего
треда. Простое подключение машины к BB само по себе скрипт не запускает.
Отдельный фоновый плагин для этой настройки не установлен.

## Context Mode для CLI

Context Mode подключается отдельно в пользовательском профиле каждой машины.
Источник: [mksglu/context-mode](https://github.com/mksglu/context-mode), npm-пакет
`context-mode`. Проверенная версия — `2.2.0`; настроены Codex CLI и Claude Code.
Инвентаризация машин и результаты проверки хранятся только в `.local/docs/`.
Это расширение CLI, поэтому запись в списке плагинов BB не требуется.

Восстановление выполняется под тем пользователем, от которого BB запускает CLI,
на каждой нужной машине, с Node.js, поддерживающим `node:sqlite`:

```sh
npm install -g context-mode@2.2.0
context-mode setup --dry-run --agents codex,claude-code --json
context-mode setup --yes --agents codex,claude-code --json
context-mode doctor --no-input --agents codex,claude-code --json
```

Выбирай только установленные CLI. Для инвентаризации используй
`context-mode setup --list` и `context-mode setup --dry-run --json`.
Настройщик подключает MCP, хуки и навыки Codex, устанавливает либо обновляет
плагин Claude Code, создаёт локальную резервную копию изменённых файлов и
откатывает настройку агента при неуспешной проверке. Другие настройки профиля
сохраняются. После изменения нужно перезапустить CLI или открыть новую сессию.

Проверка включает MCP handshake и пробный вызов хука. Предупреждение
`hook-seen: not seen yet` означает, что ещё нужен обычный вызов инструмента в
новой сессии. Снимок `scripts/snapshot.py --settings-only` сохраняет настройки BB,
но не настройки CLI; их подключение восстанавливается командами выше.
Не копируй целиком профили CLI в Git: они могут содержать авторизации.

При переходе со старой установки `setup` может пройти, а отдельный `doctor`
вернуть `old context-mode entry`. В этом случае сначала сохрани резервную
копию `~/.claude/settings.json`, удали из его `hooks` только команды
`context-mode-cache-heal`, перенеси скрипт
`~/.claude/hooks/context-mode-cache-heal.mjs` (или `.sh`) и каталоги
`~/.claude/context-mode`, `~/.codex/context-mode` в локальную папку резервной
копии за пределами профилей агентов и повтори `doctor`. Не удаляй содержимое
этих каталогов и не переноси его в репозиторий. Если doctor отмечает старые
`~/.context-mode/content` или `~/.context-mode/platform.json`, также перенеси
их в локальную резервную копию. Временные файлы doctor только отмечает;
они не требуют очистки. Результат `setup` не заменяет отдельную проверку `doctor`.

## Автоматический логотип проекта

В версии Project Logo 0.2.1 проверка и установка значка выбирают источник
проекта на машине текущего треда через SDK threads/environments. Основной
источник на другой машине больше не используется для этого треда. Если на
текущей машине нет источника, операция завершается без записи. CLI вне треда
этого проекта сохраняет выбор основного источника. Восстановление: сборка
`bb plugin build plugins/project-logo`, затем `bb plugin reload project-logo`;
проверка — `bb project-logo status <project-id>` из треда нужной машины.

Собственный плагин `project-logo` (`plugins/project-logo/`) подключает подбор
логотипа к первому запуску агента в треде обычного проекта. Агент учитывает
название проекта и первое сообщение пользователя: например, проект обновления
автомобиля вместе с обсуждением Changan получает фирменную эмблему Changan.
Сначала проверяются имеющиеся значки и материалы проекта, затем подбирается
подлинный знак, предпочтительно с официального сайта. Начиная с 0.2.0, если
готового знака нет, агент сам создаёт оригинальную простую SVG-иконку по смыслу
проекта и первого сообщения: без надписей, монохромную, читаемую при 20px.
Копировать или придумывать чужую фирменную эмблему нельзя. Подтверждение выбора
у пользователя не требуется; явный запрет изменений соблюдается.

Это задача текущего агента, а не отдельный AI-сервис или фоновый тред.
Плагин не запускает других агентов и не меняет маршруты или аккаунты.
Инструкции и инструменты приходят при следующем создании сессии провайдера;
уже работающая сессия может потребовать перезапуска после окончания хода.
Тред помечается завершённым только при наличии/установке иконки; пустая проверка
остаётся доступной для повтора. Старые отметки 0.1.0 перепроверяются один раз
по версии политики. Смена темы чата не заменяет общую иконку проекта.
У агента должны быть средства поиска и работы с файлами; соблюдение шага
зависит от выполнения агентом инструкции, это не гарантированная фоновая загрузка.

`project_logo_status` сообщает существующий значок и фактические host/root
источника проекта. `project_logo_install` принимает относительный путь к
скачанному файлу внутри этого checkout и URL страницы-источника, либо поле
`svg` с оригинальным SVG и `sourceUrl: generated from project context`
(ровно один из `filePath`/`svg`). Запись идёт
через SDK на машину источника, а не в cwd сервера. Плагин сохраняет PNG или
самодостаточный SVG до 256 КБ в `.bb/icon.png` / `.bb/icon.svg` и обновляет
Machine Tabs. Значок общий для проекта и его тредов, в списке он серый.
Существующие значки и favicon сохраняются; конкурентные установки для одного
проекта сериализованы, новая запись требует отсутствующего файла. Ошибка
доступа к машине не трактуется как отсутствие значка. SVG с активным содержимым,
внешними ресурсами или неподдерживаемой разметкой отклоняется.

Ручная проверка и установка:

```sh
bb project-logo status <project-id>
bb project-logo install <project-id> <relative-image-path> <source-page-url>
bb project-logo create <project-id> '<svg ...>...</svg>'
bb machine-tabs icons
```

Исходники, манифест, lock-файл и навык хранятся в репозитории. Установка на
сервере BB: `npm ci --prefix plugins/project-logo`, затем
`bb plugin build plugins/project-logo` и `bb plugin install ./plugins/project-logo`.
Обновление уже установленной версии: сборка и `bb plugin reload project-logo`.
Общее восстановление: `python3 scripts/restore.py --plugins --apply`.
Наличие Machine Tabs нужно для показа изображений в боковом списке.
Снимок настроек сохраняется в `.local/config/`; выбранные изображения лежат в
самих проектах и восстанавливаются вместе с их файлами, а не из bb-config.
Никакие переписки или авторизации для этой функции в репозиторий не копируются.

Проверки: `npm test --prefix plugins/project-logo` и
`npm run typecheck --prefix plugins/project-logo`. Тесты проверяют конфигурацию
нового треда, SVG, правильную машину, сохранение существующего favicon,
конкурентную установку, недоступный хост и обновление списка.

## Classic / Custom в боковом меню

Machine Tabs (`plugins/machine-tabs/`) добавляет текстовые кнопки
`Classic | Custom` рядом с New thread. Classic выбирает штатный провайдер
`thread-list/thread-list` установленной версии BB; Custom возвращает
`machine-tabs/machine-tabs`. Поэтому обновления штатного списка доступны
без копирования старого интерфейса. Переключатель остаётся в обоих режимах,
а выбор синхронизируется между окнами. Настройки Machine Tabs сохраняются.
Штатные предпочтения группировки и другие плагины остаются активными:
Classic переключает только провайдер списка тредов.

С версии 0.2.0 в строке поиска есть кнопка-воронка. Она открывает строку с
двумя фильтрами: тема и проект. Фильтры действуют вместе с вкладкой машины и
поиском (включая архив и текст сообщений) и применяются и к блоку Last 5. Тема
определяется на устройстве по словам в названии треда (русским и английским);
названия без совпадений относятся к «Обсуждению». Пока активен фильтр или
поиск, справа виден счётчик вида «7 из 24»: показано тредов из общего числа на
выбранной вкладке; предки найденного дочернего треда входят в первое число.
Крестик сбрасывает фильтры. Выбор фильтров не сохраняется между перезагрузками
страницы. Сортировка по-прежнему выбирается в меню группировки.

С версии 0.2.1 оба фильтра открывают собственный список вместо системного.
Варианты отсортированы по числу тредов, которое останется при выборе (с учётом
второго фильтра и вкладки машины); пустые идут в конце. Когда вариантов восемь
и больше, сверху есть строка поиска, понимающая и неверную раскладку. Список
управляется стрелками, Enter и Esc и прокручивается внутри боковой панели.
Воронка в поле поиска скрыта, пока курсор не на поле, и остаётся видимой при
включённом фильтре.

Поиск тредов, поиск в архиве по названиям и поиск в списках фильтров находят
название в любом алфавите: «маруся» находит `marusya`, а `finansy` — «Финансы».
Обе стороны приводятся к одному латинскому написанию; одна буква совпадает
только как набрана. Поиск по тексту сообщений выполняет сервер BB, на него это
не распространяется.

Значок перед названием треда задаёт настройка плагина `rowMark`: `project`
(логотип или буквы проекта, как раньше), `topic` (значок темы) или `ask` (по
умолчанию). При `ask` строки показывают значки проектов, а при первой загрузке
списка со значками появляется окно выбора с примерами обоих видов; «Позже»
откладывает вопрос до следующей загрузки страницы или открытия фильтров. Изменить выбор:
`bb plugin config machine-tabs set rowMark <ask|project|topic>`. Заголовки групп
проектов всегда показывают значок проекта.

В режиме Custom стрелка раскрытия субагентов (`›`) прижата к правому краю строки
треда и стоит в одной колонке у всех строк. В штатном списке она идёт сразу за
названием и в широкой боковой панели оказывается посередине. Это одно CSS-правило
в `STYLES` (`app.tsx`): `margin-left: auto` у кнопки раскрытия; при наведении она
остаётся левее кнопок действий строки.
Там же вторая правка для устройств с мышью (`@media (hover: hover)`): штатный
список держит в конце каждой строки пустую ячейку 28 px под кнопки наведения,
из-за чего название обрезалось раньше края, а стрелка стояла левее колонки
индикаторов. Теперь ячейка занимает место только при наведении, фокусе,
открытом меню или когда в ней есть индикатор; при наведении название
укорачивается на ширину кнопок. Режим Classic не затронут.

Восстановление на сервере BB: `bb plugin build plugins/machine-tabs`, затем
`bb plugin reload machine-tabs` для уже установленного плагина либо
`python3 scripts/restore.py --plugins --apply` с приватным снимком.
Выбранный провайдер сохраняется в `.local/config/ui.json`
и применяется `restore.py`. Вручную: `bb settings ui set
sidebar.threadListProvider '"thread-list/thread-list"'` или
`bb settings ui set sidebar.threadListProvider '"machine-tabs/machine-tabs"'`.
Кнопки привязаны к штатному заголовку Navigation; если его разметка изменится,
выбор остаётся доступен в Settings → Appearance → Sidebar и через CLI.

## Индикаторы usage

Для общего обзора расхода подключённых машин используется `Usage` (`usage`),
для статистики тредов и детализации по сообщениям — `Tokenomics` (`tokenomics`),
для лимитов аккаунта треда и общего обзора — собственный `Thread Account Usage`
(`plugins/thread-account-usage/`). Usage и Tokenomics остаются установленными
из каталога `bb-community`, чтобы сохранять штатные обновления.
Usage Tracker также сохранён из каталога, но отключён как дублирующий индикатор.
Исходники сторонних плагинов здесь не копируются.

В Usage Tracker штатная настройка `compactLimit` установлена в `Five-hour`:
`bb plugin config usage-tracker set compactLimit Five-hour`. Она сохраняется
в приватном снимке. Это меняет выбранное окно компактного индикатора и обзора,
но общий процент остаётся средним между аккаунтами; если пятичасового окна нет,
плагин использует доступное недельное. `+N` рядом означает число доступных
сбросов лимитов, а не дополнительные аккаунты. Дополнительные окна, включая
Fable, видны при открытии деталей конкретного аккаунта.

Восстановление: `bb plugin install usage@bb-community --yes`,
`bb plugin install tokenomics@bb-community --yes` и
`bb plugin install usage-tracker@bb-community --yes`, либо общий
`python3 scripts/restore.py --plugins --apply` с приватным снимком.
Прежние `bb--provider-usage`, `limits` и `usage-tracker` отключены штатной командой
`bb plugin disable <id>`, их настройки сохранены. Вернуть индикатор можно
командой `bb plugin enable <id>`. Плагин `ai-usage` не устанавливается.

Usage собирает историю с доступных подключённых машин; первый сбор может
занять время. Tokenomics читает доступные события истории BB и продолжает
учёт новых событий после установки.
Авторизации CLI и нестандартные пути профилей проверяются отдельно на каждой
машине; снимок настроек не содержит авторизации или историю использования.

### Thread Account Usage

В заголовке треда слева от существующего графика Tokenomics: логотип агента,
аккаунт CLI, сервер и единый значок с двумя вложенными кольцами. Рядом указаны
до двух применимых окон и время сброса каждого. Порядок колонок и колец
фиксирован: сначала 5ч, затем неделя, независимо от расхода. Модельные
и прочие окна следуют за общими, отсутствующие окна не подставляются.
График Tokenomics подписан «Тред / 24ч»: он описывает расход этой беседы,
а кольца — общие лимиты аккаунта.
Плагин поддерживает несколько одновременно открытых тредов через SDK split
layout. Кнопки терминала остаются после блока usage. Кружок контекста BB
не меняется.

Внизу сайдбара — два кольца, подписанные средние проценты 5ч и недели,
и ручное обновление. Недельная строка приглушена. `+N` расположен маленькой
меткой у логотипа/нижнего угла значка, без слова «сброс» и фона.
Точка привязана к нижнему значку и означает подтверждённое исчерпание общего
лимита 5ч/недели; число аккаунтов показано в заголовке карточки. Исчерпанная
модель и устаревшие данные в этот счётчик не входят. Тексты увеличены и выровнены.
В заголовке логотип встроен в угол кольца. Аккаунт и машина расположены
друг под другом в отдельной колонке. Справа каждое полученное окно имеет
свою колонку: подпись и процент сверху, `↻` и время до сброса снизу.
Для одного окна остаётся одна колонка, отсутствующие окна не подставляются.
Точная дата и пояснение расхода доступны по наведению. Счётчик `+N`
сохраняет прежние данные и размещение. Группы времени разделены узким
неразрывным пробелом. Навык плагина зарегистрирован из `skills/`.
Кнопка обновления сохраняет размер и вращается при запросе;
данные остаются видимыми. Взаимодействие закрепляет карточку, её состояние не
зависит от перестройки DOM заголовка.
Карточка показывает компактные строки с логотипами, аккаунтами и названиями
машин; горизонтальные полосы 5ч / неделя / Fable имеют подписи, процент и
время сброса справа. Кнопка `›` раскрывает полные данные аккаунта и до шести
последних тредов этого агента на указанных машинах, без утверждения об их
исторической привязке к аккаунту.
Точная дата — по наведению. Переключатели выделяют одно окно; отсутствующее
окно не заменяется другим и не отображается как 0%.

На телефоне (до 767px) отдельный баннер лимитов над вводом убран. Короткая
кнопка с логотипом, кольцами и главным процентом встроена в существующую
горизонтально прокручиваемую нижнюю строку треда (`data-follow-up-composer-footer`).
Нажатие открывает подробности нижней карточкой с учётом клавиатуры и safe-area.
В боковом меню средние 5ч и недели остаются двумя выровненными строками;
исправлено слипание подписей на телефоне. Десктопные стили и размещение
сохранены. При изменении DOM-маркера BB нужно перепроверить размещение. На мобильном экране pointerdown/mousedown по кнопкам нижней строки сохраняет фокус редактора до click, чтобы blur не сворачивал панель раньше открытия меню. Обработчик не останавливает распространение событий и не перехватывает touchmove; десктоп не затрагивается.
`+N` внизу и у аккаунта обозначает известные доступные сбросы. Read-only
host worker читает количество сбросов Codex через существующий CLI,
сопоставляет email и не расходует кредиты. Для Claude количество пока
неизвестно и не заменяется нулём.

Запросы к штатному SDK BB выполняются раз в 2 минуты, по фокусу и вручную,
таймер — каждые 30 секунд. Авторизация и маршрутизация не меняются. Один
логин на нескольких машинах объединяется без суммирования процентов.
Аккаунт треда определяется как текущий вход CLI на его машине с проверкой
метаданных запуска. Это не подтверждение авторизации уже запущенного процесса.
Отдельный профиль/маршрут, включённый пул или отсутствие метаданных дают
явный статус «Аккаунт не подтверждён» вместо чужих лимитов.

Настройка `hideGlobalTokenomics` скрывает верхний левый индикатор Tokenomics
адресным стилем нашего плагина; файлы готового плагина не меняются.
Можно вернуть через `bb plugin config thread-account-usage set
hideGlobalTokenomics false`. После отключения нашего плагина скрытие и
добавленные DOM-элементы удаляются.

Восстановление на сервере BB: `npm ci --prefix plugins/thread-account-usage`,
`bb plugin build plugins/thread-account-usage`, затем
`bb plugin install ./plugins/thread-account-usage --yes` и
`bb plugin disable usage-tracker`. Снимок поддерживает общий restore.
Исходники, зависимости и ограничения DOM-якорей BB описаны в
`plugins/thread-account-usage/README.md`. Проверки: TypeScript и
`node --test plugins/thread-account-usage/logic.test.ts`.
Для отката отключите `thread-account-usage` и включите `usage-tracker`.

### Совместимость Tokenomics 0.2.2

В ответе `usage_limits` неизвестная оценка `sizeTokens` возвращалась как
`undefined`, что текущий BB отклоняет с `non_json_result`. Исправление
`plugins/tokenomics-compat/server.patch` преобразует её в допустимый по схеме
`null`. Плагин остаётся установленным из каталога; исправляется только его
серверный ответ, интерфейс и учёт токенов не меняются.

На машине сервера BB выполните `python3 scripts/apply_tokenomics_compat.py`
для проверки и `python3 scripts/apply_tokenomics_compat.py --apply` для
применения, сборки и перезагрузки через CLI. Скрипт проверяет версию и
контрольные суммы исходника, не читает базы и не меняет авторизации.
Обновление из каталога заменяет исправленные файлы, поэтому исправление
восстанавливает хранитель плагинов (`voice-mode-keeper`, `patch_keeper.py`):
после обновления он накладывает `server.patch` на копию с допуском на сдвиги
(`patch --fuzz=2`), собирает её и только тогда ставит и перезагружает плагин;
если автор уже выпустил исправление, патч больше не применяется. Исправление
отправлено автору: danielbachhuber/bb-plugins#100. Скрипт ниже остаётся для
ручной проверки и при неизвестной версии останавливается.
Проверка результата: `bb plugin rpc call tokenomics usage_limits --json`
должна завершиться без ошибки JSON; статистика тредов доступна через
`bb tokenomics threads --limit 3 --json`.

## Установка

План показывает `python3 scripts/restore.py --plugins`. Для применения запустите
его с `--apply` на машине сервера BB. Локальные плагины устанавливаются из
`plugins/<id>/`; сторонние — из сохранённых источников каталога.

`restore.py` читает `config/` и `.local/config/`. Локальные значения заменяют
одноимённые публичные ключи; вложенные словари и списки заменяются целиком.
Личные файлы плагинов обнаруживаются даже при отсутствии публичного файла.
Новый checkout без `.local/` получает только общие настройки.

Публичный `config/plugins.json` повторяет установленный набор целиком: те же
плагины, источники и состояния. Публичные файлы настроек содержат все значения,
кроме личных: адресов, идентификаторов машин, прокси, путей, параметров бэкапа и
личных инструкций. Они остаются только в `.local/config/`.

`restore.py` можно запускать повторно: уже установленные плагины из каталога он
не переустанавливает (они обновляются сами), свои пересобирает и перезагружает.
Встроенные плагины, которых нет в новом BB (например, `browser-automation`), он
сначала устанавливает, затем включает. Сохранённую настройку, которую текущая
версия BB уже не принимает, он пропускает с предупреждением и печатает их список
в конце; ошибки установки плагинов прерывают восстановление.

Проверка на чистом BB: отдельный экземпляр BB 0.49 со своей папкой данных и
портами, свежий клон без `.local/`, окружение без переменных текущего треда.
Восстановление ставит все плагины в тех же состояниях; ручной настройки требует
только `codex-realtime` (нет входа в Codex). Важно для такой проверки: процесс
тестового BB не должен наследовать `BB_SERVER_URL` основного, иначе плагины,
вызывающие CLI, обращаются к основному серверу.

## Сохранение

После изменения BB проверьте источник через `bb plugin list --json`, затем:

```sh
python3 scripts/snapshot.py --settings-only
python3 scripts/snapshot.py --check
python3 scripts/privacy_check.py
```

Снимок содержит список плагинов и настройки без секретных полей схемы.
Он сохраняется только в `.local/config/`. Полный режим без `--settings-only`
копирует исходники установленных локальных плагинов, поэтому требует чистого
каталога `plugins/` и отдельной проверки кода на личные значения.
Публичные настройки редактируются вручную после обезличивания.

`setup_tracking.py --apply` добавляет общее напоминание и включает Git-хук.
Хук проверяет актуальность приватного снимка и содержимое Git index.
Проверка истории перед публикацией: `python3 scripts/privacy_check.py --history`.
Коммиты, push и открытие доступа выполняются по отдельному поручению.

## Ручные шаги

Пароли и авторизации вводятся отдельно. Сетевой доступ Connect, маршруты прокси,
ACP-агенты и чувствительные состояния сетевых плагинов автоматически не меняются.
Идентификаторы машин после новой установки сопоставляются заново.
Сложные горячие клавиши, пользовательский CSS, выбранные вкладки и лимиты машин
проверяются вручную. Маршруты и аккаунты Claude не меняются при сборе снимка.

При установке Web BB Button задайте «Публичный адрес BB» (`webUrl`) в штатных
настройках плагина. Если на сервере уже задан `BB_APP_URL`, он может использоваться
при пустой настройке. Без корректного адреса плагин показывает статус «Требуется
настройка» и инструкцию; сохранение настроек повторяет его загрузку.
Переходов на главную по умолчанию нет. Личный URL хранится в BB и приватном
снимке `.local/config/plugins/web-bb-button.json`. Серверное перенаправление
`/api/v1/plugins/web-bb-button/http/open` открывает сохранённый адрес.
После правки плагина выполните `bb plugin build <путь>` и `bb plugin reload <id>`.

Личные адреса доставки бэкапа задаются в `.local/config/backup-delivery.json`:

```json
{
  "destinationHost": "host_example",
  "destinationDir": "/path/to/private/backups",
  "compatHost": "host_example"
}
```

`server_backup.py` также принимает `--destination-host`, `--destination-dir`,
`--recipient`. `apply_inbox_compat.py` принимает `--host` и без `--apply` только
проверяет известные контрольные суммы. При изменении upstream требуется новый
просмотр совместимости. Скрипты не читают и не меняют базу BB напрямую.

## Публикация изменений

Проверяйте diff и запускайте `scripts/privacy_check.py` для текущих файлов и с
`--history` для истории. Личные документы и конфигурацию храните в `.local/`.
При очистке уже существовавшей истории сохраните приватный Git bundle и свои
незакоммиченные файлы. Старые checkout нельзя сливать обратно в очищенную историю:
клонируйте репозиторий заново, затем перенесите собственные незавершённые правки.

Данные в `.local/` отсутствуют в GitHub. Шифрованное резервное копирование и
восстановление описаны в [server-backups.md](server-backups.md).

## Project Open

`plugins/project-open/` добавляет иконки папки и терминала в строках тредов и в
заголовке треда, без замены списка и меню BB. В заголовке они видны постоянно;
в боковом меню появляются при наведении/фокусе только на десктопе. На
сенсорных устройствах дополнительные кнопки в строках вообще не монтируются,
поэтому скрытые элементы не перехватывают нажатия на тред. В строках бокового меню кнопки накладываются на правый
край строки; место под их измеренную ширину выделяется только при наведении,
видимом клавиатурном фокусе или открытом штатном меню. Кнопки стоят в штатном
ряду действий с одинаковым шагом 20 px; в заголовке треда ширина сохраняется, чтобы
штатные кнопки не сдвигались.
Обе кнопки показывают тёмный тултип с задержкой 100 мс: действие, имя машины
и полный путь окружения. Машина и путь показаны отдельными строками с
иконками ноутбука и папки. Данные сразу берутся из живого списка BB и уточняются
через SDK треда, окружения и машины при открытии подсказки.
В строках с дочерним тредом из другого проекта сохраняется штатный значок
перехода в проект. Стрелка раскрытия и значок проекта остаются в обычной
раскладке перед кнопками, а название сокращается до их границы. Отдельный
translateX убран: он накладывал стрелку на название. После клика мышью и ухода
курсора обычный focus-within больше не удерживает пустой отступ. ResizeObserver
пересчитывает ширину при изменении кнопок; при выгрузке наблюдатель удаляется.
На сенсорном экране сохраняется штатное положение стрелки и значка проекта,
а область нажатия стрелки расширена до 36×36 px.
Новые иконки стоят перед штатным Open. Терминал запускается штатным
New tab → Start terminal в нужной папке и на нужной машине.

С версии 0.3.0 место кнопок выбирается настройкой плагина `placement`. Значение
`row` (по умолчанию) оставляет описанные кнопки в строке треда. Значение `menu`
убирает их из строк и добавляет команды папки и терминала в штатное меню **…**
треда; оттуда их можно вернуть в строку через **Customize actions** (ключи
`project-open/open-folder` и `project-open/open-terminal`, штатный параметр BB
`rowActions`, не более трёх кнопок). Переключение:
`bb plugin config project-open set placement menu` либо страница настроек
плагина. Кнопки в заголовке открытого треда есть в обоих режимах.

На macOS папка открывается напрямую в Finder через локальный обработчик
`BB Project Folder.app`. Он использует уже установленный rclone и существующий
SSH-профиль; удалённый корень подключается нативным WebDAV-диском через loopback.
NFS и Cyberduck в рабочем сценарии не используются. Локальная папка открывается
без сетевого подключения. Каждый заголовок получает ID своего треда из
контекста композера, включая split-панели. В боковом меню используется ID
конкретного треда; машина и путь берутся из его окружения при нажатии, включая
worktree. У групп проектов кнопок нет: треды проекта могут быть на разных
машинах. Зависимость от маркеров Machine Tabs для выбора папки убрана.

Восстановление BB-плагина: `python3 scripts/restore.py --plugins --apply`.
Для установки клиентского обработчика скопировать каталог `macos/` из
плагина на Mac и выполнить `python3 macos/install.py --config <private-config>`.
Личный конфиг содержит только путь rclone, ID машин, допустимые корни и имена
существующих SSH-профилей. Ключи и авторизации не копируются. После проверки
включить `finderHelper` в настройках Project Open. Разрешение application-link
схемы выдаётся штатным интерфейсом BB на клиенте. Обработчик специфичен для
macOS. На iPhone/iPad/Android кнопка в заголовке открывает штатный поиск
файлов BB в контексте треда через New tab; Mac-ссылка на телефоне не вызывается.
На других десктопных ОС остаётся штатный Open BB.

Исходники и подробности — `plugins/project-open/README.md`. Проверки:
`npm test`, `npm run typecheck` и
`python3 -m unittest discover -s macos -p 'test_*.py'` в каталоге плагина.
Системный обработчик должен пройти реальное открытие локальной и удалённой
папок в Finder, повторное нажатие и переподключение диска; одного открытия
меню или успешного mount/stat недостаточно. Личные значения восстановления
хранятся в `.local/docs/folder-helper-mac.json` и `.local/docs/project-open.md`.
Журналы, статусы запросов и файловый кэш в Git и снимок настроек не включаются.

## Автоматизации и наблюдение за очередями

Исходники проверок сохранены в `scripts/thread_watchdog.py` и
`scripts/thread_queue_monitor.py`; резервное копирование — в
`scripts/daily_backup.py` и `scripts/server_backup.py`. Установленные автоматизации
содержат отдельные копии входных скриптов. Бэкап использует модули из checkout,
указанного в `BB_CONFIG_ROOT`; обновление входного `daily_backup.py` требует
повторного копирования в автоматизацию.

`scripts/automation_config.py --snapshot --project <project-id>` сохраняет
известные расписания этих скриптов в игнорируемый файл
`.local/config/automations.json`. Флаг `--project` можно повторять. В снимок
входят включённость, cron, часовой пояс, таймаут, рабочий каталог и только
разрешённые переменные окружения. Переписки, ключи, базы, содержимое бэкапов,
история запусков и наблюдений не сохраняются в репозитории. Приватный манифест
включается в зашифрованный архив `.local/config/`, описанный в
[server-backups.md](server-backups.md).

Восстановление: сначала `python3 scripts/automation_config.py` показывает
план без изменений; `python3 scripts/automation_config.py --apply` обновляет
существующие расписания или создаёт отсутствующие из исходников checkout.
Одна автоматизация бэкапа проверяет работу каждые 30 минут: личные настройки
и текущие исходники bb-config сохраняются ежедневно после 05:00 МСК (7 копий),
включая незакоммиченные доработки без автоматического commit/push. Полный штатный экспорт BB —
раз в 7 дней (3 копии). Уже созданные копии доставляются повторно без нового
экспорта. Создание полного архива и доставка разделены между запусками, чтобы
каждый укладывался в общий лимит 900 секунд. Проверка архива идёт за один
последовательный проход; доставка — блоками по 4 МиБ с проверкой SHA-256.
В каталоге назначения также сохраняется `restore-tools/` с инструкцией и
модулями восстановления. Команда `backup_keys.py decrypt` поддерживает оба
формата и использует ключ из macOS Keychain без его экспорта. Выполнена реальная
проверка восстановления обеих копий на принимающей машине, включая штатный
импорт полного BB во временный каталог с последующим удалением тестовых данных.
HTTP-ожидание экспорта продлено до 780 секунд только в дочернем CLI через
стандартный Undici dispatcher из поставки BB. BB, его база и маршрутизация
не изменяются. Адрес доставки передаётся в переменных
`BB_BACKUP_DESTINATION_HOST` и `BB_BACKUP_DESTINATION_DIR`, получатель шифрования —
в `BB_BACKUP_RECIPIENT`; они поддерживаются приватным снимком и восстановлением
автоматизаций; `BB_CONFIG_ROOT` указывает checkout с исходниками. При восстановлении
`automation_config.py --apply` привязывает бэкап к текущему checkout автоматически.
Состояние монитора и watchdog вынесено за пределы экспортируемого
каталога BB в `~/.local/state/bb-automations/`, чтобы запись JSON во время
экспорта не нарушала контрольные суммы. Исходные файлы состояния оставлены
на месте без дальнейших записей. Конкретные пути и расписания сохранены только
в `.local/config/automations.json`. После восстановления создайте каталоги
состояния с доступом только владельцу; отсутствующее состояние наблюдатели
создадут заново. Для обновления работающего бэкапа используйте
`bb automation update <automation-id> --project <project-id> --script-file scripts/daily_backup.py`;
существующие переменные, расписание и таймаут при этом сохраняются.
Проверка: `python3 -m unittest discover -s scripts -p 'test_*backup*.py'` и
реальный запуск бэкапа с проверкой доставки; подробности в
[server-backups.md](server-backups.md).
Перед применением на новой установке сопоставьте project/thread ID, пути
и параметры доставки в приватном манифесте. Для другого хоста скрипты должны
быть доступны на хосте вызывающего CLI. Повторное применение сопоставляет
задания по ID, затем по точному имени. Неоднозначные имена останавливают импорт.

Проверки запускаются раз в минуту и не требуют модели. Общий монитор только
наблюдает очередь всех доступных проектов и посылает штатное BB-уведомление:
`turn-starting` дольше 5 минут, `thread-busy` дольше 15 минут либо исчерпанные
попытки доставки. Долгое ожидание не объявляется доказанным зависанием.
Запланированные сообщения, вопросы, ожидание плагинов и недоступные машины
не считаются таким сбоем. Уведомления ограничены одним на тред за 30 минут.
Обезличенные технические наблюдения (ID, время, статус, причина очереди)
хранятся только в служебной директории, с ротацией двух файлов до примерно
2 МБ каждый; состояния удаляются через 7 дней без наблюдений.

Отдельная защита одного выбранного треда повторяет доставку уже сохранённого
сообщения и возобновляет только явно диагностированный сбой запуска
`provider_turn_start_deadline` / `provider_turn_start_timeout`. Она не
останавливает работающий ход, не очищает контекст, не отвечает на вопросы,
не подтверждает разрешения и не возобновляет ручную остановку. Не более трёх
попыток до нового сообщения пользователя, с интервалом не менее 3 минут.
Новый запрос автоматически возвращает наблюдение без ручного включения.
Состояния и счётчики не содержат текста сообщений. Если проблема —
рассинхронизация BB при продолжающейся работе провайдера, принудительного
перезапуска нет: собираем данные для исправления причины.

## Дополнительная Linux-машина и прямой маршрут Codex

Машина подключается к существующему BB исходящим соединением через Connect;
SSH-переход используется только для установки и обслуживания и не определяет
исходящий маршрут Codex. Установить поддерживаемый Node.js, зарегистрировать
машину через штатный manual installer и проверить автозапуск systemd.
Приватные команды регистрации, токены и файлы авторизации не сохранять.

Для прямого выхода Codex выполнить `bb proxy-manager prepare <machine> direct`,
`bb proxy-manager apply <machine> direct`, затем `bb proxy-manager check <machine> direct`.
Проверка без токена подтверждает сеть; вход в аккаунт выполняется отдельно на
целевой машине. Маршруты и идентификаторы сохранены только в приватном снимке.
На VPS с небольшим объёмом RAM проверить swap перед установкой CLI и запуском агентов.

## Имена фоновых служб macOS

`scripts/macos_named_services.py` оформляет описательные запускатели для
существующих LaunchAgents BB/McpGo в Login Items. Для каждого задания
используется понятное имя функции: Mac Connection, Terminal, Quick Commands,
Browser, Browser Proxy, Tunnel, Messages, Auto-send, Dashboard.
Это маленькие нативные программы из `scripts/macos_service_launcher.c`,
которые выполняют исходный Node с теми же аргументами и окружением.
Сам Node, реализации служб и разрешения Privacy не заменяются.

План: `python3 scripts/macos_named_services.py`. Применение на Mac:
`python3 scripts/macos_named_services.py --apply`. Скрипт сначала собирает
и проверяет все запускатели, затем меняет только исполняемый путь и
ассоциацию приложения в существующих пользовательских LaunchAgents.
По умолчанию службы не перезапускаются; отдельный `--restart` применяется
только по необходимости. Неактивные задания остаются неактивными.

Состояние отката хранится на Mac в
`~/Library/Application Support/BB Named Services/state.json`: только исходные
пути и ассоциации, без аргументов служб, окружения и авторизаций. Откат:
`python3 scripts/macos_named_services.py --rollback --apply`.
Копия состояния и личные детали — `.local/docs/mac-login-items-state.json`.
После обновления менеджера служб, если он пересоздаст LaunchAgents, повторить
план/применение: запускатель будет использовать актуальный оригинальный Node.
Не применять resetbtm, не править базу TCC и не переносить разрешения для
косметического изменения Login Items. Подпись локальная; Developer ID
производителя эти личные запускатели не присваивают.

## Компактный экран подключений

В `proxy-manager` сохранено компактное дерево «машина → установленные агенты».
Каждая машина оформлена отдельным блоком с выделенным заголовком;
строки агентов имеют общий контур для названия, настройки и статуса и
соединены с машиной ветками. Ветки раскрыты по умолчанию и сворачиваются
нажатием на заголовок; показаны число агентов и связь машины. Неустановленные CLI скрываются по
признаку установки, а установленный, но недоступный агент остаётся видимым
с пояснением. Выбор прокси находится в строке Codex; у остальных агентов
отображается «Прокси не управляется»: плагин пока не меняет их маршрут.
Уменьшены отступы; шапка с кнопкой «Назад»
остаётся видимой при прокрутке.
Открытие из индикатора и возврат в тред выполняются штатной навигацией
SDK BB без перезагрузки документа. Адрес исходного экрана и машина
сохраняются в памяти вкладки; обычная ссылка остаётся для открытия
в новой вкладке. Старые ссылки с `returnTo` также возвращают в тред через SDK.
При открытии без исходного адреса используется история браузера,
а в новой вкладке — штатный экран создания треда.

Работает в веб-интерфейсе установленного плагина. Восстановление:
`bb plugin build plugins/proxy-manager`, затем установка локального пути
`bb plugin install ./plugins/proxy-manager` или `bb plugin reload proxy-manager`,
если этот путь уже установлен. Исходники: `app.tsx` и `proxy-ui.css`.

Данные экрана подключений сохраняются в памяти вкладки и сразу отображаются
при повторном открытии; актуальные машины, привязки и статусы загружаются
в фоне. Обнаружение CLI кэшируется на сервере на 60 секунд, одновременные
проверки одной машины объединяются. Кнопка обновления обходит кэш; перед
сменой маршрута наличие CLI проверяется принудительно. Кэш не записывается
в настройки и не требует отдельного шага восстановления.

## Группы по пять и поиск тредов

В Machine Tabs каждый список начинает с пяти элементов. Компактные текстовые
кнопки со стрелками «Показать ещё» (+5) и «Свернуть» (до 5) расположены
в одной строке со счётчиком и проявляются при наведении на блок или фокусе
внутри него. На сенсорном экране кнопки видны постоянно. Это относится
к Last 5, проектам, машинам, дням и вложенным спискам: ограничивается вход
штатного виртуализатора, поэтому скрытые строки не остаются целями навигации.
Раскрытие хранится в состоянии компонента до его размонтирования.
Счётчик пагинации не переносится и не сжимается; на сенсорных экранах
промежутки уменьшены, чтобы обе кнопки и `10 / 14` помещались в строку.
Last 5 сохраняет связи родитель/потомок и передаёт дочерние треды штатному
списку BB, поэтому стандартные стрелки, вложенность и индикаторы работают
и в этом блоке. Сброс parentThreadId и фильтр только корневых тредов убраны.

Поле «Поиск тредов» проверяет названия всех активных тредов, включая
не раскрытые строки и группы, а также названия проектов, машин и дней.
All ищет по всем машинам; конкретная вкладка ограничивает результаты своей
машиной. Кнопка настроек появляется при наведении/фокусе; переключатели
«Включая архив» и «По тексту сообщений» выключены по умолчанию и действуют
до перезагрузки страницы. Нового постоянного вида настройки нет.
Названия активных тредов проверяются сразу. Архивные названия загружаются
страницами по 100 в фоне, кэшируются на минуту в памяти вкладки; поиск
по сообщениям использует штатный индекс BB. Задержка 250 мс и отмена
предыдущего запроса предотвращают запрос на каждое нажатие клавиши и
появление устаревших результатов. Дополнительные совпадения показываются
отдельным компактным блоком, также по пять.

Ограничение штатного API: поиск по сообщениям возвращает максимум 50
тредов на категорию (активные/архивные), затем применяется выбранная машина.
При превышении лимита интерфейс предлагает уточнить запрос. Архивный поиск
по названиям проходит все страницы метаданных и этим лимитом не ограничен.
Тексты сообщений, запросы и результаты на диск не записываются.

Восстановление: `bb plugin build plugins/machine-tabs`, затем
`bb plugin install ./plugins/machine-tabs`; если путь уже установлен —
`bb plugin reload machine-tabs`. Исходники дополнения: `app.tsx`,
`lib/group-paging.tsx` и `lib/thread-search.tsx`. После обновления BB проверить
пагинацию: адаптер использует семантические props штатного JSX-рендерера
(`itemKeys`, `renderItem`, навигационные функции) и отдельный вход pinned;
минифицированные имена функций и исходник штатного плагина не меняются.

## HOME у системной службы BB

Если системная служба BB запущена без `User=`, systemd может не задать `HOME`.
Его отсутствие наследуют терминалы и агенты; CLI могут ошибочно искать
учётные данные относительно рабочего каталога. Авторизация хранится только
в штатном пользовательском хранилище, не в checkout проекта.

`scripts/bb_service_home.py <bb-unit.service>` проверяет пользователя службы
и его домашний каталог. `--apply` устанавливает отдельный systemd drop-in
`90-bb-home.conf` с правильным `HOME` и выполняет `daemon-reload`, не перезапуская
службу. После перезапуска `--verify` проверяет окружение работающего демона.
Для восстановления выполнить тот же скрипт с `--apply` от администратора.
Перед прерыванием работы включить штатное продолжение тредов после рестарта:
`bb settings experiment resumeThreadsAfterRestart true`. Эта настройка входит
в приватный снимок; ранее остановленные пользователем и ожидающие разрешения
треды автоматический механизм не возобновляет.

## Прокси в нижней строке поля ввода

Индикатор прокси перенесён из баннера над полем ввода в нижнюю строку:
проект → ветка → машина → прокси → новая сессия. Индикатор целиком открывает
экран подключений через SDK-навигацию. Штатные элементы строки и их действия
сохранены; `composer-footer.ts` добавляет только контейнер для React portal
и атрибуты порядка через content script, убирая их при выгрузке. Каждая
форма ввода привязана к своему контейнеру. Нижняя строка не переносится,
поскольку штатный контейнер BB имеет фиксированную высоту. На телефоне
«Пуш» находится возле строки изменений (если её нет — возле ветки), поэтому
внизу помещаются ветка, прокси с текстом и штатные режим/контекст. Подписи
сохранены, область нажатия имеет высоту 44 px. Pointerdown на наших кнопках
сохраняет фокус композера до обработки клика: поле не сворачивается раньше
перехода в настройки прокси.
Если структура строки в новой версии BB не распознана, индикатор остаётся
среди действий поля ввода. SDK-декларации обновлены до версии работающего BB.

## Кнопка «Пуш»

`plugins/push-button/` добавляет кнопку рядом с веткой внизу существующего
треда. Нажатие отправляет обычное сообщение `пуш` через SDK BB в этот тред.
Если агент занят, используется штатная очередь (`queue-if-active`). Кнопка
не запускает Git и не меняет черновик, модель или разрешения. Проверку, коммит
и отправку выполняет агент по полученному поручению. Есть защита от повторного
нажатия во время отправки; после ошибки можно повторить.
Кнопка приглушена и отключена, если нет изменений/неотправленных коммитов,
либо статус ещё загружается или машина недоступна. Read-only host entry читает
Git в окружении треда: изменения, ahead относительно фактической tracking-ветки
и первую публикацию локальной ветки. Обновление раз в 5 секунд, только пока
интерфейс подписан на статус; fetch не выполняется.

Плагин отдельный, не заменяет штатные элементы ветки и изменений. Для
восстановления: `python3 scripts/restore.py --plugins --apply`; при ручной
установке — npm ci, bb plugin build и установка из каталога плагина.
Проверки: `npm run typecheck`, `npm test` в каталоге плагина.

На телефоне над композером также показано имя машины с иконкой. Оно
получено из окружения именно этого треда через SDK, включая состояние
недоступного Git, а не из выбранной вкладки машин.

## Menubar Status: статусы агентов в строке меню macOS

Плагин `menubar-status` (`plugins/menubar-status`, только серверная часть) собирает
короткую сводку по тредам: сколько ждут ответа, сколько работают, есть ли новые
ответы и ошибки, плюс последние агенты с проектом, машиной, одной строкой
последнего ответа и текущим шагом работающего агента («Команда: npm test»,
«Читает feed.ts», «Думает»). Сводку он записывает штатным `bb.sdk.files` в
`status.json` на выбранной машине: при событиях тредов (с задержкой около
секунды), раз в 4 секунды, пока кто-то работает, и не реже раза в минуту.
Субагенты показываются через свой главный тред: если работает или ждёт вас
субагент, так же помечается и главный тред («Субагент: …»); ошибка или новый
ответ субагента статус главного треда не меняют. Зачем: значок bb в Dock
показывает только число или точку, а всплывающее окно при наведении на значок
Dock в macOS сделать нельзя.

На Mac работает нативное приложение `bb Status.app` (`macos/BBStatus.swift`,
собирается установщиком через `swiftc`, LaunchAgent `dev.bb.status`). В строке
меню оно показывает `bb`, значки состояний с числами (вращающийся — пока агенты
работают) и компактный блок usage, выбранный по макетам (вариант «группы по
агентам», значок в строке подписей): на каждого агента крошечный значок
(Claude — звёздочка, Codex — шестигранник) в нижней строке, на каждый аккаунт
пара полосок — толстая = 5-часовой лимит, тонкая = неделя (у Codex только
неделя); обе показывают израсходованное и заполняются снизу вверх от 0 до
100 %, как полосы в панели и кольца в bb (пустая — лимит свежий, полная —
исчерпан), под ними буквы машин, где работает аккаунт
(первые буквы имён машин, например S — server, L — laptop; у Codex — все машины,
где выполнен вход), после
них зелёное «+1», если у аккаунта есть доступные сбросы лимита. Агентов
разделяет тонкая черта. Лимиты отдельных моделей (например, недельный «Fable»)
в полоски не попадают, как и в Thread Account Usage. В конце — время сброса:
берётся самый израсходованный 5-часовой лимит; если у этого аккаунта
кончилась и неделя (сброс 5 часов не поможет), — время сброса недели; без
5-часовых окон — самая израсходованная неделя. Обычно время приглушённое; от
90 % расхода оно белым на оранжевой плашке, при 100 % — на красной (красный и
оранжевый текст на синей строке меню читаются плохо). Полоска от 90 % залита
оранжевым, полная — светло-красным. Значки и полоски читаются только из локальных файлов.
Заголовок перерисовывается только при изменении данных, а вращение — анимация
Core Animation на отдельном слое, без перерисовки: в покое приложение не тратит
процессор. Макеты вариантов рисовал Codex (тред «Макеты usage для строки меню»).

При наведении на значок открывается панель (840×660), при уходе курсора она
закрывается; клик по значку закрепляет её, Esc или клик мимо закрывают.
Правый клик — меню («Открыть bb», «Обновить панель», «Скрыть до перезапуска»).
Закрепляет панель только настоящий клик или ввод с клавиатуры внутри неё: фокус
поля ответа, который возвращается при повторном показе, её не держит.
В панели:

- в шапке, в одну строку справа от заголовка, usage всех аккаунтов в стиле
  нижнего блока bb: значок агента (с «+1», если есть доступные сбросы лимита),
  машина и плашка тарифа («Pro $20»), рядом строки «5ч ▬ 80 % ↻1ч 57м» и
  «Нед ▬ 13 % ↻6ч 47м»; лимиты отдельных моделей не показываются, точные
  данные — в подсказке. Цена тарифа — статичная таблица в `panel.html`
  (`planPrice`: Claude Pro $20, Max 5x $100, Max 20x $200; ChatGPT Plus $20,
  Pro $200, Free $0); при смене прайса её нужно поправить;
- слева статус и разделы «Ждут вас», «Ошибки», «Работают» (с текущим шагом),
  «Только что закончили» (новые ответы и законченные за 3 часа), «Ранее»;
- справа всегда видна колонка чата, поэтому панель не меняет размер. Наведение
  на тред (с паузой 0,18 с) показывает его переписку: сообщения пользователя,
  других тредов и ответы агента, без шагов инструментов. Внизу поле ответа:
  Enter отправляет (как в bb: `mode: "auto"` — уточнение живого хода или новый
  ход), Shift+Enter — перенос. Пока в поле есть текст, наведение чат не
  переключает. Если агент или его субагент ждёт разрешения или ответа на вопрос,
  показана кнопка «Открыть в bb», которая открывает именно ждущий тред: такие
  решения принимаются в самом bb. Работающий субагент показан строкой
  «Субагент: …» под перепиской;
- клик по треду открывает его в приложении bb (`bb thread open`).

Mac ничего не запрашивает у bb: всё нужное плагин сам пишет в папку
`~/Library/Application Support/bb-menubar` на машине `hostId` и забирает оттуда
ответы.

- `status.json` — список и статусы.
- `chats/<тред>.json` — переписка каждого треда из списка. Файл обновляется при
  изменении треда, а ушедшие из списка удаляются. Панель читает все файлы
  заранее, поэтому наведение переключает чат мгновенно.
- `usage.json` — лимиты аккаунтов, раз в 2 минуты. Источник — RPC `accounts`
  плагина Thread Account Usage (`bb.sdk.plugins.callRpc`), чтобы цифры совпадали
  с индикаторами bb, вместе с тарифом и числом доступных сбросов лимита Codex;
  если плагина нет, — `bb.sdk.system.usageLimits` каждой машины. Аккаунт,
  вошедший на нескольких машинах, — одна запись; e-mail не записывается.
- `outbox/*.json` — ответы и «открыть в bb» из панели. Плагин проверяет папку
  каждые 1,5 секунды, сначала удаляет запрос (чтобы он не выполнился дважды),
  потом отправляет (`threads.send`, `mode: "auto"`) или открывает тред
  (`threads.open`). Ошибка пишется в `errors.json`. Если ответ не появился в
  переписке за 15 секунд, панель показывает «Не доставлено» с причиной.

Локальный помощник `macos/server.py` (LaunchAgent `dev.bb.menubar`,
127.0.0.1:47615, каждый запрос с токеном из `token`) только читает эти файлы и
кладёт запросы в `outbox`; учётных данных у него нет. Раньше он ходил в bb
через CLI этого Mac, но CLI вне терминалов bb получает `HTTP 401`, а
16.11.2026 — и в терминалах тоже (сломалась авторизация прокси демона на Mac).
Каждое наведение к тому же стоило запроса около 0,6 с. Файловый обмен не
зависит ни от того, ни от другого. Без машины `hostId` в сети панель
показывает последние данные с пометкой «нет связи».

Настройки плагина (`bb plugin config menubar-status set <ключ> <значение>`):
`hostId` — машина с виджетом, `filePath` — абсолютный путь `status.json` на ней
(по умолчанию для установщика —
`~/Library/Application Support/bb-menubar/status.json`), `webUrl` — публичный адрес
BB для ссылок, `maxItems` — число строк (по умолчанию 12). Значения личные: они
хранятся в BB и в приватном снимке `.local/config/plugins/menubar-status.json`.
Без `hostId` и `filePath` плагин показывает статус «Требуется настройка».

Восстановление: `python3 scripts/restore.py --plugins --apply`, затем задать
настройки. Ручной шаг на Mac (нужны Command Line Tools: `xcode-select --install`):
`zsh install.sh` из `plugins/menubar-status/macos`. Установщик собирает
приложение и ставит два LaunchAgent (`dev.bb.status` — приложение,
`dev.bb.menubar` — помощник); скрипт прежней версии на SwiftBar
(`bb-agents.5s.py`) он убирает.
SwiftBar после этого не нужен.

Проверки: `bb menubar-status show` печатает сводку, `bb menubar-status sync`
записывает файл сразу; `node --experimental-strip-types --test feed.test.ts` в
каталоге плагина (11 тестов: порядок, субагенты, текущий шаг, разбор чата,
заголовки без названия — берётся запасной заголовок bb, иначе «Без названия»).
Живая проверка на тестовых тредах: главный тред без работы с работающим
субагентом показан «работает» с шагом субагента и становится «новый ответ»,
когда тот закончил; субагент, ждущий разрешения, делает главный тред «ждёт вас»;
ответ, отправленный через помощник на Mac, дошёл до агента и его ответ появился в
чате; запросы с чужим токеном (403) и неверным id треда (400) отклоняются. Для
теста долгой команды в Claude Code нельзя использовать `sleep` на переднем плане —
агент уводит её в фон и ход заканчивается.
Панель проверена в браузере на подставных данных: ожидание решения, ошибка
отправки (текст остаётся в поле), пустой чат, нет связи, нет usage. На Mac:
`launchctl print gui/$(id -u)/dev.bb.status` и `…/dev.bb.menubar`, содержимое
папки `chats/` и `usage.json`. Живая проверка файлового обмена: ответ из панели
ставится в очередь за 13 мс, плагин забирает его за 2–3 секунды, ответ агента
появляется в переписке; ошибка (несуществующий тред) приходит в `errors.json`.

В machine-tabs подсказка при наведении на значок проекта в строке треда теперь
содержит и машину («проект · машина»): машину видно при любой группировке без
новых элементов в строке.

## Voice Mode: разговор с агентом через подписку

Из каталога BB установлены сторонние плагины `voice-mode` (Voice Mode) и
`codex-realtime` (ChatGPT Realtime Connection). Они остаются управляемыми
Git-установками для получения обновлений; локальные копии исходников не нужны.
Voice Mode работает с агентом текущего треда, включая Codex и Claude Code.
Микрофон и воспроизведение работают в клиенте BB, соединение с OpenAI — на
машине сервера BB. Мобильное устройство требует отдельной проверки микрофона,
воспроизведения и перебиваний при открытом экране.

Настройка `connection=plugin` запрещает переход на платный API-ключ при ошибке.
API-ключ не задан. Голос — `shimmer`, текст передаётся дословно
(`messageText=verbatim`), `prefixMessages=true` помечает голосовые сообщения.
Начало разговора: открыть тред с пустым полем ввода и свободным агентом,
нажать волну вместо кнопки отправки либо выполнить команду «Start or end voice
chat» (по умолчанию Ctrl+Shift+V). При первом включении разрешить микрофон;
попросить отвечать по-русски. Mute отключает микрофон, × завершает разговор.
Подтверждения опасных действий и разрешения агента остаются в интерфейсе BB.

`codex-realtime` читает существующий вход Codex на сервере и передаёт токен
только разрешённому плагину `voice-mode`. Это недокументированный способ
доступа к Realtime через подписку: он расходует её лимиты, может перестать
работать и не является бесплатным безлимитным API. Во время разговора OpenAI
получает аудио и часть контекста треда. Отдельный речевой движок TTS не
устанавливается: речь создаёт OpenAI Realtime. Авторизация не входит в снимок.

Восстановление: `python3 scripts/restore.py --plugins --apply` устанавливает
плагины и применяет несекретные настройки из приватного снимка. На машине
сервера должен отдельно существовать действующий вход Codex через ChatGPT;
не копировать `auth.json` в репозиторий. При истёкшем входе пользоваться
штатным Codex, не обновлять токен средствами второго плагина.
После восстановления проверить `bb plugin list --json`,
`bb plugin config voice-mode` и запуск на нужном устройстве. До нажатия
кнопки начала разговора микрофон не захватывается.

Серверная проверка: штатный `codex-realtime/scripts/live-check.ts` с короткой
синтетической русской фразой подтвердил подключение по подписке,
распознавание и получение русскоязычного голосового ответа без ошибок.
Тест не проверяет микрофон клиента, перебивания, отправку реальной задачи
агенту или мобильное воспроизведение: их нужно проверить в живом разговоре.

### Правки диалога и мобильного микрофона

Для Voice Mode 0.1.15 сохранён воспроизводимый патч в `plugins/voice-mode/`.
Установка остаётся из каталога; это не отдельный форк плагина. После готовности
микрофона каждый новый сеанс произносит случайное короткое приветствие из
30 спокойных и шуточных вариантов. Предыдущая фраза исключается, пока плагин
загружен; перезагрузка сбрасывает память предыдущего выбора. Ответы
настроены на русский язык и первое лицо, без упоминания отдельного агента.
Приветствие не вызывает инструменты и не читает контекст проекта.

Исправлено скрытие обычного микрофона на телефоне: штатная кнопка записи
может находиться внутри группы отправки, которую исходный плагин скрывал
целиком. До и после голосового сеанса она остаётся доступна рядом с Voice Mode.
Во время сеанса микрофоном управляет голосовая панель; для обычного сообщения
сначала завершить разговор.

Для снижения ложных перебиваний убрана локальная остановка по одной громкости.
Используется серверный детектор речи: `vadThreshold=0.7`,
`silenceDurationMs=900`, `noiseReduction=far_field`, язык распознавания `ru`.
Перебивания сохраняются по событию начала речи; теперь они зависят от задержки
сервера. Тихая речь может потребовать снижения порога. Для гарнитуры можно
выбрать `near_field`. Отделение голоса пользователя от телевизора или чужой
речи не гарантируется.

Восстановление после обычного `restore.py --plugins --apply`: выполнить
`python3 plugins/voice-mode/apply.py --apply`, затем обновить и проверить снимок.
Основной restore пропускает три новых параметра, которых нет в исходном плагине;
скрипт патча применяет их из приватного снимка после сборки. Скрипт сохраняет
резервную копию исходников и сборки в игнорируемую `.local/plugin-patches/`,
откатывает их при ошибке и отказывается применять правку к незнакомой версии.
Обновления из каталога сопровождает `voice-mode-keeper`: совместимые правки
проверяются и применяются автоматически, несовместимые не накатываются.
Применение перезагружает плагин и завершает текущий голосовой разговор.

Проверки: 48 тестов upstream с регрессиями приветствия и настроек речи,
TypeScript, браузерная проверка разметки кнопок при ширине 390 px.
Проверка живого подключения через подписку приняла параметры шумоподавления и
вернула голосовое «Я готов. Что сделать?» без ошибок. Реальный микрофон телефона
и качество фильтрации бытового шума требуют проверки пользователем.
Для обновлённого патча также проверены 30 уникальных приветствий, исключение
предыдущего выбора, применение к исходной и предыдущей версии правки и
идемпотентность. Скрипт проверяет SHA-256 известных состояний каждого файла,
чтобы обновление самого патча не применяло старые изменения повторно.

В голосовых инструкциях, описаниях инструментов и служебных результатах убраны
формулировки о передаче задачи отдельному агенту. Короткие подтверждения,
статусы и итоги должны звучать от первого лица одного собеседника: «Сейчас
посмотрю», «Проверяю», «Нашёл». Реальные сведения о проектах и настройках
по-прежнему запрашиваются через инструменты; выдумывать результаты нельзя.
На прямые вопросы об архитектуре следует отвечать честно.
Тембр переключён с `marin` на `shimmer` для сравнения; Juniper из приложения
ChatGPT в поддерживаемом наборе голосов этого Realtime-подключения отсутствует,
точное соответствие не обещается. Манера речи задана как спокойная разговорная,
без дикторского пафоса. Голос меняется только в новом голосовом сеансе.

### Автоматическое сохранение правок при обновлении

Установлен собственный небольшой плагин `voice-mode-keeper` из
`plugins/voice-mode-keeper/`; сам Voice Mode остаётся установлен из каталога
и получает обычные обновления. Каждые 30 секунд сопровождение проверяет смену
версии или сборки и ждёт окончания штатного задания обновления BB.
Для совместимой ветки 0.1.x (не ниже 0.1.15) точные изменения проверяются
во временной копии: тесты upstream с регрессиями, TypeScript и сборка. Только
после этого заменяются исходники и сборка с сохранением резервной копии.
Ошибка активации вызывает откат; журнал позволяет восстановиться после
прерывания процесса. Параллельное обновление или изменение файлов не затирается.
Выключенный Voice Mode автоматически не включается.

Голос и остальные разрешённые несекретные предпочтения сохраняются отдельно
в состоянии сопровождения. Токены, авторизации, аудио и переписки не читаются
и не копируются. После успешной проверки обновляется приватный снимок.
При несовместимой версии остаётся исходный Voice Mode, в интерфейсе появляется
предупреждение; состояние доступно в настройках сопровождения и через
`bb plugin rpc call voice-mode-keeper status --json`. Для обычного совместимого
обновления ручное применение патча больше не требуется.

Сопровождение передаёт своему рабочему скрипту адрес собственного сервера
(`BB_SERVER_URL` из `bb.server.loopbackBaseUrl`). Без этого CLI обращается к
порту по умолчанию 38886, и на машине со вторым BB или с BB на другом порту
проверял бы и правил чужой Voice Mode.

Без входа в Codex на сервере: кнопка голосового разговора видна; нажатие
создаёт обычный тред «Голосовой разговор» с коротким служебным сообщением
агенту, затем в поле ввода появляется ошибка «The realtime connection plugin
failed: … No Codex login found … Run `codex login`». Сам `codex-realtime` в списке
плагинов в состоянии «требует настройки» с той же подсказкой. Голос начинает
работать после `codex login` (вход через ChatGPT) на машине сервера и
`bb plugin reload codex-realtime`.

Восстановление: обычный `python3 scripts/restore.py --plugins --apply`
устанавливает сопровождение вместе с его закреплёнными зависимостями.
Соседняя папка `plugins/voice-mode/` должна оставаться доступной. На новой машине
один раз задать её штатный CLI:
`bb plugin config voice-mode-keeper set cliPath "$(command -v bb)"`.
Путь хранится только в приватных настройках. Это нужно потому, что серверный
процесс BB не обязан иметь CLI в PATH. Обработчик не меняет подключение
OpenAI, подписку, платёжные настройки или маршруты агентов.

Проверки: имитация совместимого обновления во временной копии с 48 тестами и
проверкой типов; 8 тестов отказа, отката, конкурентного обновления, отключения
и восстановления после прерывания; сборка и рабочее состояние сопровождения.

### Читаемая нижняя панель и голос из нового треда

В `proxy-manager/proxy-ui.css` для экранов до 640 px подписи нижней строки
не сжимаются до нескольких букв: строка прокручивается горизонтально и
сохраняет штатную высоту 32 px. Многострочная сетка убрана: футер BB резервирует
одну строку, поэтому увеличение её содержимого вызывало наложение на поле
ввода при открытой клавиатуре. Подписи 14 px; штатные обработчики и настройки
маршрутизации не меняются. При 1024 px остаётся исходная раскладка.
Правка хранится в исходниках собственного плагина и восстанавливается обычным
`restore.py --plugins --apply`.

Регрессионная страница `plugins/proxy-manager/tests/footer-layout.html` проверяет
футер вместе с полем ввода и зарезервированной высотой: отсутствие наложения,
выхода страницы за ширину, обрезанных подписей и доступность последнего пункта
прокруткой. Проверены ширины 320/390/430/1024 px и высоты 844/500/420 px.
Уменьшенная высота имитирует область над клавиатурой; настоящую клавиатуру iOS
такая проверка не воспроизводит.

В патч Voice Mode добавлена компактная кнопка с волной рядом со штатным
микрофоном в области `new-thread`, без отдельной широкой плашки.
По нажатию SDK создаёт обычный видимый тред с
выбранными проектом, окружением/машиной, провайдером, моделью и разрешениями.
Служебное первое сообщение просит лишь подтвердить готовность, без команд и
правок проекта; затем включается голос и открывается созданный тред.
Черновик с текстом не заменяется: сначала его нужно отправить или очистить.
Если пользователь ушёл с экрана во время создания, микрофон позже сам не
включается. Начало разговора использует обычные лимиты выбранного агента.

Проверки: 51 тест Voice Mode и TypeScript; сохранение выбранного окружения,
модели и режима разрешений, отказ при невыбранном проекте; проверка наложения
обновлённого патча на имитацию новой совместимой версии. Нажатие на настоящем
телефоне и системный запрос микрофона требуют проверки на устройстве.

В прокручиваемой строке отключено скрытие полных названий и принудительное
сжатие компактных контролов BB. Переопределения находятся в том же базовом
CSS-слое, что и важные правила хоста. Если штатного выбора машины нет, рядом
с маршрутом отображается её имя только для чтения. Касания маршрута не
отменяют стандартную горизонтальную прокрутку. Проверка использует собранный
CSS и правила скрытия хоста; дополнительно проверяются видимость названий и
компактное размещение кнопки Voice Mode, перенос при перерисовке и очистка.

### Названия тредов на сенсорных экранах

В `plugins/machine-tabs/app.tsx` для `(hover: none)` снят отступ под
кнопки наведения и скрыта пустая правая ячейка штатной строки треда.
Ячейка сохраняется при наличии индикатора прогресса/ожидания, открытого
меню или постоянно видимых мобильных действий. Стрелки дочерних тредов
не меняются; CSS компьютера с наведением остаётся штатным.
Работает в установленном из этого checkout плагине `machine-tabs`.
Восстановление: `bb plugin build plugins/machine-tabs`, затем штатная
установка через `python3 scripts/restore.py --plugins --apply`.
Проверены сборка и браузерная модель штатной строки: пустое место,
индикаторы, дочерние треды, открытое меню и всегда видимые действия.
Это проверка CSS и разметки, а не тест на настоящем iPhone.

### Кнопка «Пуш» при свёрнутом поле ввода

Мобильное размещение `push-button` возле строки изменений больше не требует
наличия строки выбора ветки. При сворачивании поля ввода BB может убрать
строку ветки, оставив сводку Git; раньше это убирало и кнопку.
Проверено отдельным DOM-тестом без строки ветки: кнопка сохраняется возле
сводки изменений, отправка использует прежний `queue-if-active`.
Восстановление: собрать `plugins/push-button` и применить штатный
`restore.py --plugins --apply`.

### Projects по последней активности тредов на любом уровне

проверка типов — `npx tsc --noEmit` в каталоге плагина.

### Проверка маршрута Claude и Voice Mode во время работы

`proxy-manager` каждые 5 секунд при открытом индикаторе проверяет процесс
Claude в фактической папке и на машине текущего треда. Linux использует
`/proc`, macOS — `ps`/`lsof`. Прямой маршрут/прокси подтверждается только
установленным TCP-соединением процесса с разрешённым IP Anthropic/прокси.
Неоднозначные процессы, собственные облачные шлюзы, отсутствие соединения
или доступа показываются как непроверенные. Нет процесса — отдельная подпись.
Статус Codex не используется для Claude. Доступность ответа API и системный
VPN/TUN эта проверка не подтверждает; подсказка описывает границы проверки.

Результат хранится только кратковременно в памяти. Настройки Claude, маршрут
и авторизация не меняются, запросы к модели не отправляются. В UI не
передаются переменные окружения, URL прокси с паролями или адреса соединений.
Тесты проверяют отсутствие ложного «Без прокси», неоднозначность и выбор
реальной машины треда; живой RPC проверен на Linux. macOS требует проверки
на устройстве, парсер покрыт тестом.

В патче Voice Mode убрано скрытие запуска при работающем агенте.
Замена штатной отправки по-прежнему допускается только в пустом поле
при неработающем агенте; кнопка остановки задачи остаётся доступной.
Патч остаётся в `plugins/voice-mode/changes.json` и сохраняется keeper.
Восстановление: собрать/установить `plugins/proxy-manager` штатным
`restore.py --plugins --apply`, для Voice Mode — сохранённый apply/keeper.

### Мобильная строка кнопок ввода

В `handoff-button` подпись Handoff скрывается до 767px, остаётся значок с
доступным названием. `proxy-manager` находит нижнюю строку также в тредах без

чтобы он не занимал место рядом с голосом. `thread-account-usage` запрещает
перенос внутри штатной группы голосовых кнопок и отправки только на телефоне.
До 350px выбор модели получает собственную строку, чтобы не перекрывать кнопки.
Десктопные стили не меняются. Восстановление: собрать и установить эти три
локальных плагина через `restore.py --plugins --apply`. Проверять при обновлении
DOM-маркеров BB (`data-follow-up-composer-footer`, `data-promptbox-standard-actions`).


## Project Machine Setup — кнопка рядом с Enter

Плагин `project-machine-setup` добавляет «Подключить проект» перед неактивной отправкой нового треда, когда BB сообщает `Select an environment.`. Обновление локальной установки: сборка и `bb plugin reload project-machine-setup`. Проверка снимка: `python3 scripts/snapshot.py --check`.

## Project Catalog — вкладка «Проекты» и `bb catalog`

Плагин `project-catalog` (17.11.2026) добавляет каталог проектов. BB хранит о
проекте только имя, git-remote и папки на машинах и ищет проект по имени;
каталог держит на сервере BB одну карточку на проект: короткое описание,
заметки пользователя, категорию, теги, алиасы (включая русские написания),
ссылки и статус. Карточки читают вкладка «Проекты», агенты и любые скрипты
через `bb catalog find|list|show|describe|set|unlock|categories|sync`.

- Автоописание: тред в проекте без карточки (или с изменившимся
  README/AGENTS.md/CLAUDE.md при карточке старше 14 дней) один раз получает
  указание выполнить `bb catalog describe`. Плагин сам модель не вызывает.
- Ручные правки закрепляются: поле, изменённое во вкладке или `bb catalog set`,
  автоописание не перезаписывает; заметки пользователя не меняются никогда.
- Копии на машинах: модуль на каждой машине только читает папки. Для git —
  незакоммиченное, неотправленное, отставание, stash. Для папок без git —
  сравнение содержимого копий на двух машинах по хешам и список отличающихся
  файлов. Папка без git на одной машине считается нормой. Репозиторий,
  вложенный в папку без git, оценивается по своему git-состоянию. Папки можно
  пометить как свои на каждой машине (`--local-paths`), а проект целиком — как
  разные копии (`--independent yes`); такие части не сравниваются.
  Синхронизацию плагин не выполняет.
- С версии 0.3.0 (18.11.2026): у проекта может быть до четырёх категорий,
  категории собираются в группы (`bb catalog group`), в строке проекта есть
  список последних тредов, правка и новый тред, в панели — быстрые действия и
  смена категорий и тегов в один клик; поиск по проектам отделён от фильтра
  разделов в боковой панели.
- Проверка идёт раз в три часа, при открытии вкладки с данными старше 30 минут
  и по кнопке. Офлайн-машина показывает последнее известное состояние.

Исходники, lock-файл, тесты и навык: `plugins/project-catalog/`; ограничения и
команды — в его README и навыке. Установка внесена в `config/plugins.json`,
восстановление — `python3 scripts/restore.py --plugins --apply` либо команды из
README плагина. Карточки хранятся в хранилище плагина на сервере BB и входят в
бэкап BB, а не в этот репозиторий; на новой установке каталог пуст и
заполняется заново. Проверка после восстановления: `bb catalog list` и вкладка
`/plugins/project-catalog/projects`.

## Open on Mac (`file-local-open`)

Отдельный плагин добавляет две компактные иконки у ссылок на файлы в сообщениях:
ноутбук — скачать на подключённый Mac и открыть, стрелка вниз — сохранить без

показывает его в Finder. Для открытия копии идут в `~/Downloads/BB Files/open-*/`;

пределах папки презентации; динамические fetch/import и srcset не упаковываются.
Ограничение: 20 МиБ и 100 файлов. PDF-просмотр — по ширине без миниатюр, с выбором
масштаба и действиями открыть/скачать.

Работает на сервере BB, с host-entry на подключённых машинах. Исходники:
`plugins/file-local-open/`. Восстановление на машине сервера: `npm ci --prefix
plugins/file-local-open`, `bb plugin build plugins/file-local-open`, затем
`bb plugin install path:<checkout>/plugins/file-local-open --yes`. В настройке
`macHostId` выбрать ID Mac; пустое значение выбирает единственный подключённый Mac.
Обновление path-установки: сборка и `bb plugin reload file-local-open`. Выбор другого
PDF-просмотрщика в Settings → File openers имеет приоритет. Подробности и ограничения
— в навыке плагина. Проверены TypeScript, сборка, перенос HTML с вложенными ресурсами,
проверки целостности/путей, сохранение PDF с сервера и открытие в приложении Mac.

## Индикатор BB в строке меню macOS

Исходники собственного плагина: `plugins/menubar-status/`. На Mac индикатор
показывается только пока запущено приложение BB (`dev.bb.desktop`). Полный выход
из BB скрывает значок и закрывает панель; запуск BB возвращает индикатор.
Закрытие одного окна BB не завершает приложение. Наблюдатель и локальный HTTP
помощник остаются фоновыми LaunchAgent с RunAtLoad и KeepAlive: это позволяет
заметить запуск BB после входа в macOS. События NSWorkspace дополнены проверкой
раз в две секунды, в том числе после сна. Серверный плагин продолжает обновлять
данные независимо от окна BB.

Восстановление: установить плагин из `plugins/menubar-status` штатным CLI BB.
На целевом Mac выполнить `cd plugins/menubar-status/macos && zsh install.sh`
(нужны Xcode Command Line Tools и Python 3). Установщик собирает приложение,
устанавливает его и помощника в `~/Library/Application Support/bb-menubar/`,
регистрирует `dev.bb.status` и `dev.bb.menubar` в `~/Library/LaunchAgents/`.
В настройках плагина указать Mac в `hostId` и путь к `status.json` в `filePath`.
Токен помощника генерируется на машине и в репозиторий не копируется.

Доработка 2026-11-16 применяется к приложению на Mac; исходники синхронизируются
с checkout работающего плагина на сервере. Перезапуск серверного плагина для
изменения только Swift-клиента не требуется.

Проверка: `python3 plugins/menubar-status/macos/test_lifecycle.py` на Mac
с GUI-сессией. Проверяет скрытие без приложения, показ при запуске, скрытие
при выходе и повторный цикл на отдельном временном приложении; настоящий BB
не закрывается. Сборка Swift и эта проверка прошли после доработки.


## Local Transcribe — штатные обновления с доставкой движка

Плагин 0.2.4 переведён с path-установки на управляемые Git-релизы BB. Фактический персональный Git-источник и настройки исполнителей сохраняются в приватном `.local/config/` снимке. В публичном `config/plugins.json` остаётся обезличенная path-копия для резервного восстановления. Копия в `plugins/local-transcribe/` содержит также встроенный Python-движок; отдельный рабочий checkout на исполнителях не нужен.

BB примерно раз в 6 часов проверяет совместимые релизы. Применение запускается один раз на сервере BB через интерфейс или `bb plugin update local-transcribe`. Далее host-пакет доставляет код зарегистрированным исполнителям при обращении; офлайн-машины получают его после подключения. Новые зависимости подготавливаются в отдельном окружении, задачи ждут нужную версию. Уже запущенная задача сохраняет свой путь runtime и Python; старые каталоги не удаляются обновлением. Модели и результаты остаются в кэше/данных плагина.

Регистрация исполнителей: `workerHosts` (массив machine ID, хранится приватно); источники проекта поддерживаются для совместимости. `autoSetup` разрешает подготовку окружений. Нужны установленные Python и ffmpeg. На Mac начальная миграция может переиспользовать рабочие системные библиотеки без их изменения; Linux использует CPU-окружение. Незарегистрированная машина может пользоваться API, но тяжёлые зависимости на неё не устанавливаются.

Восстановление со своим приватным снимком: `python3 scripts/restore.py --plugins --apply` восстанавливает Git-источник и настройки. На новом BB заново выбрать актуальные machine ID. Без приватного снимка можно установить свой Git-источник командой `bb plugin install 'git:<URL-репозитория>@semver:^0.2.0' --yes`. Резервная path-копия: сначала `npm ci --ignore-scripts` в `plugins/local-transcribe`, затем `bb plugin build .` и `bb plugin install . --yes`; для штатных обновлений затем выбрать свой Git-источник.

Проверка: `bb plugin rpc call local-transcribe services --json` показывает runtimeVersion, environmentManaged и setupStatus. Контрольная обработка на 0.2.0 завершилась после штатного обновления до 0.2.1; Mac и Tru получили новый код, окружения переиспользованы, история 7 прежних задач сохранена. Добавлена проверка ожидания matching-окружения; тесты генерации/целостности host-пакета охватывают Python и Unicode-шаблоны. Повторные передачи не запускают ASR заново; идентификация людей отделена от технических кластеров голосов.

Начиная с 0.2.4 новые задачи с threadId уведомляют исходный тред один раз по результату/ошибке. Агент завершает ход после submit; по вопросу пользователя status проверяется один раз. Серверный outbox переживает reload/restart, при неоднозначной ошибке сверяет очередь и страницы истории BB по маркеру до повторной отправки. notify=false отключает пробуждение. Отмена и архивирование подавляют уведомления; старые задания автоматически не будят треды. Состояние доставки видно в completionNotification. 34 Node-теста проверяют оркестрацию и уведомления, включая потерю подтверждения, повторные тики и недоступность.

Исходники и lock-файл копии сохранены. Настройки: `python3 scripts/snapshot.py --settings-only`, проверка `--check`. Модели, окружения, задания, голосовые примеры, аудио, переписка и авторизации в Git не копируются.


## Индикатор BB в строке меню macOS

Исходники собственного плагина: `plugins/menubar-status/`. На Mac индикатор
показывается только пока запущено приложение BB (`dev.bb.desktop`). Полный выход
из BB скрывает значок и закрывает панель; запуск BB возвращает индикатор.
Закрытие одного окна BB не завершает приложение. Наблюдатель и локальный HTTP
помощник остаются фоновыми LaunchAgent с RunAtLoad и KeepAlive: это позволяет
заметить запуск BB после входа в macOS. События NSWorkspace дополнены проверкой
раз в две секунды, в том числе после сна. Серверный плагин продолжает обновлять
данные независимо от окна BB.

Восстановление: установить плагин из `plugins/menubar-status` штатным CLI BB.
На целевом Mac выполнить `cd plugins/menubar-status/macos && zsh install.sh`
(нужны Xcode Command Line Tools и Python 3). Установщик собирает приложение,
устанавливает его и помощника в `~/Library/Application Support/bb-menubar/`,
регистрирует `dev.bb.status` и `dev.bb.menubar` в `~/Library/LaunchAgents/`.
В настройках плагина указать Mac в `hostId` и путь к `status.json` в `filePath`.
Токен помощника генерируется на машине и в репозиторий не копируется.

Доработка 2026-11-16 применяется к приложению на Mac; исходники синхронизируются
с checkout работающего плагина на сервере. Перезапуск серверного плагина для
изменения только Swift-клиента не требуется.

Проверка: `python3 plugins/menubar-status/macos/test_lifecycle.py` на Mac
с GUI-сессией. Проверяет скрытие без приложения, показ при запуске, скрытие
при выходе и повторный цикл на отдельном временном приложении; настоящий BB
не закрывается. Сборка Swift и эта проверка прошли после доработки.

## KodaForge: редактор кода внутри BB

Сторонний плагин из каталога BB Community (`kodaforge@bb-community`, автор
Kodaks94, версия 0.7.0). Даёт раскладку как в IDE: проводник слева, редактор
Monaco в центре, справа панель с чатом BB и списком тредов проекта. Установлен
на пробу как замена связке «BB + отдельный VS Code»; исходники не копируются,
форка нет, обновления приходят из каталога.

Перед установкой исходники v0.7.0 просмотрены: обращений к внешним серверам
нет, программы запускаются без оболочки в папке проекта, из настроек Claude и
Codex читаются только имена MCP-серверов.

Два входа:

- значок медведя в левой панели — отдельная страница со списком проектов;
- в треде: правая панель → «+» → KodaForge — редактор в папке этого треда.

Ограничения, проверенные в headless-браузере:

- В списке проектов у каждого проекта одна строка `project checkout`, и она
  открывает только основную машину проекта (источник с `isDefault`). Копия на
  другой машине открывается только через тред, который на ней работает.
- В списке не показано, на какой машине лежит проект.
- Подсказки языка есть для Python и TypeScript/JavaScript, отладка только для
  Python; языковые серверы и debugpy ставятся отдельно на машину с кодом.

Поверх каталожной версии держатся три правки из `plugins/kodaforge-compat/`
(см. его README): без рамок вокруг «похожих» букв в русском тексте, быстрое эхо
в терминале и вкладки с именем проекта и машины. Plugin Keeper 0.2.5
применяет следом патчи `workspace-close.patch` и `workspace-close-menu.patch`.

Правый клик по верхней вкладке открывает **Close others** и **Close all**.
При закрытии вкладки оставшиеся редакторы сохраняют состояние, а после
закрытия последней вкладки остаётся пустая страница. Подтверждение
учитывает несохранённые изменения закрываемых областей.

Применение на сервере BB — `python3 scripts/kodaforge_workspace_tabs.py --apply`.
Проверка — та же команда с `--check`. Keeper собирает исправленный плагин
на копии, сохраняет каталожный источник и восстанавливает правки после
совместимых обновлений.

Восстановление: `python3 scripts/restore.py --plugins --apply` или вручную
`bb plugin install kodaforge@bb-community --yes`, затем команда Keeper выше. Удаление:
`bb plugin uninstall kodaforge`. Настроек, требующих переноса, нет.

## Центральный чат в KodaForge

При первом ручном открытии редактора диалога в каждом проекте плагин `kodaforge-inspector` спрашивает вид («Применить» — для этого проекта, «Сохранить для всех» — для всех сразу): штатный (код по центру, чат справа; отмечен заранее и действует до выбора) или чат по центру. В окне выбора показаны схемы обоих видов. Общий выбор хранится в настройке `layout` (`ask`, `native`, `center`), выбор проекта — в хранилище плагина и важнее общего; меняется кнопкой «Вид…» либо `bb plugin config kodaforge-inspector set layout <значение>`. В виде с центральным чатом вкладка «Файлы и код» возвращает редактор. Терминал и ветка Git доступны в нижней строке KodaForge. Инспектор проверяет совместимость интерфейса при открытии и после замены панелей. Основной плагин обновляется через BB из каталожного источника.

Настройки `autoOpen` и `autoOpenThread` (по умолчанию выключено и пусто) открывают один выбранный диалог сразу в KodaForge; остальные диалоги и ссылки на сообщения открываются как обычно.

Проверка — `bb kodaforge-inspector status`. Для возврата к штатному виду выберите его кнопкой «Вид…» или задайте `layout native`; полное отключение — `bb plugin disable kodaforge-inspector` и обновление страницы. [Установка и восстановление центрального чата](../plugins/kodaforge-inspector/README.md).

## Code Open: код проекта или треда в один клик

`plugins/code-open/` — собственный маленький плагин поверх KodaForge. Своего
редактора в нём нет: он открывает экран KodaForge в нужной папке. Нужен, потому
что в самом KodaForge выбор проекта неудобен: список без поиска, машина не
подписана, а у проекта на нескольких машинах открывается только основная.

Кнопка `</>` стоит в трёх местах:

- в заголовке проекта в боковом списке, рядом с «+»;
- в строке треда при наведении — штатное «действие треда» BB, его рисует сам BB;
- в шапке открытого треда — всегда видимый значок.

Кнопка в строке треда показывается, пока ключ `code-open/open-code-menu` стоит
в настройке списка тредов `rowActions` (не больше трёх быстрых действий):
`bb thread-list prefs set rowActions '["code-open/open-code-menu","bb--core/newThreadInEnvironment","bb--core/archive"]'`.
Значение хранится в снимке `thread-list.json`. То же действие есть в меню треда.

Поведение:

- Кнопка треда открывает папку этого треда на его машине, справа — чат этого
  же треда.
- Кнопка проекта открывает папку самого свежего живого треда проекта, то есть
  ту машину, где идёт работа. Если тредов нет — основной checkout проекта.
- Чат справа открывается сразу. Список тредов BB сворачивается (окно от 900 px)
  и возвращается при выходе из редактора.

Ограничения: требуется плагин `kodaforge`; переход сделан через адрес его экрана
и его ключ `localStorage`, поэтому после обновления KodaForge или BB проверь три
места в браузере. Кнопка в строке треда проверена в headless-браузере с
эмуляцией наведения: одна кнопка на строку, пересоздания нет.

В версии 0.1.0 после переустановки без перезагрузки страницы в окне оставались
старые копии плагина: кнопки в строках множились, интерфейс тормозил. В 0.1.1
живой остаётся только последняя копия, пересчёт идёт не чаще раза в 200 мс и
не реагирует на изменения внутри редактора. После переустановки страницу BB
всё равно стоит перезагрузить.

С 0.2.0 кнопка в строке треда переведена на штатное действие треда: плагин
больше не вставляет её в страницу и не следит за списком тредов. Штатное
размещение в шапке (`placement: "header"`) пробовали и убрали в 0.2.1: в узком
окне BB прячет такую кнопку в меню «…».

В 0.3.0–0.3.2 плагин менял три настройки редактора KodaForge (плавная
прокрутка, миникарта, «липкие» заголовки), пока искалась причина рывков. Причина
оказалась в стилях `machine-tabs`, поэтому в 0.4.0 это убрано: плагин один раз
на браузер удаляет три своих значения из `localStorage` → `kodaforge:settings`,
и действуют настройки автора. Временный замерщик прокрутки тоже удалён.

Сборка и установка: `NODE_PATH=/usr/lib/node_modules bb plugin build .`, затем
`bb plugin install path:<репозиторий>/plugins/code-open --yes`. Проверки:
`npx tsc --noEmit`, `npx vitest run`. Восстановление:
`python3 scripts/restore.py --plugins --apply` (сначала ставится `kodaforge`).

## Производительность: правила `:has()` в стилях плагинов

Вертикальная прокрутка в редакторе KodaForge шла рывками, горизонтальная — нет.
Замер в окне пользователя (временный замерщик в `code-open` 0.3.2, удалён в
0.4.0: длительность кадров и long animation frames по осям прокрутки через
`PerformanceObserver`, отчёты уходили на сервер плагина) показал: при вертикальной прокрутке до трети кадров длиннее 25 мс, почти всё
время — пересчёт стилей и раскладки, скрипты ни при чём.

Причина — стили `machine-tabs` (0.1.0): правила
`[data-machine-tabs-list] :has(> [data-sidebar-visibility-group])` и
`span:has(> .bb-thread-title > …)`. У `:has()` без класса или атрибута на самом
элементе браузер после каждой вставки узла в любом месте страницы перепроверяет
всю страницу, а редактор при вертикальной прокрутке вставляет строки каждый
кадр. В 0.1.2 контейнер групп адресуется классом BB `div.space-y-4`, значок
агента — `[data-sidebar-thread-provider]:has(+ .bb-thread-title > …)`.

Правило для всех собственных плагинов: `:has()` только на элементе с классом
или атрибутом, никогда на `*` или голом теге. Если BB переименует класс
`space-y-4`, у групп в списке тредов пропадёт только ровный отступ.

Повторный замер после правки: длинных кадров 0–2 за 5 секунд вместо 36–45,
пересчёт стилей 0–13 мс вместо 1,2–1,5 с.

## Config Updates — релизы доработок и «Обновить с ИИ»

Зачем: установившие доработки из этого репозитория должны узнавать о новых
опубликованных версиях, а применять их должен агент, потому что обновление может
быть плагином, настройкой, скриптом или несколькими шагами. Штатные
`bb plugin outdated` / `bb plugin update` обновляют отдельные плагины по тегам
и не покрывают общий выпуск со скриптами, поэтому добавлен небольшой плагин.

Состав:

- `plugins/config-updates/` — плагин: проверка стабильных GitHub Releases
  `vX.Y.Z` каждые шесть часов и по запросу, значок в нижнем ряду боковой панели с
  карточкой и кнопкой «Обновить с ИИ» (сама открывается при новом релизе, не
  чаще раза в сутки на версию), раздел «Обновления доработок» в
  настройках плагина, команда `bb config-updates status|check|start`. Кнопка
  открывает штатный экран нового треда с готовым заданием, проектом этого
  checkout и машиной сервера (модель выбирает пользователь); после полностью
  применённого релиза тред сам уходит в архив. Релиз без действий для этой
  установки принимается при проверке без агента; значок в нижнем ряду виден
  только при обновлении, иначе убран в меню «…» (плагин правит свой пункт в
  `sidebar.hiddenFooterItems`; формат ключа — внутренний для BB 0.49). Навык: `skills/config-updates/SKILL.md`.
- `scripts/updates.py` — получение закреплённого релиза без перезаписи локальных
  правок, план по пропущенным релизам, пошаговое применение «проверить →
  применить → проверить», блокировка от параллельных запусков, журнал
  `.local/updates/journal.json` по шагам и машинам. Тесты: `scripts/test_updates.py`.
- `docs/updates.md` — обязательный порядок применения и публикации;
  `docs/releases/` — инструкции и манифесты релизов; `docs/releases/next/` —
  ожидающие шаги будущих версий, `docs/releases/templates/` — заготовки шага.

Ограничения: плагин работает только из checkout (ему нужен соседний
`scripts/updates.py`) и требует, чтобы checkout был проектом BB; иначе кнопка
объясняет, что сделать. Запросы к GitHub без авторизации: приватный репозиторий
не поддерживается. Проверка ничего не устанавливает. Журнал не входит в
зашифрованную личную копию; при его потере шаги проверяются заново по
фактическому состоянию.

Установка и обновление на сервере BB:

```sh
npm --prefix plugins/config-updates ci --include=dev
bb plugin build plugins/config-updates
bb plugin install path:"$PWD/plugins/config-updates" --yes   # первый раз
bb plugin reload config-updates                               # после изменений
bb config-updates check
```

Восстановление: запись `config-updates` в `config/plugins.json`, поэтому
`python3 scripts/restore.py --plugins --apply` собирает и ставит плагин. После
восстановления целой установки из релиза зафиксируйте исходную версию:
`python3 scripts/updates.py baseline vX.Y.Z --commit <sha>`.

Проверки: `npm test` и `npm run typecheck` в `plugins/config-updates`;
`python3 -m unittest discover -s scripts -p 'test_updates.py'`;
`bb config-updates check` (код 0 и строка о релизах; код 1 — ошибка проверки).


## Native dictation: selecting Codex without a plugin patch

The ordinary composer microphone uses Settings → AI services → voice, independently
of Voice Mode. A personal installation can select Codex with
`bb settings ai-services set voice codex --plugin provider-codex`. Verify with
`bb settings ai-services show --json`: voice must name `provider-codex/codex` and
the service must be ready. This does not change Voice Mode, thread titles or
commit-message generation. Recognition quality still requires an actual speech
check; service readiness alone is not evidence that translation errors are fixed.

BB 0.49 supports one explicit service or Automatic, not a user-defined fallback
order. Explicit Codex has no automatic bb cloud fallback. To switch manually use
`bb settings ai-services set voice bb --plugin bb-ai`; to restore the default
cloud-first fallback use `bb settings ai-services set voice automatic`.

The owner's selection is saved only in ignored `.local/config/ai-services.json`;
this is an optional personal setting, not a rollout to other installations.
The current `scripts/restore.py` restores only `automatic`/`off` AI selections.
For a saved explicit service, after restoring the corresponding installed provider,
repeat the `set voice` command above and verify readiness. Do not assume the
private JSON alone reapplies it. No plugin source or credential changes are needed.

## Voice Mode: waiting for thread context

Keeper 0.2.1 carries a narrow Voice Mode instruction/status fix. While a task is
pending, the voice acknowledges the check and waits instead of claiming missing
context. Active/starting status excludes the previous task's answer; UI questions
and completed results remain distinct. No new plugin, storage or transcript UI.
Sources: `plugins/voice-mode/changes.json`; usage and constraints are in that
folder's README and the keeper skill. Apply through `auto_update.py`, which tests
and builds in staging before reloading Voice Mode. A reload ends an active voice
session. Verify with `python3 plugins/voice-mode/apply.py --check`; snapshot settings
with `--settings-only`. Restore by reinstalling the keeper and applying the reviewed
patch; automatic catalog-update compatibility checks stay in place. Backend
regressions verify stale-result exclusion and completed-result delivery. A live
conversation is still required to validate model phrasing. To revert, restore the
previous patch specification and its matching source backup using the existing
patch recovery process, or disable the keeper and reinstall catalog Voice Mode.

## Voice Mode personal fork and upstream contribution

Source: https://github.com/ainurminibaev/bb-plugin-voice-mode, branch
`main`. Stable release v0.2.0 contains the Russian speech, mobile
launch, readiness greetings, noise controls and waiting/status edits. No separate
transcript storage or panel. Generic waiting/status behavior is proposed in
https://github.com/steveafrost/bb-plugin-voice-mode/pull/7. The upstream PR passed
47 tests; the fork passed 53 tests, typecheck and build.

`config/plugins.json` selects `@semver:^0.2.0`. BB discovers compatible stable
0.2.x tags through its native Plugins updates; apply with `bb plugin update
voice-mode`. Publishing a fork release does not require a bb-config release.
Source development and releases live in the fork; bb-config records installation,
settings and restoration. The old patch is retained only for catalog recovery.
Keeper 0.2.3 skips source patching for the fork release channel without checking
fixed commit/file hashes, and continues protecting the other catalog plugins.
`fork.json` retains the old pin solely as an allowed migration origin.

A fresh restore installs the fork directly from its Git release channel.
Older private snapshots can contain both the fork source and a catalog alias.
Restore uses the recorded fork in that case. An update checks existing Voice
Mode installations and skips installations where Voice Mode is absent.

Migration from the original catalog or the old fork pin:
`python3 plugins/voice-mode/switch_to_fork.py --apply`, then `--check`.
BB's managed-source replacement requires remove/install. The script refuses before
removal if a Voice Mode secret is configured, retains nonsecret settings and enabled
state, and leaves connection-plugin credentials untouched. Private recovery data
live under `.local/plugin-patches/voice-mode`. A failure before registration restores
the prior source; a failure after registration requires inspection and preference
recovery from the journal. Never silently discard configured credentials.
Reinstallation ends live voice sessions. Rollback uses the same credential check
and the previous source/settings from the journal. Updates within the configured
release range use BB's normal update/rollback path, not this migration script.

The fork's v0.2.0 release is published. The pending bb-config steps cover the
one-time migration and keeper change; no new bb-config stable release is implied.

Компоненты из `config/externally-managed-plugins.json` не входят в комплект
этого репозитория. Snapshot не сохраняет их настройки и исходники; restore
не устанавливает, не включает, не выключает и не настраивает их, даже если
осталась старая запись. Их установка и обновление выполняются владельцем
соответствующего продукта отдельно. Рабочая установка BB от исключения
не меняется.

## Image Gen — генерация и правка картинок для всех агентов (17 ноября 2026)

Собственный плагин `image-gen` в отдельном приватном репозитории `bb-plugin-image-gen`
(единственный источник исходников). Копии исходников здесь нет: этот репозиторий публичный,
а плагин обновляется из своего Git. Git-источник и настройки хранятся только в приватном
снимке `.local/config/`; `restore.py --plugins --apply` с этим снимком ставит плагин из Git.
Без приватного снимка плагин не восстанавливается: это ожидаемо, его репозиторий приватный.

Что делает: Codex-треды рисуют сами встроенным `image_gen`. Остальные провайдеры получают
инструменты `image_generate`, `image_edit`, `image_status`, `image_cancel`, `image_retry`,
`image_services` и команду `bb image-gen generate|edit|status|cancel|services`. Плагин
запускает `codex exec` в терминале выбранной машины (служебных тредов нет), проверяет файл
по SHA-256 и кладёт его в папку проекта вызывающего с описанием происхождения `*.png.json`.
Каскад: машина треда → другие готовые машины → (только при `maxTier=1` и заданном ключе)
платный OpenAI API. Лимит переносится только на машину с другим `accountGroups`;
неизвестный исход не повторяется автоматически.

Требования к исполнителю: Codex CLI с `codex login` (подписка ChatGPT) и python3 ≥ 3.9.
Без Codex: секретная настройка `openaiApiKey` и `maxTier=1` (платно за картинку).

Установка/обновление/откат:

```sh
bb plugin install 'git:<URL-репозитория>@semver:^0.1.0' --yes
bb plugin update image-gen --yes          # новая версия = новый тег vX.Y.Z
bb plugin install 'git:<URL-репозитория>@v0.1.2' --yes   # откат на тег
bb image-gen services                     # готовность машин
```

Аккаунт Codex на каждой машине плагин определяет сам (штатный `account/read` Codex,
хранится только хеш почты). Одинаковый аккаунт = общий лимит: при лимите задача на машину
с тем же аккаунтом не переносится. Настройка `accountGroups` нужна только для ручной замены.

Проверка 17.11.2026: `npm test` — 21 JS-тест (каскад, e2e собранного плагина с подставным BB
и Codex: инлайн-результат, перенос между машинами, правка, нет Codex, платный API, лимит,
уведомление, отмена, перезапуск, инструкции, CLI) и 9 тестов исполнителя. Реально в BB:
обновления 0.1.0→0.1.4 через `bb plugin update`; генерация на Tru (≈40 с) и правка по картинке
на UA с доставкой на Tru; спящий Mac показан как offline.

## Windows: сервер BB и рабочий компьютер

Скрипты и плагины писались на Linux и macOS. Ниже — что нужно и что проверено, когда
сервер BB работает на Windows (в том числе BB на одном ПК без других машин).

Требования на машине сервера:

- Node.js 24.22.1 или новее в ветке 24. Версии от 23.0 примерно до 24.19 на Windows
  аварийно завершаются при выходе из команд, которые добавляют плагины (`bb thread-list …`,
  `bb config-updates …`): результат печатается, затем
  `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), src\win\async.c`, и код выхода
  ненулевой. Это ошибка Node (nodejs/node#56645, исправление nodejs/node#61999). Проверено:
  24.13.0 падает в каждом запуске, 24.22.1 — ни в одном.
- Python 3.11+ как настоящий `python` в PATH. `python.exe` из
  `%LOCALAPPDATA%\Microsoft\WindowsApps` — заглушка Microsoft Store. Плагинам, которые сами
  запускают Python (`config-updates`, `voice-mode-keeper`), путь можно задать настройкой
  `pythonPath`.
- Git for Windows и `git config --global core.longpaths true`: без этого каталожные плагины
  с длинными путями (Tokenomics) не клонируются.
- Процесс сервера BB получает PATH при запуске приложения: после установки Git или Python
  перезапустите BB.

`scripts/platform_compat.py` собирает отличия Windows в одном месте; на других системах его
функции ничего не меняют. Он запускает `bb`, `npm` и `patch` (на Windows это `.cmd` и
`patch.exe` из поставки Git; понимает и лаунчер `<каталог данных>\bin\bb.cmd`, который
получают автоматизации), перезапускает скрипт в режиме UTF-8, заменяет `fcntl` и симлинки
каталогов. При Node с описанной ошибкой CLI запускается через Node из поставки BB.

Работают на Windows: `updates.py`, `snapshot.py`, `restore.py`, `codex_defaults.py`,
`patch_keeper.py`; плагины `config-updates`, `voice-mode-keeper` (сопровождение Needs You,
Tokenomics и KodaForge; часть для Voice Mode не проверялась), `file-local-open`,
`menubar-status` с клиентом на панели задач и все плагины без системных зависимостей.
Не перенесены: резервные копии (`daily_backup.py`, `server_backup.py`, `private_backup.py`,
`backup_keys.py` — `fcntl` и macOS Keychain), `setup_tracking.py`, службы macOS и systemd,
обработчик Finder у Project Open, `apply_*_compat.py` (их заменяет `patch_keeper.py`).

Особенности:

- Git for Windows по умолчанию выдаёт исходники с CRLF. Этот checkout держите с LF
  (`git config core.autocrlf false`, `git config core.eol lf` до первого checkout).
  Исходники каталожных плагинов BB клонирует сам, с CRLF: `patch_keeper.py` накладывает
  патч на LF-копию и возвращает прежние окончания строк.
- `.bb/AGENTS.md` — симлинк; без режима разработчика Windows получает вместо него текстовый
  файл с путём. Codex и Claude Code читают корневые `AGENTS.md` и `CLAUDE.md` напрямую.
- В NTFS нет POSIX-битов доступа: проверки прав `0600` в тестах на Windows пропускаются,
  доступ к `.local/` определяют права каталога.
- Browser Automation на Windows-хосте не запускается (у DevBrowser нет сборки). Для
  агентов есть `plugins/browser-page`: навык и скрипт `bb-page.mjs` поверх штатных команд
  `bb browser`.

### Статус на панели задач Windows

`plugins/menubar-status/windows/` — клиент для Windows к тому же серверному плагину.
`bb Status.exe` показывает полоску на панели задач, у её левого края. Она повторяет
заголовок значка в строке меню macOS (`macos/BBStatus.swift`, `draw` и `usageBlock`) в
масштабе панели задач, слева направо:

- `bb`;
- значок и число на каждое состояние, в котором есть агенты: оранжевая реплика с «!» —
  ждут вас, красный восьмиугольник — ошибки, синие круговые стрелки (вращаются) — в работе;
  если таких нет — зелёная точка с числом новых ответов или серая галочка; при потере
  данных — перечёркнутый значок связи;
- блок лимитов: знак агента (Claude, OpenAI — штатные значки провайдеров BB из
  `windows/icons/`), по аккаунту — вертикальные столбики, заполняются снизу вверх:
  толстый — 5 часов, тонкий — неделя; под ними инициалы машин аккаунта и зелёное «+N»
  при доступных сбросах лимита; между агентами — черта;
- один таймер до сброса значимого лимита: самого израсходованного пятичасового, а если у
  того аккаунта исчерпана и неделя — недельного; без пятичасовых — самой израсходованной
  недели. От 90 % это белый текст на оранжевой плашке, при 100 % — на красной.

Процентов и подписей «5ч»/«нед» на полоске нет, как и на Mac: они в панели. Лимит, по
которому bb не получил числа, столбика не получает и ничем не подменяется; в панели у
такого аккаунта строка «5ч — нет данных». Лимиты отдельных моделей и прочие окна
(суточное, более короткое) на полоске не показываются, но в панели Windows-клиента
перечислены под своими названиями. Данные лимитов старше 15 минут не показываются.

Наведение на полоску открывает над ней панель `panel.html` — ту же, что на Mac: лимиты
аккаунтов, агенты по разделам, переписка и поле ответа. Панель прячется, когда курсор
уходит с неё и с полоски. Клик по полоске закрепляет панель, повторный — прячет (так же
одним кликом убирается панель, в которой вы печатали); правый клик — меню. Наведение не забирает клавиатуру у окна, в котором вы работаете; клик или
нажатие клавиши внутри панели отдают ей клавиатуру, чтобы написать ответ (страница сообщает
об этом программе тем же сообщением `pin`, что и macOS-приложению), Esc закрывает её.
Всё показывается, только пока запущен BB Desktop. Данные читаются из файлов рядом с
программой, bb она не вызывает; помощник `server.py` (127.0.0.1:47615, токен) запускается
и перезапускается ею. Помощнику передаётся номер процесса программы: он завершается сам,
когда программы не стало, даже если её сняли, а не закрыли (иначе каждый перезапуск
оставлял бы по процессу Python); порт на Windows он занимает один.

Устройство. Сторонних элементов панели задач в Windows 11 нет, поэтому полоска — окно без
рамки поверх панели задач; при окне на весь экран оно убирается, при скрытой или
вертикальной панели задач вместо него показывается значок в области уведомлений. Панель —
собственное окно программы без рамки с WebView2 внутри (движок Edge из состава Windows 11;
для Windows 10 нужен WebView2 Runtime). Окно своё, поэтому показывается без активации и
всегда одно. До клика пользователя оно не может стать активным вовсе: Windows отдаёт
клавиатуру первому окну только что запущенной программы, и загрузка веб-представления её
запрашивает. Первая версия клиента показывала панель в отдельном окне Edge; от этого
отказались: Edge выводит своё новое окно на передний план, что бы ему ни указали, а
фоновая программа вернуть фокус другому окну не может — Windows ей отказывает.

Установка на нужном ПК: `powershell -ExecutionPolicy Bypass -File
plugins/menubar-status/windows/install.ps1` (нужен Python; программа собирается
компилятором C# из состава Windows), затем `hostId` и `filePath` по подсказке установщика.
Три библиотеки WebView2 SDK (Microsoft, распространяемые) установщик берёт из пакета NuGet
`Microsoft.Web.WebView2` закреплённой версии и сверяет SHA-256 пакета; без сети —
`-WebView2Package <файл>`. `-Ui tray` — вместо полоски значок в области уведомлений с
самым срочным состоянием и числом, `-Ui both` — и то и другое. Файлы лежат в
`%LOCALAPPDATA%\bb-menubar`, автозапуск — ярлык в папке «Автозагрузка». Удаление: тот же
скрипт с `-Remove`. Память: программа около 55 МБ и процессы WebView2 около 290 МБ, пока
открыт BB; страница приостанавливается через 30 секунд после скрытия панели.

Проверки (все — в `plugins/menubar-status/windows/`):

- `test-render.ps1` рисует полоску по выдуманным данным, не трогая рабочие файлы: пять часов
  и неделя, сбросы «+N», несколько машин, сброс через 10 минут, исчерпанная неделя, только
  недельные лимиты, устаревшие данные; тёмная и светлая панель задач. Результат — PNG.
- `test-hover.ps1` — приёмка настоящим курсором: три цикла «навести — показалась, увести —
  скрылась», холодный старт (перезапуск программы и наведение сразу), клик внутри панели,
  клики по полоске (убрать панель, закрепить, скрыть). Пока курсор только наводится, фокус
  клавиатуры замеряется каждые 50 мс: ни панель, ни полоска не должны получить его ни на
  миг; окно панели ровно одно. В конце — скорость и цена: панель показывается не позже
  0,6 с после наведения и прячется не позже 1 с после ухода (180 и 450 мс из них — намеренные
  задержки), программа в покое занимает меньше 5 % одного логического ядра, помощник один и
  от прежних запусков не осталось ни одного.
- `"bb Status.exe" --self-test` — то же без курсора, итог в `self-test.log`.
- Файл `debug` рядом с программой включает журнал `debug.log` (переходы фокуса и ошибки
  веб-представления, без содержимого страниц).

Проверено на Windows 11, 1920×1080, 100 %: `test-hover.ps1` — 0 ошибок при активном окне
другой программы, 0 мс перехвата клавиатуры во всех циклах; `test-render.ps1` — все случаи.
Замеры там же (доли одного логического ядра из 20): панель показывается через 225–257 мс,
прячется через ~590 мс; программа в покое — 1–2 % (значок «в работе» вращается), веб-представление
со скрытой панелью — меньше 0,5 %, с открытой — около 0,5–1,5 %. Точка «в работе» в панели на
Windows мигает ступенями: плавное мигание заставляло WebView2 перерисовываться 60 раз в
секунду и стоило около 15 % ядра, пока панель открыта.
Полоска занимает около 210 px слева; при выравнивании значков панели задач по левому краю
она их перекроет — тогда используйте `-Ui tray`. Не проверялось: другой масштаб экрана,
несколько мониторов, Windows 10.

### Открытие файлов на Windows-компьютере

## Proxy Manager: маршруты моделей только в BB (0.3.0)

В Подключениях добавлен выбор напрямую / через OpenCodex для Codex и Claude Code на каждой машине. Системный VPN и обычные конфигурации CLI не меняются. Детали, ограничения авторизации MCP и команды восстановления: `plugins/proxy-manager/README.md`. Исходники и следующий шаг: `docs/releases/next/plugin-proxy-manager-model-routes.*`. Установка: `bb plugin build plugins/proxy-manager`, затем `bb plugin reload proxy-manager`. Режимы сохраняются в KV плагина; восстановление на другой машине — командой `bb proxy-manager model-route <host-id> <provider> <mode>` после проверки штатной авторизации. Не переносить приватный профиль Codex с токенами через Git.

Проверка 0.3.0 на Windows: `npm run check` и 23 теста маршрутизации (включая

не измерялось. Старый `native.test.ts` с POSIX-правами `0600` остаётся известным

### Proxy Manager 0.3.1: проверка OpenCodex перед выбором

Пункт OpenCodex остаётся видимым, но отключён, если шлюз не настроен или недоступен.

### Proxy Manager 0.3.2: исправления по итогам ревью

Прямой профиль Codex больше не держит отдельную копию входа: `auth.json` общий с
обычным профилем, поэтому обновление токена и вход в другой аккаунт действуют на
обе стороны. `.env`, `hooks.json` и `AGENTS.md` повторяют обычный профиль вместе
с удалением, так что прямой режим не теряет сетевые настройки выбранного прокси.
Каталоги истории создаются общими до первого запуска. Смена маршрута сохраняется
до остановки тредов и не отменяется её ошибкой; неостановленный тред
перезапускается после завершения ответа. Запуск агента использует маршрут,
подготовленный при отправке сообщения, даже если повторный вызов машины не
прошёл. Задержанное сообщение повторяется через 30 секунд. Режим `inherit`
возвращает собственные настройки CLI. Проверено тестами на Linux; на машине с
работающим OpenCodex исправления не проверялись.

## Codex-делегирование: цель первой и надзор (18 ноября 2026)

Правило владельца для всего BB: тред, который создаёт подтред или тред в другом
проекте на Codex, первым сообщением ставит ребёнку цель (Goal) и следит за ним
каждые 5 минут, пока цель не выполнена.

Как устроены цели Codex в BB 0.49.0 / Codex CLI 0.170.0 (проверено вживую):
встроенный провайдер разбирает только `/goal resume|pause|clear`, а `/goal
<текст>` передаёт модели обычным текстом. Цель создаёт сама модель инструментом
`create_goal`, когда её явно просят (фича `goals` в Codex включена). Поэтому
цель встаёт и от строки `/goal …` в первом сообщении, и от явной просьбы
сообщением другого треда в уже работающий ход. Состояние цели — событие ленты
`thread/extensionState/updated` с `kind = provider-codex/goal` (`bb thread show`
его не показывает). Ответ модели «цель поставлена» не доказательство: в тесте
модель так ответила, а проверка шла только по событию.

### Установлено: плагин Codex Delegation Watch 0.1.0

`plugins/codex-delegation-watch` — серверный плагин без интерфейса. Ставит под
надзор каждый видимый тред Codex с родителем, созданный после установки
(момент сохранён в его хранилище; более старые треды — только командой `add`).
Скрытые фоновые треды не подключаются. Фоновая служба раз в 30 с проверяет,
кому пора: первая проверка через 2 мин, затем каждые 5 мин; после окончания
хода, сбоя, вопроса, архивации — сразу. Правила (`policy.ts`, 16 тестов):

- нет цели после 90 с работы — ребёнку сообщение вызвать `create_goal`;
- ход закончился при активной цели две проверки подряд — просьба продолжить
  или задать один вопрос;
- вопрос/разрешение, ошибка без повтора в очереди, цель blocked/paused/
  лимит, 15 мин без событий в работающем ходе, ход закончен без цели —
  одно сообщение родителю `[Надзор Codex] …` на каждую проблему;
- не больше 3 подталкиваний, затем сообщение родителю и режим наблюдения;
- цель `complete`, архив, удаление или 3 дня — надзор снимается сам;
- при норме ничего не пишет. Смысловой «уход не туда» не оценивает — это
  делает родитель по отчётам ребёнка.

Команды: `bb codex-watch status [--all]`, `check <тред>` (без действий),
`add <тред> [--observe]`, `remove <тред>`, `resume-goal <тред>` (отправляет
`/goal resume` от имени плагина, без подписи отправителя, поэтому провайдер
выполняет команду; только для неработающего треда). Навык
`codex-delegation` (глобальный) описывает правило и команды.

Чтобы правило знали все агенты: блок `[codex delegation]` в настройке
`custom-instructions` (лимит настройки 4096 символов, поэтому блок короткий
и ссылается на навык); в навыке dispatch личного помощника — раздел «Ребёнок
на Codex: цель первой» (файл проекта помощника, не этого репозитория).

Установка и обновление: `npm ci --include=dev`, `npm test`, `npm run
typecheck`, `bb plugin build .`, `bb plugin install . --yes` (первый раз) или
`bb plugin reload codex-delegation-watch`. Восстановление: запись в
`config/plugins.json`, `scripts/restore.py --plugins --apply`; блок
инструкций — из приватного снимка настроек. Удаление: `bb plugin remove
codex-delegation-watch`. Настроек нет, состояние — в kv-хранилище плагина.

Проверка 18.11.2026 на Tru: тесты и typecheck; вживую — три скрытых треда
Codex получили цель (строка `/goal` первой; явная просьба; сообщение другого
треда в работающий ход), все дошли до `complete`. Плагин сам подключил два
новых видимых тестовых треда; ребёнку без цели через 2 мин ушло сообщение, и
цель встала в работающем ходе; остановленный тред с целью `paused` — родителю
пришло одно сообщение, `resume-goal` вернул цель в `active`. Тред аудита nginx
(создан до плагина, без цели) поставлен в режим `--observe`: надзор видит
«работает без цели», но ничего ему не пишет.

## Chrome для агентов без повторных «Allow remote debugging?» (18 ноября 2026)

**Проблема.** chrome-devtools-mcp с `--autoConnect` подключается к основному
профилю Chrome (логины, сохранённые пароли). Начиная с Chrome 144 браузер
спрашивает «Allow remote debugging?» на каждое новое DevTools-подключение;
флага или политики, запоминающих разрешение, нет. `--remote-debugging-port` на
профиле по умолчанию Chrome 136+ не разрешает. Раньше каждая сессия Codex
запускала свой экземпляр MCP, и диалог появлялся на каждую сессию, а агенты
зависали в ожидании.

**Решение.** Одна фоновая служба macOS (LaunchAgent
`dev.bb-config.chrome-devtools-mcp-shared`) держит один экземпляр
chrome-devtools-mcp (`--autoConnect`, версия закреплена в
`services/chrome-devtools-shared/package-lock.json`). Служба раздаёт его всем
агентам через `mcp-proxy` 0.15.0 по MCP Streamable HTTP на `127.0.0.1:8766/mcp`.
В `~/.codex/config.toml` таблица `[mcp_servers.chrome-devtools]` заменяется на
`url = "http://127.0.0.1:8766/mcp"`. Остальные строки конфигурации не трогаются,
секретов в шаблоне нет. Итог: одно «Allow» после запуска Chrome или перезапуска
службы. Последующие подключения агентов идут без диалога (проверено: 5 новых
клиентов, в том числе 2 параллельных, по 0,1 с, без диалога).
`--allow-unrestricted-paths` возвращает агентам запись скриншотов и файлов вне
временного каталога: через прокси MCP roots не передаются.

**Файлы.** Исходники — `services/chrome-devtools-shared/` (`package.json`, lock,
`run.sh.template`, `launchd.plist.template`, `codex.toml.template`). Установщик —
`scripts/chrome_devtools_shared.py`. На машине: `~/.local/share/chrome-devtools-mcp-shared/`
(служба, `backup/` с копиями `config.toml` и прежней записью chrome-devtools),
`~/Library/LaunchAgents/dev.bb-config.chrome-devtools-mcp-shared.plist`,
лог `~/Library/Logs/chrome-devtools-mcp-shared.log`.

**Установка и восстановление** (на Mac под пользователем, запускающим Codex;
нужны Node.js ≥ 20.19 и uv):

```
python3 scripts/chrome_devtools_shared.py --apply   # идемпотентно
python3 scripts/chrome_devtools_shared.py --check   # Chrome не трогает, диалога нет
```

Один раз в Chrome включить `chrome://inspect/#remote-debugging`, если ещё не
включено. При первом обращении агента нажать «Allow». Уже открытые сессии Codex
переходят на общую службу после перезапуска. Если вручную созданный
LaunchAgent запускает тот же `run.sh` под другой меткой, `--apply` переносит его,
и Chrome один раз спросит «Allow».

**Откат:** `python3 scripts/chrome_devtools_shared.py --remove`. Скрипт снимает
службу и возвращает прежнюю запись Codex из `backup/`. Каталог службы и
mcp-proxy остаются.

**Ограничения.** Выбранная вкладка и состояние MCP общие для всех агентов:
параллельные агенты в браузере могут мешать друг другу. Порт слушает только
127.0.0.1, но любой локальный процесс пользователя получает через него
управление основным Chrome, как и при прежнем autoConnect. Claude Code и
BB browser-automation этой настройкой не затрагиваются. Запасные пути — Playwright
MCP `--extension` и AppleScript `execute javascript`.

**Состояние у автора.** Служба поставлена вручную до оформления, под
другой меткой. `--check` проходит и сообщает о прежней метке. Перенос выполнит
`--apply` при удобном перезапуске (одно «Allow»).

## Мост telegram-projects 0.9.8: итог делегированной задачи (18 ноября 2026)

Исправлена потеря итога делегированной из Telegram задачи: если исполнитель сам запускал вспомогательные треды, их уведомления о завершении попадали в его текущий ход и снимали с хода маршрут ответа, итог не возвращался в Telegram. Теперь такие уведомления и сообщения координатора не меняют адресата хода, а ход со смешанными поручениями явно передаётся координатору с пометкой. Источник: тег v0.9.8 (коммит e05dd1f) в ветке personal-assistant репозитория ainurminibaev/bb-plugin-telegram-projects; установка штатная: `bb plugin update telegram-projects --yes` (источник git semver ^0.9.1-personal.24, токен бота и привязки чатов сохраняются). Откат без удаления плагина: штатное обновление сам откатывает неудачную активацию; при регрессии после активации — опубликовать в той же ветке исправление с тегом v0.9.9 (например, revert e05dd1f) и выполнить то же обновление. `bb plugin remove` не использовать: он удаляет токен бота и привязки.
