# Бесшовное продолжение работы агентов при исчерпании лимитов подписок

Ресёрч от 27.11.2026, BB 0.50.1. Только чтение: ничего не устанавливалось, маршруты Claude, аккаунты и токены не менялись.

Обозначения: **[проверено]** — факт прочитан в первоисточнике (документация, код, issue); **[вторичный]** — пересказ в блоге, новости или сниппете; **[предположение]** — вывод автора отчёта. В отчёте нет имён машин и аккаунтов: «хаб» — основной сервер BB, «Mac» — ноутбук-исполнитель.

## Кратко

**Рекомендация.** Делать «Мульти-аккаунт» по топологии «хаб»: собственный провайдер BB только на сервере. Он выбирает маршрут на каждом ходе:

- Основной аккаунт Claude хаба работает локально в нативном `claude` со всеми его инструментами.
- Аккаунт на Mac используется как «удалённый мозг». На Mac запускается нативный `claude` со своим логином и выключенными встроенными инструментами. Все файловые и shell-операции он выполняет на хабе через MCP-инструменты поверх `bb file` и `bb terminal`.
- Codex подключается только после подтверждения владельца.

Транспорт и инструменты уже есть в экспериментальном `claude-origin-failover`, поэтому ядро роутера стоит строить из него. Сначала через подмену исполняемого файла штатного провайдера Claude Code (так работает сейчас), затем обернуть в свой провайдер со списком моделей «Авто / Opus 5.5 / Fable 5.2…».

**Не подходят:**

- API-прослойка (шим Messages API → `claude -p`) прямо попадает под новую строку AUP Anthropic про proxy через потребительские подписки, теряет prompt cache и нативные tool calls.
- Пулы и переключатели аккаунтов (Account Pooler, claude-swap, CLIProxyAPI) нарушают ограничение 1.
- Сетевые ФС под агентом: медленно и опасно при обрывах.

**Главный нерешённый риск — правовой.** Свои несколько подписок иметь можно. Но автоматическое переключение между ними ради продолжения работы может быть истолковано как обход лимитов: у Anthropic это общая формулировка, у OpenAI прямой запрет «circumvent any rate limits», на HN описан бан за авторотацию. Это решение владельца, см. «Вопросы».

## 1. Постановка и ограничения

- Каскад (после уточнения владельца): 1) Claude Max 20 на хабе → 2) Claude на Mac → 3) Codex, только с подтверждением владельца. «Русский Gemini» из каскада убран.
- Когда приоритетный аккаунт освобождается после сброса окна, работа сама возвращается на него.
- Ограничение 1: аккаунт логически не покидает свою машину. Токен не копируется, IP и MAC не меняются.
- Ограничение 2: только нативные CLI. Подписку нельзя подставлять в сторонний harness.
- Ограничение 3: CLI запускается на машине своего аккаунта, файлы проекта остаются на хабе. Нужно переживать обрывы, не терять данные и почти не нагружать машины.
- Топология «хаб» (уточнение владельца): роутер ставится только на основном сервере, треды с каскадом запускаются там. Треды, запущенные на других машинах, не переключаются.
- Критерий владельца — «как молоток»: надёжно, на своей машине, нативный CLI, без подмены и переноса логина.

### 2.2. Штатные механизмы самих CLI

- **Claude Code 2.1.234+, авто-продолжение** [проверено] ([interactive-mode](https://code.claude.com/docs/en/interactive-mode), [#13354](https://github.com/anthropics/claude-code/issues/13354) закрыт как completed). После сброса лимита сессия ждёт и продолжает сама: до 3 раз подряд, не дальше 24 ч. Это ожидание того же аккаунта, а не переключение.
- **`--fallback-model` у Claude** [проверено] ([cli-reference](https://code.claude.com/docs/en/cli-reference)) срабатывает при перегрузке, не при исчерпании лимита. Окна 5 ч и недели общие для моделей. Модельное окно (например, Opus) обходится другой моделью ([costs](https://code.claude.com/docs/en/costs)).
- **Statusline Claude** [проверено] ([statusline](https://code.claude.com/docs/en/statusline)) получает `rate_limits.five_hour/seven_day` (`used_percentage`, `resets_at`). BB читает те же окна через `system.usageLimits`.
- **Codex** [проверено]. Авто-продолжения нет ([#21073](https://github.com/openai/codex/issues/21073) открыт). Есть `codex exec resume`. С 0.168 resume показывает треды только текущего аккаунта, флаг `cli_resume_account_check` готовится запретить resume чужого ([PR #58918](https://github.com/openai/codex/pull/58918)).
- **Codex `/import`** [проверено] подхватывает сессию Claude Code на той же машине; на больших сессиях есть баг ([#34656](https://github.com/openai/codex/issues/34656)).

### 2.4. Что пишут люди

Ни один CLI не умеет продолжить ту же сессию другим аккаунтом на другой машине. Все известные решения сводятся к одному из трёх вариантов:

- ждать сброса;
- сменить модель того же аккаунта;
- пересказать контекст в новой сессии.

Самые показательные ссылки:

1. [anthropics/claude-code#13354](https://github.com/anthropics/claude-code/issues/13354). Главный запрос сообщества (+212) закрыт: появилось нативное «Continue automatically at usage limit». Это ожидание, а не смена аккаунта.
2. [HN 47082232, бан за claude-nonstop](https://news.ycombinator.com/item?id=47082232). Прямое свидетельство: авторотация аккаунтов ради лимита закончилась баном.
3. [Ask HN 49904074](https://news.ycombinator.com/item?id=49904074). Ровно наш вопрос «не терять контекст при смене агента». Массового решения нет; на практике пишут handoff-файл на хуках.
4. [openai/codex#21073](https://github.com/openai/codex/issues/21073). Самый популярный запрос авто-резюма в Codex (+95), ответа нет.
5. [Codex PR #58918](https://github.com/openai/codex/pull/58918). OpenAI привязывает треды к аккаунту, приём «тот же тред, другой логин» отмирает.
6. [sanecode: continue the same conversation in another account](https://sanecode.co/blog/claude-usage-limit-switch-account/) (26.11.2026). Самое подробное описание `/login` + `--continue` и `CLAUDE_CONFIG_DIR` + `--resume <path>` с разбором ToS. Работает только когда оба логина на одной машине, поэтому критерию не соответствует.
7. [get-bb/bb#5916](https://github.com/get-bb/bb/issues/5916). Запрос «перенести тред BB на другую машину». Прототип в форке переносит нативную сессию чанками с sha256, не влит.
8. [get-bb/bb#7966](https://github.com/get-bb/bb/issues/7966) и [#5552](https://github.com/get-bb/bb/issues/5552). «Продолжить упёршийся в лимит тред на запасном провайдере»: прототипы создают новый тред или передают ход в Handoff, не влиты.
9. [Show HN: Hydra](https://news.ycombinator.com/item?id=47851935). Типичная обёртка: ловит лимит и передаёт контекст другому CLI, но в новой сессии.
10. [Hermes issue 48320](https://github.com/NousResearch/hermes-agent/issues/48320). Опыт «`claude -p` как модельный бэкенд»: «does not return structured tool calls… regex-extract responses… just unreliable».

### 2.5. BB: почему тред привязан к машине и модели

- Тред живёт в environment, environment принадлежит host-daemon одной машины: «project sources and environments retain the host boundary» [проверено] ([system-overview](https://github.com/get-bb/bb/blob/main/docs/system-overview.md)). Нативная сессия провайдера — файл на той же машине. Отсюда запрет `bb thread fork` на другую машину [проверено, `bb guide threads`].
- Провайдер фиксируется при создании треда: «A thread's provider is fixed when the thread is created» [проверено] ([#7938](https://github.com/get-bb/bb/issues/7938)). Модель того же провайдера менять можно.
- Штатного переноса существующего треда на другую машину или к другому провайдеру нет. Handoff и плагин [vburojevic/bb-plugin-handoff](https://github.com/vburojevic/bb-plugin-handoff) создают **новый** тред; незакоммиченное переносится патчем.
- Встроенный Account Pooler собирает токены на сервере и пускает трафик через прокси. Для нас **неподходящий** (ограничение 1).

| Вариант | Мелкие файлы (git status, rg) | Обрывы связи | Потеря данных | Ресурсы | macOS / Linux | Вывод |

| sshfs (macFUSE/FUSE-T) | плохо: 2–3 RTT на файл, git status ~30 с [вторичный] | I/O блокируется; Claude Code может зависнуть навсегда, resume тоже ([claude-code#110768](https://github.com/anthropics/claude-code/issues/110768)) [проверено] | низкая, но запись может оборваться посередине | низкие | macOS: только FSKit с macOS 26 или kext | **Не подходит** |

| JuiceFS | плохо для git [вторичный] ([discussion](https://github.com/juicedata/juicefs/discussions/3929)) | зависит от Redis/S3 | средний | высокие | да / да | Не подходит |
| Mutagen two-way-safe, `.git` только на хабе | локальная скорость | работает офлайн, досинхронизирует | низкий: конфликты не перезаписываются; окно до `flush` | низкие | да / да | Подходит, если нужны встроенные Read/Edit; Bash остаётся проблемой |
| Syncthing / Unison / lsyncd | локальная, задержка ≥1–10 с | хорошо | конфликт-файлы | средние | lsyncd на macOS нет | Хуже Mutagen |
| **Инструменты на хабе через MCP** (`--tools ""` + MCP) | хорошо: rg и git выполняются на хабе, по сети идёт только вывод | stdio-MCP сам не переподключается ([#43177](https://github.com/anthropics/claude-code/issues/43177)); HTTP-MCP делает 5 попыток | низкий: данные только на хабе | низкие при долгоживущем сервере | да / да | **Рекомендуется** |
| Codex `exec-server` (агент на B, fs/process на A) | хорошо | Noise-relay с resume/ack | низкий | низкие | да / да | Хорошо для Codex, но experimental ([README](https://github.com/openai/codex/blob/main/codex-rs/exec-server/README.md)) |
| Claude Desktop SSH sessions | всё на A | задача живёт на A, вывод в буфере 16 МиБ | низкий | ~1 ГБ на A | GUI | **Не подходит:** процесс на A ходит в API со входом аккаунта B, то есть запросы идут с IP другой машины ([desktop](https://code.claude.com/docs/en/desktop)) |

Ключевой довод в пользу MCP-инструментов [предположение]: при любой файловой синхронизации команды `Bash` выполняются на исполнителе. Там другие зависимости, службы, git-доступы и BB CLI. При проксировании инструментов команда выполняется там, где живёт тред. Открытых замеров `rg`/`git status` на 10k файлов нет; нужен свой замер (раздел E).

## 4. C. Непрерывность треда: что уже есть

### 4.1. Штатно в BB (проверено по справке BB 0.50.1 и навыкам)

| Механизм | Что даёт | Чего не даёт |
|---|---|---|
| `provider-retry` | Повтор хода вскоре после сброса окна, со случайным разбросом; ≤4 повторов; `maximumWait` 6 ч | Не меняет машину, аккаунт и модель |
| `bb thread fork` | Клон нативной сессии | Только на той же машине |
| Handoff | Новый тред с транскриптом на другом провайдере или машине | Новый тред |
| `bb thread spawn --provider --model --machine` | Подтред сразу на нужной машине | Существующий тред не переносит |
| `system.usageLimits({hostId})` | Окна лимита по машине и провайдеру: `usedPercent`, `resetsAt`, `planLabel`, `accountEmail` | — |
| `bb.providers.experimental_contributeEnv(providerId, resolver)` | Переменные окружения штатному провайдеру на каждом start/resume/fork/turn; контекст `threadId`, `projectId`, `hostId` | Таймаут резолвера 5 с |
| `bb.providers.register` + provider bridge | Свой провайдер: `model/list`, `provider/usage`, `thread/start|resume`, `turn/start`, поток `thread/delta`, уведомления `provider/rateLimits/updated`, `provider/modelFallback` | Мост работает на машине треда; встроенные мосты Claude и Codex как библиотека не экспортируются [предположение: в SDK 0.6.132 их нет] |
| `bb file read/write --host --root --expected-sha256`, `bb terminal run|create --machine` | Файлы и команды на любой машине через сервер BB, без SSH и токенов | Каждый вызов CLI — отдельный процесс node |

### 4.2. limit-guard (наш, 0.9.2)

Что уже умеет:

- каждые 2 минуты читает `usageLimits` по машинам и считает темп расхода;
- шлёт в идущий ход `[limit-guard]`;
- делает снимки незаконченной работы в `refs/wip/bb/<env>`;
- держит «продолжай после сброса» в очереди;
- различает пороги по тарифам и приоритеты тредов, подтреды их наследуют.

Не умеет переключать маршрут. Для роутера это готовый монитор и источник порогов.

### 4.3. claude-origin-failover (экспериментальный, ветка `fix/origin-failover-live-usage`)

По коду он уже реализует схему «нативный CLI на другой машине как мозг, тред и файлы на исходной»:

1. `server.ts` через `experimental_contributeEnv("claude-code")` подменяет `BB_CLAUDE_CODE_EXECUTABLE` для выбранного треда на `bin/claude-origin-relay.mjs`. Штатный мост Claude остаётся, ядро не правится.
2. Без маршрута relay просто запускает локальный `claude`.
3. С маршрутом relay открывает терминал BB на резервной машине и запускает там нативный `claude` со своим логином. Флаги принудительные: `--tools=` (встроенные инструменты выключены), `--setting-sources=`, `--strict-mcp-config`, без автопамяти. Аргументы и управляющие сообщения пропускаются по белому списку. Транспорт: «BB terminals only… No ssh, no tokens».
4. Инструменты на резерве — MCP `workspace` (`bin/workspace-tools.cjs`): `git_status`, `read_file`, `edit_file` (запись только при совпадении SHA-256 прошлого чтения), `bb_cli` (команда BB в терминале исходного треда). Секретные пути запрещены.
5. История передаётся текстом видимых сообщений, страницами и с контрольной суммой (`probe-history.mjs`). Возврат на исходную машину — `probe-return.mjs`.
6. Лимит распознаётся по нативному `rate_limit_event` (`five_hour`/`seven_day`, `resetsAt`) в `quota-window.mjs`. Каркас маршрутизации `dispatch.mjs`/`routing.mjs` уже есть: `nextRoute`, запоминание исчерпанных окон, повтор только при отказе до исполнения.
7. Проверено: текстовый relay между двумя машинами в обе стороны, повтор опроса терминала при HTTP 504. Не сделано: полный набор инструментов в рабочем режиме, штатное ожидание лимита, авторотация.

Чего не хватает для работы «как молоток»:

- `grep`/`glob`, `bash` с учётом режима прав треда, `edit` в семантике str_replace (сейчас файл переписывается целиком, лимит 128 КиБ);
- долгоживущий MCP-сервер вместо процесса `bb` на каждый вызов;
- HTTP-MCP, чтобы сервер сам переподключался.

### 4.4. Перенос нативной сессии

- **Claude**: `~/.claude/projects/<закодированный cwd>/<id>.jsonl`, `--resume <путь>`. С v2.1.234 `CLAUDE_CODE_PROJECT_DIR_NAME` снимает зависимость от абсолютного пути. В jsonl нет токенов, но формат «changes between versions» [проверено] ([sessions](https://code.claude.com/docs/en/sessions), [agent-sdk/sessions](https://code.claude.com/docs/en/agent-sdk/sessions)).
- **Codex**: один rollout-файл `~/.codex/sessions/YYYY/MM/DD/…jsonl`, без SQLite [вторичный]. Resume чужого аккаунта скоро будет запрещён (2.2).
- **Между провайдерами** надёжнее сводка плюс состояние git, чем конвертация транскриптов [предположение по [sessions](https://code.claude.com/docs/en/sessions) и практике].

Вывод для топологии «хаб»: переносить файлы сессий на исполнитель не нужно. Сессия исполнителя временная, в изолированном каталоге. Источник истины — таймлайн треда BB на хабе.

## 5. D. Архитектура

### 5.1. Варианты

| # | Вариант | Как работает | Огр. 1 | Огр. 2 | Правовой риск | Надёжность | Объём работ |
|---|---|---|---|---|---|---|---|
| 0 | **Ждать и передавать** (сейчас) | `provider-retry` ждёт сброса. При долгом ожидании — handoff в новый тред на другой машине или к Codex | да | да | низкий | высокая | 0 |
| 1 | **Сетевая ФС или синхронизация** | Тред переезжает на исполнитель (handoff или перенос jsonl), файлы подключены через sshfs/NFS или Mutagen | да | да | низкий (свой CLI, свой логин) | низкая (ФС) или средняя (Mutagen; Bash на чужой машине) | средний |
| 2 | **API-прослойка** | Claude Code на хабе с `ANTHROPIC_BASE_URL` на шим; шим на каждый шаг вызывает `claude -p` или `codex exec` на исполнителе, ответ превращает в `tool_use` | формально да | **нет**: подписка становится моделью для чужого tool-loop | **высокий**: AUP «proxy… route requests through consumer subscriptions… misrepresent the product or client»; Hermes и OpenClaw-подобные обёртки упирались именно в это | низкая: нет структурных tool calls, разбор текстом ненадёжен | средний |
| 3 | **Удалённый мозг** (развитие claude-origin-failover) | Тред остаётся на хабе. Штатный провайдер Claude Code; на ход с маршрутом исполнитель запускает нативный `claude` со своим логином, без встроенных инструментов, с MCP-инструментами хаба | да | да: агентный цикл и tool calls — сам Claude Code | средний, см. 5.4 | средняя → высокая после доработки инструментов | средний (основа есть) |
| 4 | **Свой провайдер «Мульти-аккаунт»** на хабе | Провайдер в пикере с моделями «Авто / Opus 5.5 / Fable 5.2…». На каждом ходе выбирает аккаунт: локальный `claude` хаба с нативными инструментами, удалённый мозг на Mac или Codex после подтверждения | да | да | как у 3 | высокая при хорошем мосте | большой: свой мост и транслятор потока Claude и Codex |

**Почему API-прослойка отвергнута, даже если её назвать «личной»:**

- **Правила.** Строка AUP про proxy не делает исключения для личного использования. Фактический harness — шим плюс Claude Code хаба без подписки. `claude -p` на исполнителе служит модельным бэкендом [вывод].
- **Кэш.** Префиксный кэш держится только при байт-в-байт одинаковом префиксе ([prompt-caching](https://code.claude.com/docs/en/prompt-caching)) [проверено]. Шим, собирающий каждый шаг заново, почти гарантированно теряет его. По независимым замерам cache read в ~57 раз дешевле некэшированного input для окна подписки, холодный ход на 800k контекста стоит ~23 тёплых ([techbytes](https://techbytes.app/posts/what-a-week-of-claude-code-holds-the-usage-meter/)) [вторичный]. Окно исполнителя будет таять на порядок быстрее.
- **Tool calls.** `claude -p` не возвращает структурные вызовы чужих инструментов: определения нужно вшивать в промпт и разбирать регулярками ([Hermes 48320](https://github.com/NousResearch/hermes-agent/issues/48320)) [вторичный]. Теряются параллельные вызовы, строгие схемы, interleaved thinking. Модель видит ещё и собственные инструменты Claude Code.

**Чем вариант 3 отличается от прослойки:** в нём нет «запросов к модели» от чужого клиента. На исполнителе работает целый Claude Code со своим агентным циклом, системным промптом и нативными `tool_use`; MCP — официальный способ дать ему инструменты. Кэш сохраняется: пока маршрут не меняется, сессия на исполнителе живёт и наращивает тот же префикс. Это тот же класс использования, что и сам BB, claude-squad или vibe-kanban, только MCP-сервер находится на другой машине.

### 5.2. Топология «хаб»

Что упрощает:

- **Один роутер, одно состояние лимитов.** Сервер BB уже опрашивает `usageLimits` всех машин (limit-guard, thread-account-usage). Второй монитор не нужен.
- **Файлы проекта только на хабе.** Синхронизации нет вообще, ни в одну сторону: исполнитель читает и пишет через MCP-инструменты. Нет конфликтов, нет копий кода на ноутбуке.
- **Хаб = сервер BB.** Инструмент исполнителя идёт Mac → сервер → локальный демон, один сетевой переход. Сервер и так единая точка (база, треды, очередь), поэтому новой точки отказа хаб не добавляет [вывод из `bb guide machines`].
- **Нативная сессия основного аккаунта** лежит на хабе и продолжается `--resume` без переноса файлов.
- **Codex на хабе** работает локально и нативно, с файлами под рукой.

Риски:

- **Единая точка отказа.** Хаб недоступен — не работает ничего, но это уже так для BB в целом. Добавить бэкап сервера (есть `docs/server-backups.md`) и не держать на хабе единственную копию незапушенного кода (снимки limit-guard).
- **Mac как исполнитель спит, уходит в офлайн, меняет сеть.** Роутер выбирает его, только если машина на связи (`hosts` connection status) и недавно отвечала. При обрыве посреди хода — повтор на хабе после сброса или ожидание. Каскад не должен зависеть от закрытой крышки.
- **Задержка.** Каждый вызов инструмента — сетевой круг плюс, в текущем коде, запуск процесса `bb` (~1 с; Browser Relay ~0,9 с на вызов). На ход с сотней вызовов набегают минуты. Нужен долгоживущий MCP-сервер с SDK-соединением вместо процесса на вызов.
- **Безопасность.** Модель на Mac исполняет команды на хабе от имени пользователя BB. `bash`-инструмент обязан соблюдать режим прав треда и лимит машины, а не обходить их через `bb terminal run`.
- **Нагрузка на основной аккаунт.** Все треды с каскадом сначала едят аккаунт хаба, а Mac берёт только перелив. Это и есть приоритет, но фоновые подтреды стоит пускать на Mac только по явному правилу (5.5).

### 5.3. Рекомендация: вариант 4 на ядре варианта 3, поэтапно

Ядро общее для обоих:

- политика маршрута;
- транспорт relay;
- MCP-инструменты хаба;
- перенос истории.

Этап 1 — быстрая польза без своего моста. Этап 2 — интерфейс, который хочет владелец.

**Этап 1. Роутер на штатном Claude Code** (развитие claude-origin-failover):

- Резолвер `contributeEnv("claude-code")` на каждом ходе решает: хаб (подмены нет, нативный `claude` со всеми инструментами) или Mac (relay). Решение по `usageLimits` хаба и Mac плюс порогам limit-guard.
- Режим «Авто» для треда — переключатель плагина, наследуется подтредами, как приоритет limit-guard.
- Инструменты relay: `read`, `write`, `edit` (str_replace с проверкой версии), `grep`/`glob` (rg на хабе), `bash` (через терминал треда, с учётом режима прав), `git_status`, `bb_cli`. Один долгоживущий HTTP-MCP на время хода.
- Codex на этапе 1 — только через подтверждение и handoff в новый Codex-тред на хабе.

**Этап 2. Провайдер «Мульти-аккаунт»** (`bb.providers.register`):

- **Список моделей.** Мост отвечает на `model/list` динамически: параметры `cwd`, `envVars`, `selectedModel`; BB кэширует список на машине и обновляет его в фоне, если он старше минуты [проверено: схема `modelListParamsSchema` в SDK 0.6.132, `bb guide providers`]. Значит, «Авто», «Opus 5.5», «Fable 5.2» можно отдавать из конфигурации каскада. Пункты недоступных моделей помечать или скрывать с задержкой до минуты.
- **Доступность модели на аккаунте.** Две вещи с сервера плагина:
  - `bb provider models claude-code --machine <машина>` (SDK `providers`) — какие модели видит нативный CLI этого аккаунта;
  - `system.usageLimits({hostId})` — окна 5 ч, недели и модельные, например отдельное окно Fable, которое уже показывает thread-account-usage.

  Модель доступна на аккаунте, если она есть в списке и ни одно применимое окно не выше порога.
- **Подтреды**: `bb thread spawn --provider multi-account --model auto|<модель>`. Оркестратор ничего не знает о машинах.
- **Мост** работает на хабе (провайдер ставится только там). Ход на аккаунте хаба запускает нативный `claude`/`codex` локально, ход на Mac идёт через тот же relay.
- **Главная работа**: собственный транслятор потоков Claude (stream-json) и Codex в `thread/delta`. Встроенные мосты как библиотека не экспортируются [предположение]. До начала этапа 2 надо проверить в `docs/provider-plugin-api.md` репозитория BB, можно ли переиспользовать встроенный мост. Если нет — оценить объём по примеру `examples/plugins/echo-provider`.
- **Состыковка с claude-origin-failover**: его `routing.mjs`/`dispatch.mjs`, relay и `workspace-tools` переходят в общий пакет. На этапе 2 подмена `BB_CLAUDE_CODE_EXECUTABLE` больше не нужна: мост сам запускает CLI.

Почему не сразу этап 2: этап 1 даёт каскад Claude → Claude уже на проверенном механизме, где BB сам рисует ход Claude. Этап 2 нужен ради пикера моделей и Codex внутри того же треда.

### 5.4. Правовая оценка варианта 3/4 [предположение]

| Пункт | Оценка |
|---|---|
| Токен не покидает машину, IP свой | соблюдено: relay не передаёт окружение и файлы авторизации |
| Нативный немодифицированный CLI со своим агентным циклом | соблюдено |
| «proxy… route requests through consumer subscriptions» | Сырые запросы к API не проксируются, работает весь Claude Code. Риск низкий, но формулировка широкая, а практика применения неизвестна |
| «ordinary, individual usage» | соблюдено: один человек, свои задачи |
| **Несколько своих подписок и переключение между ними** | **главный риск.** Прямого запрета нет, но есть общие формулировки про обход ограничений (Anthropic) и прямой запрет «circumvent any rate limits» (OpenAI); есть публичный бан за авторотацию. Смягчение: аккаунты оплачены отдельно, на разных машинах, без подмены логинов, переключение редкое и видно в журнале. Решение за владельцем |

### 5.5. Правила роутера

**Мониторинг:**

- данные `system.usageLimits` по машинам — тот же кэш, что у limit-guard (раз в 2 минуты);
- плюс нативное `rate_limit_event` из потока CLI для мгновенного отказа.

Новых опросов не добавлять (AGENTS.md: фоновые проверки не нагружают сервер).

**Выбор маршрута на каждом ходе:**

- первый аккаунт каскада, у которого машина на связи, модель доступна и окна ниже порогов (5 ч < 90%, неделя < 97%, модельное окно < 97%; пороги из `accountRules` limit-guard);
- маршрут не меняется посреди хода.

**Возврат на приоритетный аккаунт:**

- на границе хода, когда у него прошёл `resetsAt` и окна ниже порога возврата (например, 5 ч < 70%);
- минимальное время на маршруте — 30 минут, чтобы не платить холодным кэшем за переключения туда-обратно.

**Передача контекста:**

- *Хаб → Mac*: сессия на Mac заводится один раз на тред и маршрут и получает историю из таймлайна BB; дальше её продолжает `--resume` на Mac.
- *Mac → хаб*: нативная сессия хаба продолжается `--resume`, недостающие ходы Mac подаются одним сообщением (`probe-return`). Каждое переключение — один холодный ход.

**Codex:**

- шаг каскада «Codex» требует подтверждения владельца: одно сообщение через помощника в Telegram, кнопки «Да для этого треда до сброса Claude» и «Нет, ждать»;
- без ответа — ждать сброса;
- согласие действует на тред и до ближайшего сброса Claude, не навсегда.

**Каскад выбранной модели исчерпан.** Значение по умолчанию:

- если ближайший сброс ≤ `maximumWait` (6 ч) — ждать, строка ожидания в очереди треда как у `provider-retry`, плюс одно уведомление владельцу с кнопкой «Перейти на Авто для этого треда»;
- если ждать дольше — спросить владельца; без ответа — ждать;
- в «Авто» молча не переходить: выбор модели (например, Fable для оркестратора) обычно осознанный, а «Авто» может дойти до Codex.

**Подтреды:**

- наследуют провайдер, модель и приоритет limit-guard;
- `low/background` по умолчанию не уходят на Mac и не доходят до Codex, а ждут сброса (настраивается);
- новые подтреды при исчерпанном хабе стартуют сразу на доступном маршруте.

**Точки опоры на BB** (ядро и каталожные плагины не правятся):

- `providers.register`, `providers.experimental_contributeEnv`;
- `system.usageLimits`, `hosts.list/get`, `providers` (модели);
- `files.read/write`, терминалы;
- `events.on("turn.failed"|"thread.idle")`;
- `provider-retry` `decision.get` (не дублировать его повтор);
- limit-guard (пороги, снимки, «продолжай после сброса»).

## 6. E. План тестов

Все опыты — в отдельном синтетическом треде с отдельным тестовым проектом на хабе; рабочие треды помощников не трогать. Маршрут Claude и тест с переходом на другой IP требуют отдельного поручения владельца (AGENTS.md).

| # | Что проверяем | Где | Критерий успеха |
|---|---|---|---|
| 1 | Замер транспорта | хаб ↔ Mac | Задержка и CPU: `bb file read`, `bb terminal run rg`, `git status` на репозитории ~10k файлов. Цель: p50 < 1,5 с на вызов, < 0,5 с с долгоживущим MCP; CPU исполнителя < 5% в простое |
| 2 | Инструменты relay | синтетический тред | Набор задач «найти → прочитать → исправить → прогнать тест» проходит на Mac-маршруте. Все изменения на хабе, на Mac в изолированном каталоге нет файлов проекта, конфликт версий при `edit` ловится |
| 3 | Аудит границ | журнал relay, `ps`/окружение на Mac | Ни одного файла авторизации, переменной окружения хаба или токена не уходит. Процесс `claude` на Mac — штатный бинарник со своим логином |
| 4 | Обрыв связи | Mac: отключить сеть и усыпить посреди хода (`tests/relay_disconnect.py`) | Ход завершается штатной ошибкой или повтором, нет обрезанного потока и полузаписанных файлов, тред не висит дольше таймаута |
| 5 | Лимит и возврат | живой прогон `live-once` | Отказ по окну хаба → следующий ход на Mac → после `resetsAt` возврат на хаб в пределах одного хода. Проверка контекста: слово, придуманное на Mac, хаб повторяет |
| 6 | Подтреды | оркестратор в синтетическом треде | `spawn --model auto` стартует на доступном маршруте; `background` не уходит на Mac |
| 7 | Подтверждение Codex | сухой прогон | Без ответа владельца Codex не запускается; согласие действует только на свой тред и срок |
| 8 | Теневой режим | один реальный тред помощника, сутки | Роутер только пишет решения в журнал, ничего не переключает. Решения совпадают с ожидаемыми, лишних опросов нет |
| 9 | Кэш и расход | синтетический тред, 20 ходов на одном маршруте и с переключениями | `cache_read` растёт на стабильном маршруте; холодный ход только при переключении |

Порядок: 1 → 3 → 2 → 4 → 5 → 9 → 6 → 7 → 8. Тесты 1–4 решают, жизнеспособен ли транспорт; без них этап 2 не начинать.

## 7. Главные риски

1. **Правовой: ротация собственных подписок** (5.4). Единственный пункт, который не снимается техникой.
2. **Качество работы без встроенных инструментов** на Mac-маршруте: у MCP-инструментов нет Edit-семантики Claude Code, нет чекпоинтов и diff-интерфейса [предположение]. Проверяется тестом 2.
3. **Задержка и обрывы** Mac-исполнителя (тесты 1 и 4).
4. **Хрупкость к обновлениям.** Форматы stream-json и сессий меняются; `experimental_*` API BB тоже. Нужны контрактные тесты и откат к штатному поведению при сбое (AGENTS.md).
5. **Объём этапа 2**: свой транслятор потоков Claude и Codex.

## 8. Вопросы к владельцу

1. **Риск ротации.** Готовы ли вы автоматически переключаться между своими двумя Claude-подписками, зная про общий запрет «обхода ограничений» и известный бан за авторотацию? Оба аккаунта оформлены на вас и оплачены отдельно?
2. **Тариф хаба.** Max 20x переименован в Ultra; у verified Ultra нет пятичасового окна [вторичный]. Подтвердите, какие окна сейчас видит аккаунт хаба: от этого зависят пороги.
3. **Codex.** Где залогинен Codex, который можно брать? Устраивает ли форма согласия «на тред до сброса Claude»?
4. **Исчерпанный каскад модели.** Принимаете значение по умолчанию «ждать до 6 ч, потом спросить, в Авто без согласия не переходить»?
5. **Фоновые подтреды.** Можно ли им расходовать аккаунт Mac, или Mac только для `normal`?
6. **Mac как исполнитель.** Насколько он бывает на связи (крышка, сеть)? Если часто в офлайне, Claude на Mac — ненадёжная ступень, и Codex на хабе может оказаться практичнее второй ступенью.
