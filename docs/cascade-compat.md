# Совместимость плагинов с «Каскадом подписок»

Тред каскада имеет `providerId` `agentcli-subscriptions-cascade`. Плагины,
которые раньше решали по `claude-code`/`codex` или по машине окружения треда,
читают **паспорт треда**: RPC `agentcli-subscriptions-cascade.threadStatus({ threadId })`
→ `{ cascade: true, profileId, step: { hostId, providerId, model, accountKey, kind }, anchorHostId, syncMode, path, freshCopyHostId }`.

Правила чтения (`cascade-passport.ts`, одинаковая копия в каждом плагине):

- каскад спрашивается только для его тредов; треды `claude-code`/`codex` идут
  старым путём без единого вызова;
- не установлен, выключен, не ответил за 3 с или ответил не по контракту —
  `null`, плагин ведёт себя как без каскада;
- неизвестные поля игнорируются; неизвестный провайдер ступени — ступени нет;
  неизвестный `kind` считается шлюзом (без квоты подписки);
- папка треда: `freshCopyHostId` → `anchorHostId` → машина ступени, путь `path`.

## provider-retry (встроенный, не правим)

Плагин реагирует только на неудачные ходы провайдеров `claude-code` и `codex`
и ставит в очередь повтор после открытия окна подписки.

- **Путь B (свой провайдер, текущий план).** Ходы треда каскада идут под
  `agentcli-subscriptions-cascade` — provider-retry их не видит и повторов не
  ставит. Двойной работы нет; ожидание сброса, когда все ступени исчерпаны, —
  забота каскада (`exhaustedWaitHours`). Патч через Keeper **не нужен**.
- **Путь A (relay внутри штатного провайдера).** `providerId` остаётся
  `claude-code`/`codex`, и упор в лимит провайдера даст повтор «Please continue»
  после сброса, хотя каскад уже перевёл бы тред на другую ступень. Решение без
  Keeper: каскад не выпускает ошибку лимита наружу (переключает ступень до
  закрытия хода) либо после `decision.get` отменяет повтор
  (`bb provider-retry cancel <thread>`). Keeper — только если этого окажется мало.
- limit-guard при упоре треда каскада в лимит не уведомляет и не предлагает
  handoff (тред не из списка провайдеров), снимок папки делается как у всех.

## Предложение для каскада: «Перевести в каскад»

Массовый handoff тредов в каскад, прежде всего упёршихся в лимит.

- CLI: `bb subscriptions-cascade adopt [--stuck] [--thread <id>…] [--project <id>] [--profile <id>] [--dry-run]`.
  `--stuck` берёт треды из `bb limit-guard stuck --json` (упёрлись в лимит и
  ждут) или, без limit-guard, треды в `error` с категорией `rate-limit`.
- Для каждого треда: штатный handoff (`bb handoff <id> --to agentcli-subscriptions-cascade`)
  с тем же проектом и окружением, профиль каскада по умолчанию или `--profile`.
  Исходный тред: отменить ждущий повтор provider-retry (`bb provider-retry cancel`),
  чтобы два агента не делали одно и то же, и пометить в limit-guard как переданный
  (он уже снимает повтор у источника по `handoff.started`).
- Кнопка в карточке limit-guard «Лимит … ждёт» и в боковой панели каскада:
  «Перевести в каскад (N)» со списком тредов и галочками; `--dry-run` показывает
  план: тред → первая готовая ступень (через `selectStep`), без запуска.
- Ограничения: подтреды переводятся вместе с родителем только при
  `subthreadsUseOtherMachines`; тред с идущим ходом пропускается; повторный
  запуск безопасен (уже переведённые пропускаются по `originPluginId`/метке).
