# Зашифрованные резервные копии

## Личная конфигурация

`python3 scripts/private_backup.py` упаковывает `.local/config/` и `.local/docs/`
и шифрует архив через age. Получатель берётся из
`.local/config/backup-encryption.json` (`recipient`) либо `BB_BACKUP_RECIPIENT`.
Без получателя скрипт отказывается создавать архив. Закрытый ключ не требуется
для шифрования и никогда не хранится в Git. Выходной файл имеет права 0600.

Архив появляется в `.local/backups/config/`. Обязательно скопируйте его на другую
машину или внешний носитель; локальная копия не защищает от потери сервера.
Старую историю `.local/privacy-migration/` скрипт намеренно не включает.

Восстановление: расшифруйте архив на доверенной машине командой
`age --decrypt -i /private/path/identity.txt -o /private/path/config.tar.gz archive.age`,
просмотрите `tar -tzf /private/path/config.tar.gz`, затем распакуйте его в корень
checkout. Ручная копия содержит `.local/config/` и `.local/docs/`.
Автоматическая ежедневная копия дополнительно содержит `source/` с текущими
исходниками bb-config, включая незакоммиченные изменения. При восстановлении
скопируйте содержимое `source/` в checkout, а `.local/` — в его корень.
Не публикуйте расшифрованный архив и удалите его после восстановления.
После возвращения личных файлов запустите `python3 scripts/restore.py` и проверьте
план, затем примените его с `--plugins --apply` на машине сервера.

## Экспорт BB

`scripts/server_backup.py` использует штатный экспорт BB, проверяет manifest,
шифрует архив и доставляет его через BB на указанную машину. Параметры доставки
хранятся в `.local/config/backup-delivery.json` или передаются флагами.
Получатель — `.local/config/backup-encryption.json` или `BB_BACKUP_RECIPIENT`.
Восстановление ключа на macOS поддерживает `scripts/backup_keys.py` через Keychain.
Ключ нельзя передавать в чат, Git или аргументы shell.

Архив экспорта BB не включает рабочие каталоги проектов и `.local/config/` этого
репозитория. Для них необходим отдельный зашифрованный архив, описанный выше.

## Источники плагинов и журнал релизов

У работающего BB часть плагинов может использовать `.local/updates/releases/`.
Эти каталоги можно заново получить из проверенных тегов. Экспорт BB содержит
данные плагинов, но их рабочие исходники из каталогов релизов в экспорт не входят.

Если важно перенести историю проверок, сохраните `journal.json` из
`.local/updates/` в закрытой резервной копии. При переезде перенесите сам журнал.
Исходники локальных плагинов зарегистрируйте из чистой копии соответствующего
релиза заново. Для полной установки используйте `restore.py` с вашей собственной
приватной конфигурацией и предварительно проверьте его план. Сохраните связь
постоянного checkout с проектом в BB. Обновление через BB снова создаст
служебные каталоги на новой машине. Если журнала нет, сначала проверьте
фактическое состояние шагов. `baseline` подходит только для установки, которая
уже целиком проверена на версии, указанной в команде.

## Автоматическая схема
Одна автоматизация запускает `scripts/daily_backup.py` каждые 30 минут.
Это проверка состояния, а не создание нового полного архива каждые полчаса.

- Личная конфигурация: раз в сутки после 05:00 МСК обновляются снимок настроек
  и приватный манифест расписаний, затем `.local/config/` и `.local/docs/`
  вместе с текущими исходниками bb-config шифруются и доставляются на указанную
  машину. Хранятся 7 ежедневных копий. Источники берутся из видимых Git файлов
  `scripts/`, `plugins/`, `config/`, `docs/`, `.bb/` и основных инструкций:
  учитываются `.gitignore`, исключаются env-файлы, каталоги авторизации,
  базы, ключевые файлы, `.git/`, `.local/` и `node_modules/`. Это сохраняет
  текущие доработки до коммита; автоматический commit/push не выполняется.
- Полный BB: раз в 7 дней создаётся штатный экспорт, проверяется manifest
  и SHA-256 каждого файла, затем архив шифруется. Хранятся 3 полные копии.
- Доставка: следующий запуск доставляет уже зашифрованный полный архив.
  При отключённом Mac копия остаётся на сервере; следующий tick повторяет
  доставку без нового экспорта. Незавершённая доставка не удаляет прежние копии.

Архивы конфигурации и BB хранятся в одном каталоге назначения, но имеют разные
префиксы и независимое удаление старых копий. Рядом создаётся `restore-tools/`
с инструкцией и тремя исходными модулями восстановления. На Mac с ключом в
Keychain любой из двух архивов расшифровывается и проверяется одной командой:
`python3 restore-tools/backup_keys.py decrypt ARCHIVE.age --output restored.tar.gz`.
Ключ не выводится в чат и не записывается в файлы. Расшифрованный архив
содержит личные данные; удалите его после восстановления.
На сервере конфигурация остаётся
в `.local/backups/config/`, полный BB и служебное состояние — в
`~/.bb-backups/server/`. Рабочие каталоги проектов не включены в эти архивы:
их Git-историю и незакоммиченные файлы нужно резервировать отдельно.

Автоматизация хранит копию входного `daily_backup.py`, а модули загружает из
checkout `BB_CONFIG_ROOT`. Это позволяет сохранять одну актуальную реализацию.
Смена входного скрипта требует `bb automation update <automation-id>
--project <project-id> --script-file scripts/daily_backup.py`.
В окружении задания должны быть `BB_CONFIG_ROOT`, `BB_BACKUP_RECIPIENT`,
`BB_BACKUP_DESTINATION_HOST`, `BB_BACKUP_DESTINATION_DIR`; рабочий каталог —
checkout на сервере. Личные значения сохраняются только в приватном манифесте
`.local/config/automations.json`. `scripts/automation_config.py --apply`
восстанавливает расписание и привязывает `BB_CONFIG_ROOT` к текущему checkout.

Общий лимит запуска — 900 секунд. Ожидание штатного экспорта — 780 секунд:
только его дочернему Node CLI подключается временный preload с Undici из
поставки BB, задающий срок ожидания HTTP-заголовков. Без этого встроенный fetch
обрывает большой экспорт примерно через 5 минут. Исходники приложения,
база и маршруты BB не меняются; при отсутствии bundled Undici экспорт
отказывается запускаться. Проверка архива потоковая, без распаковки и без
повторных поисков по именам; передача идёт блоками по 4 МиБ. Контрольные суммы
проверяются до шифрования, перед отправкой и на принимающей стороне.

Проверки: `python3 -m unittest discover -s scripts -p 'test_*backup*.py'` и
`python3 -m unittest discover -s scripts -p 'test_private_config.py'`.
Ручной запуск всей схемы: `python3 scripts/daily_backup.py`;
немедленная копия настроек и текущих исходников:
`python3 scripts/daily_backup.py --force-config`;
новая полная копия независимо от срока: `python3 scripts/daily_backup.py --force-full`.
После создания полного архива повторный запуск выполнит его доставку.
Проверка восстановления выполнена на принимающем Mac: обе копии расшифрованы
ключом из Keychain, конфигурация и исходники извлечены во временную папку,
полный архив проверен и импортирован через штатный `bb server import` в
отдельный временный каталог. Временные распакованные данные удалены.

Служебное состояние наблюдателей очередей (`MONITOR_STORAGE`, `WATCHDOG_STATE`)
должно находиться вне каталога данных BB, например в
`~/.local/state/bb-automations/`. Экспорт BB проверяет контрольные суммы файлов:
постоянно меняющиеся JSON внутри `plugins/automations/` приводят к
`digest_mismatch`. При переносе скопируйте состояние между завершёнными
запусками и обновите переменные через `bb automation update --env-json`;
передавайте весь прежний словарь с изменённым путём. Старые файлы можно оставить
неизменяемыми. Не отключайте проверку контрольных сумм ради успешного экспорта.

После потери сервера используйте штатный `bb server import` в новую пустую
директорию совместимой версии BB. Не редактируйте базу вручную. Прежний сервер
должен быть остановлен до запуска восстановленной копии. Учётные данные CLI и
рабочие проекты восстанавливаются отдельно. Перенос живого сервера требует
отдельного явного поручения.
