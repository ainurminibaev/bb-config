# Обновления доработок: публикация и применение

Этот документ задаёт порядок применения и публикации. Обновление начинается
на сервере BB и использует служебный checkout закреплённого релиза.

## Что считается обновлением

- Сигнал для пользователей — **опубликованный стабильный GitHub Release** с тегом
  `vX.Y.Z`. Draft, prerelease, тег без релиза и обычные коммиты в `main`
  сигналом не являются: `main` — текущая разработка.
- Версии по SemVer: patch — совместимые исправления, minor — совместимые
  возможности, major — несовместимые изменения. Опубликованный тег не
  перемещается; исправление выходит следующей версией.
- Релиз закрепляется парой «тег + полный SHA коммита». Применяется только этот
  коммит. Если тег указывает на другой коммит, обновление останавливается.
- Каждый релиз несёт в своём коммите инструкцию `docs/releases/vX.Y.Z.md`
  (для человека и агента) и манифест шагов `docs/releases/vX.Y.Z.json`
  (для скрипта). Шаги будущих версий ждут в `docs/releases/next/`.
- Обновления самого BB и сторонних каталоговых плагинов идут своим путём
  (`bb plugin outdated`, `bb plugin update`). Релиз может задать допустимые
  версии сторонних плагинов.

Релиз bb-config объединяет собственные плагины, спутники и патчи интеграций,
скрипты, навыки и миграции настроек. Внешние продукты из
`config/externally-managed-plugins.json` обновляются своим способом. Настройки
установки восстанавливаются из её приватной копии. Состав компонентов и
порядок действий внутри релиза определяет манифест и состояние установки.

## Как пользователь узнаёт об обновлении

Плагин [Config Updates](../plugins/config-updates) проверяет релизы каждые шесть
часов и по запросу (`bb config-updates check` или «Проверить сейчас» в настройках
плагина). При доступном релизе он показывает уведомление с кнопкой
**«Обновить с ИИ»**. Версия, описание и ручная проверка доступны в настройках. Проверка
ничего не устанавливает. Ошибка сети или GitHub показывается как ошибка
проверки; отсутствие обновлений она не означает.

Для обновлений используйте постоянную рабочую копию на машине сервера и
подключите её к BB как проект. При удалении временного окружения треда BB
может сохранить только исходники плагина в `preserved-source`. В них нет
журнала и `scripts/updates.py`. Проверьте путь через
`bb plugin source config-updates`. При переезде или восстановлении выполните
[порядок восстановления плагинов и журнала](server-backups.md#источники-плагинов-и-журнал-релизов).

Кнопка открывает штатный экран нового треда BB: задание уже вписано, выбраны
проект этого checkout и машина сервера. Провайдера, модель и права пользователь
видит и выбирает сам, затем отправляет сообщение. `bb config-updates start`
запускает тред сразу, с провайдером и моделью проекта по умолчанию. Пока
в журнале открыт запуск, кнопка ведёт в его тред, второй не создаётся.

Если релизу нечего делать на этой установке — все его шаги уже выполнены по
фактическому состоянию или неприменимы, шагов для машин-исполнителей нет, —
плагин при проверке принимает его без агента: `scripts/updates.py accept`
скачивает закреплённый коммит в служебный checkout, записывает проверенные шаги
и отмечает версию установленной. При этом ничего не собирается, не
устанавливается и не настраивается; любая неясность оставляет обычный путь
через агента. Отключается настройкой плагина.

Ход обновления, остаток шагов и состояние зависимостей видны в настройках
плагина и в `bb config-updates status`.

После полностью применённого релиза тред обновления сам уходит в архив, когда
агент закончил ответ (настройка плагина, по умолчанию включена). Тред с
остатком шагов или ошибкой остаётся.

Без плагина то же можно сделать вручную: взять тег и SHA со страницы релиза и
попросить агента выполнить этот документ.

## Порядок применения (для агента)

Скрипт `scripts/updates.py` печатает JSON. Коды выхода: 0 — успех, 1 — ошибка,
2 — остались шаги, 3 — нужно решение пользователя или подтверждение проверки.

1. **Получить релиз.** Из папки действующего скрипта обновлений выполни
   `python3 scripts/updates.py fetch vX.Y.Z --commit <sha> --repository <owner/repo>`.
   Команда получает только этот тег, сверяет полный SHA и возвращает `checkout`
   в `.local/updates/releases/<sha>`. В этом каталоге находятся и исходники, и
   документы релиза. Рабочий checkout разработки, его ветка и локальные правки
   не участвуют в операции. При повторах тег сверяется с GitHub заново.
   Старые шаги продолжают пользоваться своим состоянием в `.local/config` и
   `.local/plugin-patches` действующей установки.
2. **Прочитать инструкции** из возвращённого каталога `checkout`: этот файл и
   `docs/releases/<версия>.md` каждого релиза между установленной версией и
   целевой. Остальные команды запускай из этого каталога. Пропущенные релизы
   применяются по порядку, их шаги не пропускаются.
3. **Открыть запуск.** `bb machine list --json` даёт машины;
   `python3 scripts/updates.py begin vX.Y.Z --commit <sha> --machines <id,id>`
   перечисляет все машины-исполнители, включая машину сервера, если на ней
   работают агенты. Ответ содержит план: незавершённые шаги и их описание.
   Код 3 означает, что обновление уже ведёт другой тред: не дублируй работу,
   открой тот тред. `--takeover` допустим, только если тот тред точно
   остановлен или удалён (`bb thread show <id>`).
4. **Выполнить шаги** в порядке плана.
   - Шаг на сервере: `python3 scripts/updates.py run vX.Y.Z/<шаг>`. Команда
     сначала проверяет фактическое состояние. Уже применённое только
     фиксируется (`how: existing`), миграция не повторяется. Иначе шаг
     применяется и проверяется снова (`how: applied`).
   - Шаг `where: executors` выполняется для каждой машины. На машине сервера:
     `run vX.Y.Z/<шаг> --machine <id>`. На другой машине выполни команды шага
     там штатными средствами BB (`bb terminal`, тред на той машине). Если шаг
     запускает код bb-config, на этой машине сначала получи ровно закреплённые
     тег и SHA в отдельный каталог так же, как в разделе о переходе со старого
     Config Updates. Используй код из этого каталога. После проверки запиши
     результат: `record vX.Y.Z/<шаг> --machine <id> --status verified
     --evidence "<что проверено и что показало>"`.
   - Шаг без автоматической проверки (`kind: manual` без `verify`) выполняется
     по `.md` релиза и записывается через `record` с содержательным
     `--evidence`.
   - Плагин, которого у пользователя нет, не ставится: шаг получает
     `not-applicable`. Новый компонент (`introduces`) ставится только с согласия
     пользователя: `run … --install`; при отказе —
     `record … --status not-applicable --evidence "пользователь отказался"`.
   - Отключённый пользователем плагин обновляется, но остаётся отключённым.
   - Для уже установленного `path:`-плагина из `bb-config` BB переносит источник
     в папку проверенного релиза, сохраняя настройки, секреты и расписания.
     Источник из другого репозитория или каталога остаётся у пользователя.
   - Ошибку шага разбери: сопоставь окружение с инструкцией, исправь причину,
     повтори `run`. Не помечай шаг выполненным без проверки. Недоступная машина
     остаётся в остатке.
5. **Завершить.** `python3 scripts/updates.py finish`. Установленной считается
   старшая версия, все шаги которой и всех предыдущих проверены на сервере и на
   каждой указанной машине. При остатке код выхода 2: версия не повышается,
   остаток виден в `status`, кнопка обновления остаётся. Затем
   `bb config-updates check`.
6. **Сообщить пользователю** по компонентам и машинам: что уже было применено,
   что применено сейчас, что осталось и почему.

### Прерывание и повтор

Повтори шаги 1 и 3 с теми же тегом и SHA: `begin` того же владельца продолжает
запуск, план содержит только незавершённое. `run` безопасен для повторного
вызова. Машину, за которой остался долг, нельзя убрать из списка молча: она
возвращается в план, пока шаг не проверен или не записан как неприменимый.

### Что обновление не делает

- Не применяет снимок настроек автора: `scripts/restore.py` и `config/`
  предназначены для восстановления целой установки, а не для обновления.
- Не меняет личные настройки, аккаунты, маршруты, прокси, состав плагинов и
  выбранные компоненты сверх шагов релиза.
- Не делает commit и push в checkout пользователя.

## Журнал

`.local/updates/journal.json` — локальный, в Git не попадает, секретов не
содержит. Хранит установленную версию, открытый запуск (владелец — ID треда),
остаток прошлого запуска и записи «релиз/шаг, машина, статус, способ, время».
Ключ машины — `server` для шагов сервера и ID машины BB для исполнителей.
Наличие тега или свежего checkout установкой не считается: запись появляется
только после проверки. Потеря журнала безопасна: шаги будут проверены заново
по фактическому состоянию.

- `python3 scripts/updates.py status` — установленная версия, остаток, запуск.
- `python3 scripts/updates.py status --dependencies` — текущая совместимость
  зависимостей, проверенных при установке. Состояние BB сверяется заново при
  `bb config-updates check`. Несовместимая версия не переписывает историю
  применённого релиза. В записи шага остаются проверенные версии и источники.
  У промежуточного релиза, проверенного из содержимого более позднего тега,
  `appliedFrom` указывает фактически использованный коммит. Поле `commit`
  заполняется, когда проверен коммит самого тега.
- `python3 scripts/updates.py baseline vX.Y.Z --commit <sha> --note "…"` — для
  установки, сделанной сразу из релиза (например, восстановление целиком):
  шаги этой и более ранних версий больше не требуются. Не используй, чтобы
  скрыть невыполненные шаги.

## Зависимости плагинов

Поле `after` задаёт порядок шагов. Если серверному шагу нужна работающая
интеграция, укажи ещё `requiresPlugins`. Например,
`[{"id":"addon","min":"1.4.0","before":"2.0.0"}]` требует включённый и
запущенный `addon` с версией от `1.4.0` включительно до `2.0.0` исключительно.
Для точной версии укажи `version` вместо границ. Если зависимость обновляет
другой шаг этого релиза, добавь его ID в `after`.
Указывай требования в каждом шаге обновления интеграции. Пустой список
`requiresPlugins` снимает ранее объявленное требование этого компонента.

При несовместимости шаг остаётся незавершённым, чужой плагин сохраняет свой
источник. Каталоговый плагин пользователь обновляет штатно через BB. Проверка
повторяется перед `finish`, а после ручных обновлений несовместимость видна в
Config Updates. Если интеграцию нужно безопасно отключать при несовместимости,
проверку её возможностей реализует сам плагин.

## Переход со старого Config Updates

Версии до `0.1.6` формируют задание с `fetch`, который делает fast-forward.
При первом переходе, если старая команда останавливается на локальных
изменениях, на сервере подготовь временный каталог, скачай туда только нужный
тег и сверь его SHA с опубликованным обновлением. Для POSIX-shell:

```sh
git init "$bootstrap_dir"
git -C "$bootstrap_dir" fetch --depth=1 --no-tags "https://github.com/$repository.git" "refs/tags/$tag:refs/tags/$tag"
test "$(git -C "$bootstrap_dir" rev-parse "refs/tags/$tag^{commit}")" = "$commit"
```

Если проверка успешна, выполни `git -C "$bootstrap_dir" checkout --detach "$commit"`.
Из этой копии вызови `python3 scripts/updates.py --installation <путь-к-действующему-bb-config> fetch <тег> --commit <sha> --repository <owner/repo>`.
Он возьмёт путь журнала из действующей установки. После этого используй
`checkout`, который вернула команда, и продолжи с шага 2. Дальнейшие обновления
Config Updates запускает с новым заданием. Папки в `.local/updates/releases/`,
на которые ссылаются работающие плагины, должны оставаться на диске.

## Для автора: разработка и публикация

Разработка и публикация разделены.

1. **Разработка.** Агент ставит порученное изменение в работающий BB автора,
   проверяет его и сохраняет в репозитории по `AGENTS.md`. Изменение, которое
   должно дойти до пользователей, в той же задаче получает **ожидающий шаг**:
   пару файлов `docs/releases/next/<id>.json` и `<id>.md` (заготовки —
   `docs/releases/templates/`). Один шаг — одна пара файлов: общий файл
   будущей версии не ведётся, чтобы параллельные задачи не смешивались. В
   шаге: стабильный ID, проверка фактического состояния, скрипт применения,
   повтор и откат. Повторяемые действия оформляются скриптами с режимами
   проверки и применения (например,
   `scripts/migrations/<имя>.py --check|--apply`). Изменённый плагин получает
   новую версию в `package.json`: по ней шаг `local-plugin` отличает старую
   установку от новой. Проверка шага у автора:
   `python3 scripts/updates.py run next/<id> --development`. Запись получает
   режим `development` и публикацией не считается.
   Для изолированной проверки можно запустить отдельный BB с временными
   данными. Если проверка идёт на основном BB автора, `--development` из
   рабочего checkout может перевести свой плагин с каталога релиза обратно на
   рабочий источник. Версия из разработки останется отдельной записью журнала.
2. **Commit и push** по поручению сохраняют разработку. Шаг коммитится вместе
   со своим изменением. Пользователи остаются на прежнем релизе.
3. **«Публикуй обновление»** — отдельное поручение. Агент:
   - если в `main` есть изменения для других выпусков, делает ветку выпуска
     от последнего стабильного тега и переносит в неё только выбранные изменения;
   - выбирает ожидающие шаги, изменения которых закоммичены, и собирает
     версию: `python3 scripts/updates.py release vX.Y.Z --title "…"
     [--steps id,id]`. Команда пишет `docs/releases/vX.Y.Z.json` и `.md`,
     убирает использованные файлы из `next/` и отказывается, если у плагина
     шага есть незакоммиченные правки. Невыбранные шаги остаются ждать;
   - дополняет `.md` разделами «Что изменилось» и «Проверка релиза», коммитит
     и пушит;
   - из чистого клона этого коммита проверяет
     `python3 scripts/updates.py validate vX.Y.Z` (в том числе: плагин шага
     действительно изменён в коммите), `python3 -m unittest discover -s scripts
     -p 'test_*.py'`, тесты затронутых плагинов;
   - `python3 scripts/privacy_check.py --history`; в инструкциях и манифесте нет
     путей, ID машин, адресов и настроек автора;
   - сверяет diff от прошлого релиза с шагами: каждое изменение, требующее
     действия у пользователя, имеет шаг, и ни один шаг не ссылается на то,
     чего в коммите нет;
   - создаёт стабильный релиз на точном коммите:
     `gh release create vX.Y.Z --target <sha> --title "…" --notes-file <описание>`
     без `--draft` и `--prerelease`. Описание — раздел «Что изменилось» и ссылка
     на `docs/releases/vX.Y.Z.md` в этом теге.
     Коммит выпуска должен войти в историю `main` с сохранением изменений
     других задач. Тег остаётся на проверенном коммите ветки выпуска.
4. **Установка автора после публикации.** Плагин покажет собственный релиз.
   Обновление проходит тот же порядок: шаги, применённые при разработке,
   проверяются и получают запись `existing` без повторной миграции. Версия
   плагина сверяется с закреплённым коммитом. Более новая работающая сборка
   автора остаётся на месте. Плагин с совпадающей версией, который всё ещё
   подключён к рабочей папке, переводится на исходники проверенного релиза.
5. **Ошибка в опубликованном релизе** исправляется следующей версией. Тег не
   перемещается. Ошибочный шаг можно убрать из манифеста прошлой версии в
   новом коммите с пометкой в её `.md`: манифесты читаются из коммита целевого
   релиза.

Проверки механизма: `python3 -m unittest scripts/test_updates.py` (из каталога
`scripts`: `python3 -m unittest test_updates`) и `npm test` в
`plugins/config-updates`.
